第 04 章

Skills

把高频操作封装成可复用的指令，让 Codex 一键执行复杂流程

一份 SKILL.md，按需触发；一次定义，反复生效

从零开始

你每次都要教 Codex 怎么完成同一个任务

场景一：写论文引言

"帮我写一段引言，要包含研究背景、问题陈述、贡献点，用学术语气，引用近三年的文献。"

你花了 5 分钟描述格式要求。

场景二：又要写引言

下周写另一篇论文，你又要重新描述一遍同样的格式要求。

第三次。第五次。每次都在重复。

根本原因

AGENTS.md 解决的是"项目规则"，但任务级的操作流程没有被封装。你需要一种机制，把"怎么做某件事"写一次，以后直接调用。

开始之前

适合谁

  • 经常让 Codex 做同类任务（写文档、查论文、操作 PR）
  • 想把自己的工作流程标准化，减少重复描述
  • 想复用社区或团队共享的 Skill 模板

你将学会

  • 理解 Skill 的本质与目录结构
  • 查阅 内置 System Skills 的能力
  • 创建自己的自定义 Skill
  • 掌握 Skill 的渐进式加载机制

本章不覆盖

  • AGENTS.md（第 02 章）：项目级规则
  • Slash Commands（第 03 章）：命令入口
  • MCP（第 06 章）：工具扩展

是什么

给 AI 的"工作手册"——在什么场景、按什么规则、用什么工具

一句话定义

Skill 是一个目录，里面有一个 SKILL.md 文件。它告诉 Codex：在什么场景下、按什么规则、用什么工具完成任务。

类似物

  • 给新员工的 SOP 操作手册
  • 函数库里的 API 文档
  • 烹饪食谱——食材、步骤、火候

核心特征

  • 按需触发：不是每次加载，而是匹配到场景才激活
  • 自包含：指令、脚本、参考文档都在一个目录里
  • 可组合：多个 Skill 可以同时生效

Skill vs AGENTS.md

两者互补，不是替代

维度 AGENTS.md Skill
作用域 项目级，始终生效 任务级，按需触发
内容 "你该怎么做事"（规则） "怎么做这件事"（流程）
加载时机 会话启动时全部加载 匹配到 description 才加载
文件格式 单个 Markdown 文件 目录 + SKILL.md + 资源
典型例子 "用 TypeScript，命名用 camelCase" "review PR 时按这个 checklist 逐项检查"
选择指南：如果一个指令在任何时候都适用 → AGENTS.md。如果只在特定任务或流程中触发 → Skill。两者可以互相引用。

目录结构

一个 Skill 就是一个自包含的文件夹

skill-name/
├── SKILL.md              # 必需：核心指令文件
│   ├── YAML frontmatter  # 必需：name + description
│   └── Markdown body     # 必需：具体指令内容
├── agents/               # 推荐：UI 元数据
│   └── openai.yaml
└── Bundled Resources     # 可选：辅助资源
    ├── scripts/          # 可执行脚本
    ├── references/       # 参考文档
    └── assets/           # 模板、图标等
关键：只有 SKILL.md 是必需的。其他目录按需添加，让 Skill 从"纯指令"升级为"带工具的工作流"。

SKILL.md 结构

frontmatter 决定触发，body 决定执行

什么是 frontmatter？它是文件最顶部、用三条横线 --- 包裹的一段元数据（YAML 格式）。你可以把它理解为这个 Skill 的"身份证"——Codex 不读这里的正文内容，只读这里的字段（如 name、description）来决定"要不要激活这个 Skill"。三条横线下方的正文叫 body，才是 Skill 被激活后真正执行的指令。 
---
name: skill-name
description: 一句话描述，决定何时触发此 Skill
---

# Skill 标题

## 使用说明
在这里写具体的操作步骤、注意事项和输出格式。

## 示例
给出一个典型用例，帮助 Codex 理解你的期望。

frontmatter 字段

  • name（必需）：Skill 的唯一标识
  • description（必需）：最关键——Codex 根据这段描述判断何时激活此 Skill

body 内容

  • 具体的操作步骤和规则
  • 输入输出格式要求
  • 引用的脚本或参考文档路径
  • $ARGUMENTS 占位符接收用户参数

description 决定触发

写好 description 是 Skill 成功的关键

好的 description

description: 生成或编辑 raster 图片，
适用于封面、插图、去背景等场景。
用户说"画个封面""去背景"时触发。

✅ 说明了做什么、什么时候、典型触发词

差的 description

description: 图片工具

❌ 太模糊，Codex 不知道何时该用这个 Skill

注意：description 不是给用户看的，是给 Codex 的匹配引擎看的。要具体、要包含触发场景和关键词。

自定义 Skill

在两个位置创建，作用域不同

全局 Skill

~/.codex/skills/
└── my-skill/
    └── SKILL.md

对所有项目生效，适合个人通用的工作流（如写作风格、代码审查偏好）。

项目 Skill

.codex/skills/
└── my-skill/
    └── SKILL.md

仅对当前项目生效，适合项目特有的流程（如发布 checklist、部署流程）。

优先级：项目级 Skill 优先于全局 Skill。同名时，项目内的版本胜出。

自定义 Skill 示例

一个实际的 commit message 规范 Skill

---
name: commit-message
description: 生成符合 Conventional Commits 规范的
 commit message。当用户说"帮我写个 commit message"
 或"生成提交信息"时触发。
---

# Commit Message 生成器

## 规则
1. 格式：`<type>(<scope>): <subject>`
2. type 必须是以下之一：
   - feat: 新功能
   - fix: 修复 bug
   - docs: 文档变更
   - refactor: 重构
   - test: 测试相关
   - chore: 构建/工具变更
3. subject 用中文，不超过 50 字
4. 不要加句号

## 输入
$ARGUMENTS（用户的改动描述）

## 输出
直接输出一行 commit message，不要解释。

加载机制

渐进式加载，按需激活

第一步：扫描 frontmatter

Codex 启动时扫描所有可用 Skill 目录，只读取 SKILL.md 的 YAML frontmatter（name + description）。这一步很轻量。

第二步：匹配 description

当用户发出请求时，Codex 将请求与各 Skill 的 description 进行语义匹配。匹配度最高的 Skill 被选中。

第三步：加载 body

只有被选中的 Skill 才会加载 Markdown body 内容。未匹配的 Skill 不占用上下文窗口。

第四步：按需加载资源

如果 body 中引用了 scripts/、references/ 或 assets/，这些文件在需要时才被读取。

设计优势：渐进式加载意味着即使安装了 50 个 Skill，每次会话只加载匹配的那几个，不会撑爆上下文窗口。

最佳实践

写出高质量 Skill 的几个原则

description 要精准

包含做什么、什么时候、典型触发词。这是 Skill 能否被正确触发的关键。

body 要简洁

只写 Codex 不知道的信息。它已经很聪明了，不需要教它基础概念。每多一行，就多占一点上下文。

善用 $ARGUMENTS

用 $ARGUMENTS 接收用户传入的参数，让 Skill 更灵活。不要硬编码具体值。

资源按需引用

大段参考资料放 references/，脚本放 scripts/，不要在 body 里堆砌。

常见误区

避开这些坑，Skill 才能好用

❌ 误区一：description 太宽泛

"处理文件"——Codex 不知道什么时候该用。改成"将 Markdown 转换为符合公司模板的 Word 文档"。

❌ 误区二：body 太长

写了 500 行指令。结果：上下文被撑爆，执行变慢。保持精简，复杂逻辑拆到 scripts/。

❌ 误区三：和 AGENTS.md 混淆

"用 TypeScript" 应该放 AGENTS.md。"按以下流程发布 npm 包" 应该放 Skill。规则 vs 流程。

内置 Skills

覆盖生图、文档、PPT、浏览器、PR 操作等场景。开箱即用，按需触发。
