Agent SDK 与动态工作流

把 AI 能力嵌入你的程序，编排大规模 AI 协作

当 AI 能被编程调度，软件开发的范式才真正改变

CLI 还不够

有些场景，你需要用代码精细控制 AI

想把它嵌进产品

你做一个开发者工具，想集成 Qoder 的 AI 能力，但 CLI 是给人用的，没有编程接口。

复杂编排做不到

"让 5 个 AI 专家并行评审，再让 1 个汇总，最后让第 7 个挑刺"——这种复杂编排，对话和脚本都很难表达。

想动态决策

根据上一步结果决定下一步做什么——这种条件分支、循环、并行的逻辑，需要真正的编程语言。

本章给出两个答案：① Agent SDK——用 TypeScript/Python 把 AI 能力嵌进你的程序；② 动态工作流——用 JavaScript 编排大规模 AI 协作。这是 Qoder CLI 能力栈的最顶层。

什么是 SDK

定义、白话、和 CLI 的关系

Agent SDK 是 Qoder 提供的编程库（TypeScript 和 Python 两个版本），让你在自己的代码里直接调用 AI 的能力——读文件、改代码、执行命令、委派子代理，全部通过 API 控制。

说白了，CLI 是给人用的遥控器，SDK 是给程序用的接口。同一个 AI 引擎，两种调用方式：你敲命令，或你的代码调函数。

CLI（命令行）

  • 给人用，交互式或 Print 模式
  • 配置驱动（文件、参数）
  • 适合开发者日常工作
  • 编排能力有限

SDK（编程库）

  • 给程序用，代码调用
  • 代码驱动，完全可编程
  • 适合构建 AI 产品/工具
  • 可表达任意复杂逻辑

SDK 用法

用几行代码唤起一个 AI 会话

TypeScript 示例——在你的程序里创建一个 AI agent，让它完成任务：

import { query } from "@qoder-ai/qoder-sdk";

// 用一行代码发起一个 AI 任务
const result = await query({
  prompt: "审查 src/ 目录的代码，找出潜在 bug",
  options: {
    permissionMode: "plan",       // 只读模式，安全
    outputFormat: "json",         // 结构化输出
    allowedTools: ["Read", "Grep", "Glob"]
  }
});

console.log(result.text);  // 处理 AI 返回的结果
SDK 的威力：你拿到了 AI 的结果作为程序变量，可以继续处理——存数据库、发通知、传给下一个 AI、做条件判断。AI 成了你程序里的一个函数调用。

SDK 场景

什么时候该用 SDK 而不是 CLI

构建 AI 产品

做一个代码审查 SaaS、智能 commit 工具、自动化文档平台——把 AI 能力包装成你的产品。

定制工作流

有独特的研发流程，CLI 的配置不够灵活——用代码精确描述你的流程。

批量处理

遍历 100 个仓库做统一改造、分析 1000 个文件——代码循环比手动高效。

嵌入现有系统

把 AI 能力加进你的 CI 平台、IDE 插件、内部工具——SDK 是集成的基础。

别为了用 SDK 而用 SDK。如果你的需求 CLI + 脚本就能满足，没必要上 SDK。SDK 适合需要编程级控制力的场景——产品化、复杂逻辑、深度集成。

动态工作流

用 JavaScript 编排大规模 AI 协作

动态工作流是 Qoder 的高级编排能力：用 JavaScript 脚本描述多个 AI 如何协作——谁先做、谁后做、谁并行、谁汇总。它提供几个核心原语：

原语作用
agent()创建并调用一个 AI agent 执行任务
parallel()让多个 agent 同时执行
pipeline()让任务串行流水线式推进
phase()划分执行阶段
启用方式：动态工作流是高级功能，通常需要环境变量启用（如 CLAUDE_CODE_WORKFLOWS=1，Qoder 沿用类似机制），并通过特定关键字（如 ultracode）或 SDK 触发。具体开关以官方文档为准。

工作流示例

一个"多专家并行评审 + 汇总"的工作流

// 伪代码：展示工作流的编排思路
const reviews = await parallel([
  agent({ role: "security-auditor", task: "查安全问题" }),
  agent({ role: "perf-analyst",     task: "查性能问题" }),
  agent({ role: "code-reviewer",    task: "查代码质量" })
]);
// 三个专家并行跑，各自专注一面

const summary = await agent({
  role: "tech-lead",
  task: `汇总这三份评审，按优先级排序：${JSON.stringify(reviews)}`
});

return summary;
这段编排的含义：三个专家 AI同时从不同角度评审（并行省时），结果交给一个"技术负责人"AI 汇总排序。用代码精确描述了协作结构——这是对话和脚本都难以做到的。
运行约束：工作流有并发限制（如同时不超过 16 个 agent）、总量限制（如单次最多 1000 个）、以及一些确定性约束（如不使用 Date.now()，保证可复现）。具体数值以官方文档为准。

对抗式验证

工作流的高级用法——让 AI 互相挑刺

动态工作流最强大的模式之一是对抗式验证：让一个 AI 写代码，另一个 AI 专门挑刺，形成"红蓝对抗"。

图：对抗式验证工作流

【AI 生图提示词】请生成一张中文技术示意图，风格简洁、配色柔和、适合教学： - 画面主体：三个 AI agent 方框，分别标注"实现者"、"攻击者"、"裁判" - 各元素关系：实现者产出代码 → 攻击者找漏洞 → 裁判判定。攻击者和实现者之间画双向箭头表示"对抗"，裁判在下方用单向箭头指向"最终结果" - 在右侧画一个循环箭头，标注"未通过则回到实现者修复" - 配色建议：实现者用蓝色，攻击者用红色，裁判用橙色，背景浅灰 - 画面比例：16:9

实现者

写代码、修 bug、实现功能。

攻击者

专门找实现者的破绽——边界情况、安全漏洞、逻辑错误。

裁判

判断攻击是否成立，决定通过还是打回重做。

为什么有效：单个 AI 容易"自满"——写完就觉得没问题。对抗机制强制它接受审视，显著提升产出质量。这是 AI 协作的高级形态。

如何选择

CLI、SDK、工作流——三个层次各管一段

层次适合典型用户
CLI（含 Print 模式） 日常开发、CI 自动化、脚本任务 所有开发者
Agent SDK 构建 AI 产品、定制工作流、深度集成 工具/产品开发者
动态工作流 大规模 AI 协作、对抗验证、复杂编排 AI 工程师、高级用户
选择原则：从 CLI 开始——它覆盖 90% 的需求。当你需要"编程级控制"时上 SDK；当你需要"多 AI 复杂协作"时上工作流。不要跳级，每一层都建立在前一层的理解上。

排错指南

SDK 与工作流相关的高频问题

SDK 认证失败

原因：Token 未配置或失效。修复：设置 QODER_PERSONAL_ACCESS_TOKEN 环境变量；确认 Token 未过期。

工作流没触发

原因：未启用工作流功能。修复：设置启用环境变量；确认用的触发关键字正确；查官方文档当前启用方式。

并发超限

原因：同时调度的 agent 超过上限。修复：减少 parallel 的并发数；分批处理。

结果不确定（每次不同）

原因：用了非确定性函数（如时间）。修复：工作流内避免 Date.now() 等；需要确定性时固定随机种子。
