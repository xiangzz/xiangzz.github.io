Advanced Features

高级特性——让复杂任务变得可控

Planning、Thinking、Auto Mode、后台任务、会话管理、Worktree、沙盒、配置等

任务变复杂后

你有没有发现，Claude 处理简单任务很好用，但任务一复杂就开始跑偏？

改着改着就偏了

让 Claude 给项目加通知系统。它改了 15 个文件，改到一半你已经看不懂了。它到底在按什么计划做事？

想不清楚就动手

让 Claude 重构认证模块。它直接开始改代码，没有先跟你确认方案。改完才发现方向不对，回退成本很大。

到处都是确认框

给 Claude 一个自动化任务，但每一步都要手动确认权限。10 个步骤点了 10 次"允许"，比自己做还慢。

高级特性就是为这些场景设计的：Planning Mode 让 Claude 先规划再动手，Extended Thinking 让它想得更深，Auto Mode 让它在安全边界内自动执行。不是让 Claude 变得更聪明，而是让你对复杂任务的控制力更强。

深度推理

Extended Thinking：让 Claude 在给出方案前多想一会儿

Extended Thinking让 Claude 在给出解决方案前，花更多时间进行分步骤推理。

说白了，就是让 Claude "先打草稿再写正式答案"。草稿不打给你看，但最终答案质量更高。这个比喻只是为了帮你建立直观感受。实际上，Extended Thinking 是模型在推理时分配额外的计算预算（推理 token），用于内部的链式思考。这些思考过程不会展示给你，但直接影响输出的质量和深度。

级别符号适合场景
low○简单任务，快速响应
medium◐常规任务（默认）
high●复杂任务，需要深入推理
max◉极复杂任务（仅 Opus）
 
# 通过 CLI 设置
$ claude --effort high "设计缓存策略"

# 通过 slash command
$ /effort max

# 快捷键：Option+T (macOS) / Alt+T (Win/Linux)

# 配置文件
# ~/.claude/settings.json
{
  "thinking": {
    "enabled": true,
    "effort": "high"
  }
}

权限与自动化

六种权限模式，对应不同的自动化程度

Auto Mode（研究预览）：每个动作执行前，后台安全分类器评估风险。安全 → 自动执行，需确认 → 提示你，危险 → 阻止。
模式行为适合
default必要时询问权限日常开发
plan只规划，不执行复杂任务规划
acceptEdits自动接受编辑受控环境
auto自动执行 + 安全审查自动化场景
dontAsk自动执行，但不做安全审查信任环境下的快速操作
bypassPermissions跳过所有权限完全信任的 CI
 
# 启用 Auto Mode
$ claude --enable-auto-mode

# 然后在 REPL 中用 Shift+Tab 切换到它

分类器默认允许

  • 只读检查（cat、ls、grep）
  • 常规分析和搜索
  • 低风险文件修改

分类器默认阻止

  • 明显危险的文件操作（rm -rf）
  • 高风险 shell 命令
  • 可能泄露凭据的操作
回退行为：如果分类器无法判定风险，Claude 会回退到更保守的权限处理方式，即提示你确认。建议先用 default 观察行为模式，再逐步切换到 auto。
安全提醒：bypassPermissions 只应在完全信任的 CI 环境中使用。本地开发请用 default 或 auto。

Print Mode

非交互式输出——给一个任务，输出结果，然后退出

claude -p 适合自动化和 CI/CD。不需要交互，直接输出结果。

# 基本用法
$ claude -p "run tests and summarize failures"

# 管道输入
$ cat logs.txt | claude -p "find the root cause"

# JSON 输出
$ claude -p --output-format json "list all functions"

# CI/CD 集成
$ claude -p "review this diff and return JSON" > report.json
输出格式：text（默认）、json（结构化，可配合 jq 处理）、stream-json（流式，适合实时处理长输出）。

限制自主回合数

Print Mode 默认允许 Claude 多步执行。你可以限制回合数，防止跑偏：

$ claude -p --max-turns 3 "fix the lint errors"

CI/CD 集成要点

  • 用 --output-format json 获取结构化结果
  • 用 --max-turns 限制执行步数
  • 输出重定向到文件做后续处理
  • 配合 bypassPermissions 实现全自动

长时间运行的任务不阻塞对话，定时任务按计划重复执行

后台任务

构建、测试、下载、安全扫描等长时间运行的任务，放到后台执行。完成后收到通知。

会话管理

在多个会话之间恢复、重命名、分叉和持续工作

核心思路：会话是你和 Claude 的工作上下文。管理好会话，等于管理好工作历史。可以随时恢复、分叉、命名，让复杂项目的多线索工作变得可控。
命令作用场景
claude -c继续最后一次对话关掉终端后接着干
claude -r "name"恢复指定名称/ID 的会话回到之前某个任务
/resume在 REPL 中恢复历史会话切换上下文
/rename给当前会话重命名标记用途，方便查找
/fork分叉当前会话想实验但不破坏原会话
 
# 继续最后一次对话
$ claude -c

# 恢复指定会话
$ claude -r "feature-auth"

# 恢复并分叉——适合在已有会话上做实验
$ claude -r "feature-auth" --fork
会话持久化：你可以选择保留、继续或重建会话上下文。为重要会话命名（/rename），需要时分叉（/fork）而不是硬改——这是会话管理的最佳实践。

Worktree

隔离目录并行工作——实验、重构互不干扰

Git Worktree 的价值：在隔离的工作目录里并行开发，主分支保持整洁。一个 worktree 做实验，另一个做稳定开发，互不影响。 
# 在隔离 worktree 中启动 Claude Code
$ claude -w

# Monorepo 场景：sparse checkout 只加载需要的部分
# 大型 monorepo 中配合使用，提升效率

核心特性

  • 隔离目录：每个 worktree 是独立工作区
  • Worktree 位置：控制放置位置，保持主工作区整洁
  • 自动清理：不需要的 worktree 可以自动清理
  • Hooks 支持：worktree 场景下依然可以配合工具和 hooks

典型场景

  • 并行尝试多个方案，对比效果
  • 隔离高风险重构，不影响主分支
  • 保持主分支整洁，review 时更清晰

沙盒隔离

操作系统级文件系统和网络隔离，显著降低自动化操作风险

沙盒的作用：限制 Claude 可触达的文件和网络边界。即使 Claude 的操作有误，也不会影响到隔离范围之外的内容。

可配置项

  • 允许访问的目录白名单

  • 例外列表

适合场景

  • 低风险自动化
  • 在不完全信任的输入上执行任务

任务列表

跨 context compaction 持久保存任务进度

为什么需要任务列表？当对话变得很长，Claude 会进行 context compaction（压缩上下文）。普通的待办事项会丢失，但任务列表中的任务会被持久保留，即使上下文被压缩也能继续跟踪。

核心能力

  • 持久任务：context compaction 后任务不丢失
  • 切换显示：在设置中打开或关闭任务列表
  • 命名目录：给任务分组或目录命名，方便管理

环境变量

# 通过环境变量控制
CLAUDE_TASK_LIST=true

适合长期运行的任务——你不用反复提醒 Claude 做什么，任务列表会替你记住。

举个例子：你用 Planning Mode 做一个"添加日志系统"的规划。计划生成后，把不同阶段分给 Subagent 执行（一个负责后端、一个负责前端）。每个阶段完成后自动触发 Hook 做质量检查。如果某个阶段结果不对，用 Checkpoint Rewind 回去重来。

高级特性把前面学的所有模块串成一条完整的复杂任务处理链。

排错指南

过度规划

症状：连改个 CSS 都要先做一份三阶段计划，反而浪费时间。

修复：简单任务直接做，复杂任务才规划。判断标准：涉及 3 个以上文件或需要分步验证的才算"复杂"。

计划没有验收标准

症状：计划写了一堆步骤，但每步做完了不知道对不对。

修复：每个阶段必须有明确的验证方式——"运行测试通过"、"编译无报错"、"页面正常加载"。

Extended Thinking 用太多

症状：所有任务都用 max 级别推理，响应变慢。

修复：只在架构决策、复杂 bug 排查、多方案比较时用 high/max。日常编码用默认级别即可。

Auto Mode 太激进

症状：Auto Mode 下 Claude 执行了意料之外的破坏性操作。

修复：先用 default 模式观察 Claude 的行为模式，确认安全后再切到 auto。生产环境慎用 bypassPermissions。

动手练习

写一份可执行的计划骨架

不用真的去执行——只写计划。重点是想清楚"分几个阶段、每个阶段验证什么、有什么风险"。

  • 用 /plan 触发规划
  • 输出包含 3-4 个阶段
  • 每个阶段有明确的验证标准

参考答案

/plan 为项目添加结构化日志系统

## 实现计划

### 阶段 1：基础设施
1. 添加日志依赖（SLF4J + Logback）
2. 创建 logback.xml 配置文件
3. 定义日志格式和输出目标
**验证**: 启动应用，控制台输出结构化日志

### 阶段 2：核心集成
4. 创建 LoggingAspect（AOP 切面）
5. 为 Controller 层添加请求/响应日志
6. 为 Service 层添加业务操作日志
**验证**: 调用 API，日志中记录完整请求链路

### 阶段 3：错误处理
7. 全局异常处理器添加错误日志
8. 慢查询日志（超过 500ms）
9. 敏感字段脱敏处理
**验证**: 模拟异常，确认日志不含敏感信息

### 关键风险
- 日志量过大 → 采样策略
- 敏感信息泄露 → 脱敏规则
- 磁盘空间不足 → 滚动策略
计划三要素：分阶段（不是一口气全做完）、有验证（每个阶段能确认做对了）、识风险（提前想好哪里可能出问题）。
