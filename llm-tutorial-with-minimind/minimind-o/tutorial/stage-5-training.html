从会写到会说

阶段 5 · 全模态模型的训练流水线

训练难在哪

如果你训练过纯文本 LLM，套路很熟：搭好数据，写个训练循环，让它跑。但 MiniMind-O 多了两层麻烦：

  • 它要同时学好「写字」和「说话」两件事，不能让其中一件把另一件压垮
  • 它站在 SenseVoice/SigLIP2/Mimi 这些冻结的外部编码器之上，要先让它们和 Thinker 对齐

所以 MiniMind-O 的训练不是「一把梭」，而是精心设计的三阶段流水线——先学会根据文字出声，再学会听懂声音，最后端到端打通。本章拆解这条流水线，以及让训练既快又稳的工程技巧。

Part 1：为何不能一把梭

三阶段流水线，每阶段只解决一个子问题。

如果直接全量训练会怎样

设想最激进的做法：所有参数一起解冻，所有数据一起喂，一个损失加总，开训。结果几乎注定失败——因为模型同时面对太多陌生信号（要学文字、要学声音、要学对齐编码器），梯度方向打架，根本收敛不了。

MiniMind-O 的解法：拆成三个阶段，每个阶段只让一部分参数学习、只喂一类数据、只优化一个目标。像搭积木一样，每一步都站在上一步的成果上。

阶段 1：T2A

先学会「看着字说话」

T2A = Text-to-Audio。这个阶段的目标单纯：给 Talker 一段文字，让它学会生成对应的声音。

  • 数据：文本 SFT 数据 + 配对的音频
  • 策略：从已有的 LLM 权重初始化 Thinker，所有参数都可训练
  • 学到什么：Talker 能根据文本意图，产出像样的语音

这一步先把「嘴」练熟。Mini 版本约 60 分钟。

Talker 怎么站起来

从 Thinker 拷层初始化

📌 对应源码：trainer_utils.py 的 init_omni_model() 第 81-89 行

Talker 是一个全新随机初始化的小 Transformer（只有几层），如果直接从随机权重开始学语音生成，几乎不可能收敛。MiniMind-O 的关键技巧：把 Thinker 最后几层的权重，直接复制给 Talker 的前几层，给 Talker 一个「已经懂语言」的起点。

📜 真实源码：trainer_utils.py 第 81-89 行

if from_resume == 0 and omni_config.talker_hidden_size == omni_config.hidden_size:
    n_talker = omni_config.num_talker_hidden_layers   # Talker 层数
    n_thinker = len(model.thinker.layers)             # Thinker 层数
    has_talker = any(k.startswith('talker.layers.') for k in weights)
    if not has_talker and n_talker > 0:
        for i in range(n_talker):
            src = n_thinker - n_talker + i
            # 把 Thinker 倒数第 n_talker 层，逐层拷给 Talker 第 i 层
            model.talker.layers[i].load_state_dict(
                model.thinker.layers[src].state_dict())
        Logger(f'Talker层初始化: 复制thinker layers[{n_thinker-n_talker}:{n_thinker}] → talker layers[0:{n_talker}]')

三个生效前提要注意：(1) from_resume == 0——首次训练才拷，续训不拷；(2) 权重里没有 talker.layers.* 键（说明 Talker 是新的）；(3) talker_hidden_size == hidden_size——两者隐藏维度一致才能直接搬。这就是「阶段 1 能训出语音」的真正起点：Talker 不是从零开始，而是站在 Thinker 的肩膀上。

阶段 2：A2A Proj

让耳朵和大脑对齐

A2A = Audio-to-Audio。这一步要解决「怎么听」的问题。但不是全量训练，而是冻结一切，只训练音频投影器。

为什么？因为 SenseVoice（音频编码器）是冻结的，它的输出维度（512）和 Thinker 的输入（768）还没对齐。这个阶段就是专门练那个小小的音频投影器，让 SenseVoice 的特征能被 Thinker 理解。

  • 策略：mode='audio_proj'，冻结 Thinker/Talker，只解冻音频投影器
  • 学到什么：音频编码器的输出，能被 Thinker 正确理解

Mini 版本约 15 分钟（投影器很小，训得快）。

阶段 3：A2A Full

端到端打通

前两步分别练好了「嘴」和「耳朵对齐」。最后一步解冻所有参数，用小学习率端到端微调，让「听 → 想 → 说」整条链路协同。

  • 策略：mode='all'，全参数可训练，但学习率很小（2e-5）
  • 学到什么：听懂语音 → 理解 → 用语音回复的完整能力

两个独立的冻结旋钮

📌 对应源码：train_sft_omni.py 第 211-216 行（args.mode 分支）+ trainer_utils.py 的 init_omni_model() 第 92-103 行（freeze_backbone 分支）

关键纠正：之前的表把「Thinker 冻结」归到 mode 上，是错的。源码里其实是两个相互独立的旋钮，作用对象不同，可以叠加：

旋钮（命令行参数）作用对象取值谁会被冻结/解冻
--mode投影层all不动 requires_grad，全量训练（默认）
--mode投影层audio_proj先全冻结，再只解冻 model.audio_proj
--mode投影层vision_proj先全冻结，再只解冻 model.vision_proj
--freeze_backboneThinker 主干noneThinker 主干全可训（默认）
--freeze_backboneThinker 主干all冻结整个 Thinker 主干 model.model
--freeze_backboneThinker 主干last1冻主干但解冻 Thinker 最后一层

两者会叠加，但有先后：--freeze_backbone 在更早的 init_omni_model() 里先动 Thinker 主干；--mode 在 train_sft_omni.py 主流程里后动，且 audio_proj/vision_proj 会先来一句 for p in model.parameters(): p.requires_grad = False——这一刀把主干也连带冻结了，再单独解冻投影器。所以阶段 2（A2A Proj）只需要 --mode audio_proj 一个参数就够，主干自然被冻住，--freeze_backbone 在这里写不写都一样。

那 --freeze_backbone 什么时候才真正有用？在 --mode all（阶段 3 全量训练）时——此时 mode 不碰 requires_grad，主干默认全可训；如果你想在阶段 3 也冻住 Thinker 主干只微调 Talker，就加 --freeze_backbone all。

之前为便于理解讲成「mode 一档同时控制 Thinker」，真实实现是：--mode 走 audio_proj/vision_proj 时会全冻结（含主干）再解冻投影层；Thinker 主干的独立冻结则由 --freeze_backbone 在 mode=all 场景下负责。

Part 2：端平三种损失

全模态训练的损失不是一个数，是三个数的加权组合。

三个损失项

📌 对应源码：train_sft_omni.py 的 train_epoch() 第 93、95 行

# 第 93 行：8 层音频损失求和后，先除以 8 得到「平均单层损失」
audio_loss = audio_loss / 8

# 第 95 行：三项相加，再整体除以梯度累积步数
loss = (text_loss + audio_loss + res.aux_loss) / args.accumulation_steps

别被公式里的 audio_loss 搞混。第 95 行用的 audio_loss 是上一行已经除过 8 的值，所以它和 text_loss 量级相当，不再需要额外缩放。除以 accumulation_steps 是因为梯度累积——累积 N 步才更新一次，每步只回传 1/N 的损失，保证累积总梯度等价于一个大 batch。

损失衡量什么
text_loss文本预测得准不准（预测下一个词）
audio_loss8 层音频码的平均单层损失（已除以 8）
aux_lossMoE 专家负载是否均衡（可选）

这三项加起来反传梯度，模型同时学习写字和说话。下面两页讲决定它们能否和平共处的两个细节。

文本损失的手动掩码

text_loss 怎么忽略 padding

📌 对应源码：train_sft_omni.py 的 train_epoch() 第 74-79 行

一个 batch 里序列长度不一，短的会被 -100 填充（padding + 不计算损失的 prompt 段）。常规做法是 CrossEntropyLoss(ignore_index=-100)，但 MiniMind-O 没用这个参数，而是手动掩码，原因是要和后面 audio 的加权写法保持一致。

📜 真实源码：train_sft_omni.py 第 74-79 行

loss_fct = nn.CrossEntropyLoss(reduction='none')   # 不聚合，逐元素

# Text loss —— 手动忽略 -100
text_loss_raw = loss_fct(res.logits.view(-1, res.logits.size(-1)), labels.view(-1))
text_mask = (labels.view(-1) != -100).float()       # 有效 token 位置为 1
text_loss = (text_loss_raw * text_mask).sum() / (text_mask.sum() + 1e-9)

关键三步：(1) reduction='none' 让损失不自动求平均，逐 token 返回；(2) 构造 text_mask 把 padding(-100) 位置乘成 0；(3) 分母只数有效 token 数 text_mask.sum()，加 1e-9 防全 0 除零。这样 padding 既不影响分子也不影响分母，干净忽略。

音频损失为何除以 8

音频损失是 8 层码本损失相加的。如果不除以 8，audio_loss 会天然比 text_loss 大好几倍——梯度被音频主导，模型的「脑力」全用在学说话上，文字能力反而退化。

不除以 8

audio_loss ≈ 8 × 单层损失

音频主导训练，文字被压制

除以 8

audio_loss ≈ 单层损失的平均

和 text_loss 量级相当，平衡训练

停止码为何权重 ×10

一句话里可能有上千个普通音频码，但停止码只有 1 个。如果不加权重，模型很容易忽略这个唯一的停止码——结果就是音频无限生成，停不下来。

📌 对应源码：train_sft_omni.py 的 train_epoch()（音频损失计算段，第 83-93 行）

教程简化版

# 直觉理解：停止码(2050)权重放大到 10 倍
weight = 10.0 if target == STOP else 1.0
audio_loss = (ce(logits, target) * weight).mean()

把「加权」抽象成一个简单的条件权重，便于先建立直觉。

真实源码 train_sft_omni.py:86-92

layer_loss = loss_fct(al_flat, target_flat)   # reduction='none'
valid_mask = (target_flat != -100).float()     # 忽略 padding
stop_mask  = (target_flat == 2050).float()     # 停止码位置
weighted_loss = layer_loss * valid_mask * (1 + stop_mask * 9)
msum = valid_mask.sum()
if msum > 0:
    audio_loss += weighted_loss.sum() / (msum + 1e-9)

没有 if，全靠向量化掩码相乘：停止码权重 = 1 + 1×9 = 10，普通码权重 = 1 + 0×9 = 1，再乘 valid_mask 顺带忽略 padding。

之前为便于理解写成 weight = 10.0 if ... else 1.0，真实实现是向量化掩码乘法 loss * valid_mask * (1 + stop_mask * 9)——避免逐元素 Python 循环，跑在 GPU 上快得多。另外还要注意：分母是 valid_mask.sum()（只对有效 token 求平均），padding 不参与归一化。

放大 10 倍后，模型「非常重视」学会停止。这是用加权解决「样本不均衡」的典型手法——稀有但重要的样本，给更高的权重。

Part 3：训练的工程技巧

三个让训练在单卡上跑得动的关键技巧。

混合精度：省一半显存

用一半显存，换几乎一样的效果

📌 对应源码：train_sft_omni.py 第 187 行（autocast 上下文）+ 第 232 行（GradScaler）+ train_epoch() 第 97-103 行（五步法）

默认参数用 32 位浮点（FP32）存。混合精度训练把计算和存储切成 16 位（BF16/FP16），显存直接减半，速度还更快。MiniMind-O 默认用 dtype=bfloat16。

# 一行代码开启混合精度上下文
with torch.cuda.amp.autocast(dtype=torch.bfloat16):
    output = model(input_ids)      # 用 BF16 算前向
    loss = criterion(output, labels)  # 损失保持 FP32 精度

为什么不全程 16 位？ 因为 16 位的精度有限，算梯度时太小的数会「下溢」变成 0。所以关键步骤（损失计算、参数更新）仍用 FP32，只有前向的大规模矩阵乘法用 BF16。这种「该精则精、该快则快」的混合，就是「混合精度」名字的由来。

GradScaler 五步法

FP16 防下溢流水线

📌 对应源码：train_sft_omni.py 的 train_epoch() 第 97-103 行

autocast 只管「前向用低精度」。一旦真正反传梯度，FP16 下小梯度可能下溢成 0。解决办法是用 GradScaler：先把 loss 放大（让小梯度浮起来），反传完再缩回去。整个流程是固定的五步。

教程简化版

loss.backward()
optimizer.step()
optimizer.zero_grad()

省略缩放，便于先理解「反传→更新→清零」的主干。

真实源码 train_sft_omni.py:97-103

scaler.scale(loss).backward()           # ① 放大 loss 后反传
if step % args.accumulation_steps == 0:
    scaler.unscale_(optimizer)           # ② 反缩放，还原真实梯度
    torch.nn.utils.clip_grad_norm_(
        model.parameters(), args.grad_clip)  # ③ 梯度裁剪
    scaler.step(optimizer)               # ④ 检查 inf/NaN 再 step
    scaler.update()                      # ⑤ 更新缩放因子
    optimizer.zero_grad(set_to_none=True)

裁剪必须放在 unscale_ 之后、step 之前——否则裁剪的是放大后的假梯度。

📜 关键一行：train_sft_omni.py 第 232 行

scaler = torch.cuda.amp.GradScaler(enabled=(args.dtype == 'float16'))

注意 bfloat16 默认不启用 scaler：BF16 的指数位和 FP32 一样宽，几乎不会下溢，所以 enabled=False 时上面五步会自动退化成「直接 .backward() + .step()」。只有切到 --dtype float16 时 scaler 才真正起作用。这就是 BF16「既省显存又稳定」的原因——你拿到的是混合精度的速度，却不用操心缩放。

梯度累积：显存不够，步数来凑

大 batch 训练效果更好，但显存放不下。梯度累积的思路：把一个大 batch 拆成几次小 batch，每次只算梯度不更新，攒够了再一起更新。

图：梯度累积——用 4 次小 batch 模拟 1 次大 batch

代价是：每更新一次参数要走 4 步前向反向，速度稍慢。但换来的是大 batch 的训练稳定性——在显存有限时非常划算。

余弦退火：学习率退潮

📌 对应源码：trainer_utils.py 的 get_lr() 第 25-27 行；调用点 train_sft_omni.py 第 68-70 行（每个 step 都重新算 lr 并写回 optimizer）

学习率不该一直不变。训练初期要大（大胆探索），后期要小（精细打磨）。MiniMind-O 用余弦退火：学习率从最大值，按余弦曲线平滑衰减到最大值的 10%。

# 余弦退火公式
lr = base_lr * (0.1 + 0.45 * (1 + cos(π * step / total_steps)))
# step=0 时 lr=base_lr×1.0（最大）
# step=total 时 lr=base_lr×0.1（最小）

Part 4：检查点与多卡

训练动辄几小时，中途断了怎么办？多张卡怎么协同？

原子化保存：防中断损坏

📌 对应源码：trainer_utils.py 的 omni_checkpoint() 第 120-122、150-152 行

保存检查点时，如果直接写文件，写到一半断电就废了。MiniMind-O 用原子保存：先写到临时文件，写完再重命名成正式文件——重命名是一瞬间的事，不会出现「半个文件」。

📜 真实源码：trainer_utils.py 第 120-122 行

ckp_tmp = ckp_path + '.tmp'
torch.save(state_dict, ckp_tmp)   # 先写临时文件（慢、可中断）
os.replace(ckp_tmp, ckp_path)     # 再原子替换（瞬间完成）

另外，保存时会排除冻结的外部编码器（SenseVoice/SigLIP2/Mimi）。它们不参与训练，没必要重复保存（每次存几百 MB 太浪费），加载时单独从原文件读。源码第 118 行：clean_state_dict = {k: v for k, v in ... if not k.startswith('audio_encoder.') and not k.startswith('vision_encoder.')}。

双检查点：一份推理、一份续训

📌 对应源码：train_sft_omni.py 第 117-127 行（存两份）+ trainer_utils.py 的 omni_checkpoint() 第 107-162 行

每个 save_interval，MiniMind-O 同时写两份文件，各司其职：

ckp（推理用）

{weight}_{hidden}.pth

  • 只存半精度权重（.half().cpu()），体积小
  • 排除 audio/vision encoder
  • 供下一阶段 from_weight 加载、或推理脚本直接用

  • 存完整恢复态：model + optimizer + scaler + epoch + step + world_size + wandb_id
  • 中断后从这里无缝续训
  • 体积大（含优化器动量等）

resume_data = {

续训的三道保险

world_size 换算 + SkipBatchSampler

📌 对应源码：trainer_utils.py 的 omni_checkpoint() 第 153-162 行 + SkipBatchSampler 第 176-199 行；调用点 train_sft_omni.py 第 237-259 行

断点续训不是「加载权重就完事」——它要保证从断点那一刻起，喂给模型的数据完全一致，否则优化器状态和当前数据对不上，训练会抖动。MiniMind-O 用三道保险：

📜 真实源码 1：trainer_utils.py 第 154-161 行（GPU 数量变化时换算 step）

if os.path.exists(resume_path):
    ckp_data = torch.load(resume_path, map_location='cpu')
    saved_ws = ckp_data.get('world_size', 1)        # 存档时的 GPU 数
    current_ws = dist.get_world_size() if dist.is_initialized() else 1
    if saved_ws != current_ws:
        # 比如从 4 卡续到 2 卡，每个 step 处理的数据减半，step 要翻倍
        ckp_data['step'] = ckp_data['step'] * saved_ws // current_ws

📜 真实源码 2：trainer_utils.py 第 176-199 行（数据层跳过已训 batch）

class SkipBatchSampler(Sampler):
    def __init__(self, sampler, batch_size, skip_batches=0):
        self.sampler = sampler
        self.batch_size = batch_size
        self.skip_batches = skip_batches   # 要跳过的 batch 数
    def __iter__(self):
        batch, skipped = [], 0
        for idx in self.sampler:
            batch.append(idx)
            if len(batch) == self.batch_size:
                if skipped < self.skip_batches:   # 前 N 个 batch 直接丢弃
                    skipped += 1; batch = []; continue
                yield batch; batch = []           # 之后的才真正产出

第三道保险在 train_sft_omni.py 第 237-242 行：model.load_state_dict(ckp_data['model']) + optimizer.load_state_dict(...) + scaler.load_state_dict(...)，把训练状态完整还原。三者合起来，断点前后「数据流」和「参数流」都对齐，才能做到真正的无缝续训。

DDP：多张卡怎么协同训练

单卡训练慢，多卡能加速。DDP（分布式数据并行）是最简单的多卡方案：每张卡放一份完整的模型副本，各自处理不同的数据，算完梯度后平均，再同步更新参数。

关键性质：4 张卡的模型副本始终参数一致（因为用同一份平均梯度更新）。所以 DDP 是「数据并行」——并行的是数据，不是模型。Full 版本就在 4 卡上训练。

练习：理解训练设计

回答三个「为什么」

  1. 为什么训练要分 T2A → A2A Proj → A2A Full 三个阶段，而不是一次性全量训练？
  2. 总损失 text_loss + audio_loss/8 + aux_loss 里，为什么 audio_loss 要除以 8？
  3. 显存只够 batch=16，但想要 batch=64 的效果，用什么技巧？

参考答案

1) 一次性全量训练，模型同时面对写字、说话、对齐编码器三重陌生信号，梯度方向打架无法收敛。分阶段让每步只解决一个子问题，像搭积木。2) audio_loss 是 8 层相加，不除以 8 会比 text_loss 大数倍，音频主导训练、压制文字。除以 8 取平均，两者量级平衡。3) 梯度累积。设 accumulation_steps=4，4 次 batch=16 的梯度累加后才更新一次，等效 batch=64。

训练常见坑

loss 一直是 NaN

原因：学习率太大、梯度爆炸，或混合精度下梯度下溢。

修复：调小学习率；确认用了 GradScaler；检查输入数据有没有异常值；确认梯度裁剪生效。

📌 对应源码：train_sft_omni.py 第 100、133 行 torch.nn.utils.clip_grad_norm_(model.parameters(), args.grad_clip)，--grad_clip 默认 1.0（见第 150 行）。它把所有参数梯度的范数整体缩放到不超过阈值，是防梯度爆炸的第一道闸——每次 optimizer.step() 前都会执行。如果还在爆 NaN，先把 grad_clip 调小（如 0.5）再排查。

音频生成停不下来

原因：stop token 没学好（权重不够）。

修复：确认 stop token 权重 ×10 生效；检查训练数据里 answer_audios 是否正确以 2050 结尾。

训练速度比预期慢很多

原因：数据加载成了瓶颈（GPU 等数据）。

修复：增加 DataLoader 的 num_workers；启用 pin_memory；检查音频增强是否在主进程做。

中断后无法恢复

原因：检查点没存 optimizer 状态，或文件损坏。

修复：确认 omni_checkpoint 存了完整状态；用原子保存防损坏；必要时从头训。

CUDA out of memory（显存不足）

症状：训练几步就报 CUDA out of memory。

原因：batch 太大、序列太长，或没开混合精度。

修复：按这个顺序逐个试——① 减小 --batch_size（如 16→8）；② 开梯度累积 --accumulation_steps 4 补回等效 batch；③ 减小 --max_seq_len（如 768→512）；④ 确认 --dtype bfloat16（默认）已生效，省一半显存；⑤ 关掉其他占显存的程序。CPU 上能跑但慢几十倍，只作兜底。

loss 居高不下 / 高位震荡

症状：loss 不变成 NaN，但一直在高位反复横跳，降不下来。

原因：学习率过大、label masking 反了、或冻结组合不对。

修复：① 学习率砍半试试（尤其阶段 3 应是 2e-5 量级）；② 检查 -100 是否标反——若误把要学的位置全 mask 成 -100，text_mask.sum() 趋零，模型根本没东西可学；③ 确认当前阶段该冻的冻了、该训的没被误冻（看日志 Trainable: XM 是否符合预期）。

torch.cuda.amp 相关报错或警告

症状：报 torch.cuda.amp 已弃用，或 UserWarning 满屏。

原因：PyTorch 2.x 起，旧的 torch.cuda.amp 命名空间建议迁到 torch.amp。

修复：不影响训练，可忽略警告；若硬报错，把 from torch.cuda.amp import autocast 换成 from torch.amp import autocast 并指定 autocast('cuda', ...)。同时确认显卡驱动和 CUDA 版本与 PyTorch 匹配（torch.version.cuda 与 nvidia-smi 对得上）。

关键要点回顾

三阶段流水线

T2A（学会出声）→ A2A Proj（耳朵对齐）→ A2A Full（端到端打通）。每步只解决一个子问题。

训练模式控制

mode=all/audio_proj/vision_proj 精确控制哪些参数可训练，是分阶段训练的基础。

损失平衡

audio_loss/8 防止音频压制文字；stop token ×10 解决样本不均衡。

混合精度

BF16 算前向省一半显存，关键步骤保 FP32 精度。

梯度累积

攒几次小 batch 的梯度再更新，用步数换 batch 大小。

余弦退火 + 原子保存

学习率先大后小；检查点原子保存防中断损坏，支持断点续训。
