阶段 7 · Web 演示——从命令行到实时语音通话

命令行好用，但不够「人话」

上一章你在命令行里让 MiniMind-O 干活。但要让普通人也能体验——发个消息、录段语音、甚至实时通话——就得给它套一层 Web 界面。

这听起来只是「加个前端」，但全模态的 Web 演示藏着两个硬骨头：怎么让文字一个字一个字地蹦出来（流式），怎么实现打断我说话、随时插话的实时通话。

本章不讲模型，专讲「模型外面这层壳」。你会看到两套方案：快速搭 demo 的 Gradio，和能撑住实时通话的 Flask+WebSocket。重点理解流式传输和实时交互的实现原理。

Part 1：两套方案

MiniMind-O 提供两个 Web 演示，复杂度差很多。

Gradio：十分钟搭个演示

Gradio 是专为 ML 模型演示设计的框架。你只需写一个 Python 函数处理输入输出，它自动生成一个网页。

import gradio as gr

Gradio 的优点

代码极少，自动处理前端、流式、音频播放。适合做 demo、给别人看效果。

Gradio 的局限

定制能力弱，做不了实时通话、打断这种复杂交互。界面风格也固定。

Flask 方案

WebSocket 撑住生产级交互

想要完整能力（实时通话、声音克隆、打断），就得自己写前后端：Flask 做后端服务，自己写 HTML/JS 前端，用 WebSocket 做实时双向通信。

Part 2：文字逐字蹦出

Chat 模式的核心：流式传输。

为什么要流式

如果等模型把整段话（文字+语音）全算完再返回，用户要干等好几秒——体验很差。流式的好处是算出一个字就显示一个字，用户立刻有反馈，感觉模型在「实时思考」。

回顾阶段 3：模型的 generate(stream=True) 本来就是逐字 yield 的。所以后端要做的，就是把每次 yield 的内容立刻推给浏览器，而不是攒着。

SSE：服务器主动推送

普通的 HTTP 请求是「一问一答」——浏览器发请求，服务器返一次响应就结束。这做不了流式。SSE（Server-Sent Events）是专门为流式设计的：服务器建立一个长连接，然后持续地、一条一条地往浏览器推数据。

图：SSE 流式传输——服务器逐条推送

每条消息带一个 type，浏览器据此决定怎么处理。重点：音频不是一条发完，而是切成多段 pcm 分片推送——c 是这一段的 base64 PCM 数据，d（done）标记这是不是最后一段。浏览器要边收边拼接播放，而不是等齐。这正是上一页说的「分块解码」在传输层的体现。完整的真实类型还有 user_prompt（回显用户输入）、ttft（首字/首音延迟统计）等。

音频分块解码

不是「攒齐再发」

前面简化说法是「每生成 ~80ms 直接发」。真实实现是按固定帧数分块解码：stream_pcm() 把累积的 Mimi audio frame 攒到 audio_chunk_frames（默认 4 帧 ≈ 320ms）的倍数，才解码一块 PCM 推出去，最后 flush=True 解掉尾巴余数。

为什么要攒块？因为 Mimi 解码是「帧→波形」的，块太短边界会断裂、出杂音。所以每块还带上 audio_overlap（默认 2 帧）的重叠帧，解码后用 pcm_bytes 里的 ov 参数把重叠部分切掉，拼起来才平滑。

📌 对应源码：webui/web_demo.py 的 stream_pcm()（85-98 行）与 pcm_bytes()（78-83 行）。Chat 模式（gen() 334/338 行）和 Call 模式（426/429 行）都调它。

教程简化版

                                      return_audio_codes=True):

真实源码 webui/web_demo.py:78-98

def pcm_bytes(frames, ov):      # ov: 要切掉的重叠帧数
    r = _mimi_decode(frames)
    if r is None: return None
    au, T = r
    if ov > 0: au = au[int(ov * len(au) / T):]  # 切掉开头重叠
    return (au * 32767).astype('int16').tobytes()

def stream_pcm(frames, flush=False):
    """yield (pcm_bytes,) on chunk boundaries or on final flush."""
    if not M['mimi']: return
    cf, ov_max, n = M['cfg'].audio_chunk_frames, M['cfg'].audio_overlap, len(frames)
    if not flush and n >= cf and n % cf == 0:   # 攒到 4 帧的倍数
        ov = min(ov_max, n - cf)
        p = pcm_bytes(frames[-(cf + ov):], ov)  # 多取 ov 帧重叠
        if p: yield p
    elif flush:                                 # 收尾：解余数
        rem = n % cf
        if rem:
            ov = min(ov_max, n - rem)
            p = pcm_bytes(frames[-(rem + ov):], ov)
            if p: yield p

所以真实延迟是「每凑够 4 帧（≈320ms）解一块、发一块」——块大小是延迟和边界质量的折中。--audio_chunk_frames 调大播放更卡、调小延迟更低但杂音更多。

推理与转写并行

prepare_turn 的 asr_thread

用户发来一段语音，后端要做两件事：① 把语音喂给模型的音频编码器开始推理；② 用 SenseVoice 把语音转成文字，给前端显示「你说了啥」。真实实现里这两件事是并行的——推理立刻开跑，转写在后台线程做，文字算好了再 yield 给前端。

📌 对应源码：webui/web_demo.py 的 prepare_turn()（220-240 行）。Chat 模式 gen()（307 行）和 Call 模式（410 行）都用它。

📜 真实源码：webui/web_demo.py 第 220-240 行

def prepare_turn(text, samples, image_b64, do_asr_for_image):
    """返回 (audio_inputs, audio_lens, pixel_values, prompt, user_text, asr_thread, asr_result)"""
    audio_inputs = audio_lens = pixel_values = None
    prompt = text or ''
    user_text = text or ''
    asr_thread, asr_result = None, [None]
    if samples is not None:
        if image_b64 and do_asr_for_image:          # 图片+语音：同步转写当 prompt
            user_text = asr_run(samples)
            prompt = user_text
        else:                                       # 纯语音：立刻 prep_audio 开始推理
            audio_inputs, audio_lens, prompt = prep_audio(samples)
            if M['cfg'].max_history_turns > 0:
                sa = samples.copy()
                def _a(): asr_result[0] = asr_run(sa)   # 后台线程跑 SenseVoice 转写
                asr_thread = threading.Thread(target=_a); asr_thread.start()
    if image_b64:                                   # 图片走视觉编码，拼特殊 token
        pixel_values = prep_image(image_b64)
        # ... 拼接 image_special_token ...
    return audio_inputs, audio_lens, pixel_values, prompt, user_text, asr_thread, asr_result

生成循环里每生成一个 token 都瞄一眼 asr_thread：一旦转写线程结束（not asr_th.is_alive()）就把文字 yield 给前端（见 gen() 318-321 行）。这样首字延迟不被转写拖累——文字稍晚到没关系，语音回复尽快开始。

Part 3：实时语音通话

Call 模式要做的事，远比 Chat 复杂。

实时通话的三道难关

  • 怎么知道用户说完了——总不能让用户每次按按钮。得自动检测「说话结束」
  • 低延迟传输音频——SSE+base64 太慢，实时通话要毫秒级
  • 怎么支持打断——用户说到一半想插话，得能立刻中止 AI 的输出

MiniMind-O 用三个技术分别解决：VAD 检测、WebSocket 二进制流、状态机管理打断。

VAD：自动检测「说完了」

VAD（语音活动检测）是个小模型，输入一小段音频，输出「这段里有没有人在说话」的概率。MiniMind-O 用 Silero VAD。

逻辑很简单：持续检测，如果检测到语音的概率从高变低并维持一段时间，就判定「用户说完了」，触发模型开始回复。

📌 对应源码：整个实时通话由 webui/web_demo.py 的 realtime() 路由（@sock.route('/ws/realtime')，353-440 行）编排；VAD 概率由 model/model_omni.py 的 SileroVAD 算出，端点判定由 RealtimeSession.push_chunk() 完成（下一页详讲）。

图：VAD 如何判断说话结束

两个阈值很关键：min_speech（最短算一句话的时长，防噼啪声误触发）、min_silence（静多久才算说完，防正常停顿被误判成结束）。

WebSocket：双向音频

毫秒级低延迟

SSE 是单向的（服务器→浏览器）且只能传文本，做不了实时通话。WebSocket 是全双工的——浏览器和服务器可以随时互发消息，且支持二进制（直接传音频字节，不用 base64 编码，省时间）。

Chat 模式（SSE）

单向，文本（音频要 base64）。

延迟较高，适合「发消息等回复」。

Call 模式（WebSocket）

双向，二进制（音频直传）。

延迟极低，适合实时通话。

# Call 模式的音频流
服务端: 每生成一块 PCM 音频片段（默认 4 帧 ≈ 320ms）
  → WebSocket 二进制帧直接发给浏览器
浏览器: 写入 AudioBuffer 播放队列
  → 连续播放，实现无缝语音

状态机藏在哪

RealtimeSession 与 SileroVAD

前面说「VAD 不在模型内部」——更准确的说法是：VAD 与模型推理零耦合（它只看音频概率，不参与 Transformer 计算），但这两个类物理上就在 model/model_omni.py 的末尾，是纯工程层的封装。之前为便于理解讲成「VAD 不在模型内部」，真实实现是「VAD 类 SileroVAD + 状态机类 RealtimeSession 都写在 model_omni.py 里，但逻辑上和模型本体解耦」。

📌 对应源码：model/model_omni.py 的 SileroVAD（399-412 行）与 RealtimeSession（415-462 行），webui 通过 from model.model_omni import RealtimeSession 导入。

SileroVAD 本身很薄：把 1024 采样喂进 ONNX，维护一个隐状态 h,c，返回「这段音频有人说话的概率」。

📜 真实源码：model/model_omni.py 第 399-412 行

class SileroVAD:
    def __init__(self, path):
        opts = ort.SessionOptions()
        opts.inter_op_num_threads = opts.intra_op_num_threads = 1
        self.session = ort.InferenceSession(path, providers=["CPUExecutionProvider"], sess_options=opts)
        self.h, self.c = np.zeros((2, 1, 64), dtype=np.float32), np.zeros((2, 1, 64), dtype=np.float32)

    def reset(self):
        self.h[:], self.c[:] = 0, 0

    def __call__(self, chunk, sr=16000):
        out, self.h, self.c = self.session.run(None, {"input": chunk.reshape(1, -1).astype(np.float32), "h": self.h, "c": self.c, "sr": np.array(sr, dtype="int64")})
        return float(out[0][0])   # 返回这段音频是语音的概率（0~1）

真正复杂的是 RealtimeSession.push_chunk()——它把 Silero VAD 的概率包成了一个状态机，维护五个状态：buffer（攒下来的音频）、ring（说话前的前置缓冲，防截断）、speaking（正在说话）、generating（AI 正在生成）、interrupt（被用户打断）。

push_chunk 状态机

真实逻辑

📌 对应源码：model/model_omni.py 的 RealtimeSession.push_chunk()（426-457 行）。webui 的 realtime() 路由每收到一块音频就调它一次。

核心参数（构造时设定，见 416 行）：threshold=0.8（概率高于此算语音）、min_speech_ms=128（要凑够这么长才算「真的在说话」，防噼啪声）、min_silence_ms=800（静音超过这么久才算「说完了」）。它们会按采样率换算成采样数 min_speech / min_silence。

📜 真实源码：model/model_omni.py 第 426-457 行

def push_chunk(self, chunk, W=1024):           # W=1024：每次喂 1024 采样给 VAD
    for i in range(0, max(len(chunk), 1), W):
        w = chunk[i:i + W]
        if len(w) < W:
            w = np.pad(w, (0, W - len(w)))      # 末尾不足 1024 的补零
        prob = self.vad(w, self.sr)             # 拿到这段是语音的概率
        if prob > self.threshold:               # --- 认为是语音 ---
            self.silence_samples = self.tail_silence = 0
            self.speech_samples += len(w)
            self.buffer.append(w)
            if self.speech_samples >= self.min_speech and not self.speaking:
                self.speaking = True            # 攒够了 min_speech，正式进入「说话中」
                self.buffer = self.ring + self.buffer  # 把 ring 缓存拼到前面（防开头被截断）
                self.ring = []
            if self.generating and self.speaking:      # AI 正在生成，用户又开口了 → 打断！
                self.interrupt = True
                return 'interrupt'
        elif self.speaking:                     # --- 说话中遇到静音段 ---
            self.silence_samples += len(w)
            self.tail_silence += 1
            self.buffer.append(w)
            if self.silence_samples >= self.min_silence:  # 静够了 min_silence
                if self.tail_silence > 1:
                    del self.buffer[-(self.tail_silence - 1):]  # 删掉尾巴上多余静音
                self.speaking, self.speech_samples, self.silence_samples, self.tail_silence = False, 0, 0, 0
                return 'speech_end'             # 判定说完，触发模型回复
        else:                                   # --- 还没开始说话 ---
            if self.speech_samples > 0:
                self.buffer.clear()
            self.speech_samples = 0
            self.ring = [w]                     # 留一段 ring，等会儿判定说话时拼到前面
    return 'listening'

五个状态怎么协作

  • buffer：攒实际语音，speech_end 后交给 get_audio() 取走
  • ring：说话前的预备缓冲，避免「第一个字开头被切掉」
  • speaking：凑够 min_speech 才置真，过滤短噪声
  • generating：由 webui 路由在开始生成时置真，决定是否触发打断
  • interrupt：生成中又检测到说话时拉起，路由据此中止输出

两个关键返回值

  • 'speech_end'：静音超 min_silence(800ms) 且 tail_silence>1，删掉尾巴静音，把攒的音频交给推理
  • 'interrupt'：generating 且 speaking 时又听到人声 → barge-in
  • 'listening'：默认值，表示这一轮还没有结论，继续等数据

打断（barge-in）

随时插话

这是实时通话最人性化的能力。AI 正在说话时，用户开口了，AI 应该立刻闭嘴听用户说。实现靠一个状态机：

关键在「AI 说话」状态下，VAD 仍然在工作。一旦检测到用户开口（概率升高），立刻中断正在生成的回复，转入处理新输入。这就是为什么打电话时能自然地打断对方——AI 也学会了。

为什么要两条线程

recv_loop + queue

📌 对应源码：webui/web_demo.py 的 realtime() 路由（353-440 行）及其内部的 recv_loop()（382-388 行）。

问题在于：模型生成一回合要花好几秒，这段时间里用户的音频还在源源不断地从 WebSocket 进来。如果主线程边生成边收音频，ws.receive() 会阻塞生成；如果不收，浏览器发的音频堆在网络缓冲里、甚至被丢弃——用户想打断时，VAD 根本看不到新音频。

解法是经典的「生产者-消费者」：开一条 daemon 线程 recv_loop 专门收数据塞进 queue.Queue，主线程专心推理、需要时再从队列里偷瞄一眼。

📜 真实源码：webui/web_demo.py 第 382-393 行（接收线程 + 主循环分发）

def recv_loop():                       # 子线程：只管把数据塞进队列
    while alive[0]:
        try:
            data = ws.receive(timeout=1)   # 每次最多阻塞 1 秒
            if data is None: alive[0] = False; break
            q.put(data)                    # str（控制消息）或 bytes（音频）都往里塞
        except: alive[0] = False; break

threading.Thread(target=recv_loop, daemon=True).start()   # daemon：主线程退出时自动结束
# --- 下面是主线程（在同一 realtime() 函数里）---
while alive[0]:
    try: data = q.get(timeout=0.05)        # 从队列取，等不到 50ms 就跳过
    except queue.Empty: continue
    if isinstance(data, str):              # 控制消息：context/stop/end
        m = json.loads(data)
        if m.get('type') == 'context': set_ctx(m)
        elif m.get('type') == 'stop': session.interrupt = True
        elif m.get('type') == 'end': break
        continue
    if session.generating:                 # AI 正在说话：音频只喂 VAD 看是否打断
        push_audio(data); ws.send(json.dumps({'type': 'vad', 'speaking': session.speaking})); continue
    status = push_audio(data)              # 没在生成：正常做端点检测
    ws.send(json.dumps({'type': 'vad', 'speaking': session.speaking}))
    if status != 'speech_end': continue    # 还没说完，继续等
    session.generating = True              # 说完了，进入生成
    audio = session.get_audio()            # 取走 buffer 里攒的语音
    # ... 开始 run_generate ...

为什么是两条线程

生成耗时期间，recv_loop 持续 ws.receive 把音频搬进队列，保证用户开口的瞬间音频不丢。生成循环再用 poll_interrupt() 去队列里捞——这就实现了「边说边听」。

生成中的音频怎么处理

当 session.generating 为真，新来的音频不再做端点检测的「攒语音」，而是直接 push_audio 喂给 VAD——此时 push_chunk 命中 generating and speaking 分支，返回 'interrupt' 触发 barge-in。

生成中如何知被打断

poll_interrupt

📌 对应源码：webui/web_demo.py 的 poll_interrupt()（368-380 行），在生成循环里（417-419 行）每次迭代调用。

recv_loop 保证音频进了队列，但生成循环还得主动去捞。每生成一个 token，poll_interrupt() 就把队列里所有新消息排空：新音频就 push 进 VAD 看有没有 'interrupt'；遇到 stop/end 就直接置 session.interrupt。这就是 barge-in 的真实实现——「生成中不断偷瞄队列」。

📜 真实源码：webui/web_demo.py 第 368-380 行 + 生成循环 417-419 行

def poll_interrupt():
    while True:
        try: data = q.get_nowait()              # 非阻塞地拿一条
        except queue.Empty: return False
        if isinstance(data, bytes):             # 新音频：喂 VAD 看是否触发打断
            if push_audio(data) == 'interrupt': return True
            ws.send(json.dumps({'type': 'vad', 'speaking': session.speaking}))
        else:                                   # 控制消息
            m = json.loads(data)
            if m.get('type') == 'context': set_ctx(m)
            elif m.get('type') in ('stop', 'end'):
                if m['type'] == 'end': alive[0] = False
                session.interrupt = True; return True

# 生成循环里每次迭代都偷瞄一眼：
for y, af in run_generate(x, audio_inputs, audio_lens, pixel_values,
                           max_new_tokens=512, temperature=0.7, **va_rt):
    if poll_interrupt() or session.interrupt:   # 一旦被打断
        interrupted = True; break               # 立刻跳出，停止生成
    # ... 正常处理 text / audio frame ...

注意 poll_interrupt 用的是 q.get_nowait()（非阻塞），所以「没消息」时立刻返回 False，几乎不浪费推理时间——这正是打断延迟能做到「几百毫秒」的原因。

Part 4：克隆界面流程

把阶段 6 的声音克隆能力，包装成「录一段、存音色」的交互。

录、验、存、用

声音克隆界面的四步流程：

  1. 录：用户录 3-6 秒自己的声音
  2. 验：检查时长、音量、噪声是否合格（不合格要求重录）
  3. 存：Mimi 编码成 ref_codes + CAM++ 提取 spk_emb，保存成音色文件
  4. 用：之后对话时，选这个音色，AI 就用你的声音回复

为什么要质量验证？ 声音克隆的效果高度依赖参考音频质量。太短（信息不够）、太安静（提取不出特征）、噪声大（特征被污染）都会导致克隆失败或很难听。前端先卡一道质量关，能避免用户录完不能用。

克隆录音处理

先加速 1.5 倍

「存」这一步藏着一个反直觉的技巧：把用户的录音先 speedup(playback_speed=1.5) 加速 1.5 倍再编码。听上去像是要把声音变快，其实是为了缩短参考音频长度，让它更贴近训练时 ref_codes 的长度分布，克隆更稳。

加速后分两路：一路转 24kHz 喂 Mimi 编码成离散 codes（取前 8 层 × 前 300 帧作为 ref_codes）；另一路转 16kHz 喂 CAM++ 提取说话人向量 spk_emb。

📌 对应源码：webui/web_demo.py 的 build_clone_voice()（164-191 行）。由 /clone_voice 路由调用。

📜 真实源码：webui/web_demo.py 第 164-191 行

def build_clone_voice(audio_b64):
    if M.get('mimi') is None or M.get('campplus') is None or M.get('mel_fn') is None:
        raise RuntimeError('Mimi 或 CAM++ 未加载')
    seg = AudioSegment.from_file(io.BytesIO(base64.b64decode(audio_b64))).set_channels(1).set_sample_width(2)
    if len(seg) < 1000:
        raise RuntimeError('录音太短，至少读 1 秒')
    try:
        seg = seg.speedup(playback_speed=1.5, chunk_size=150, crossfade=25)  # 反直觉：先加速 1.5 倍
    except Exception:
        seg = seg.speedup(playback_speed=1.5)
    seg24 = seg.set_frame_rate(24000)   # 给 Mimi（24kHz）
    seg16 = seg.set_frame_rate(16000)   # 给 CAM++（16kHz）
    w24 = torch.tensor(np.frombuffer(seg24.raw_data, dtype=np.int16).astype(np.float32) / 32768.0)
    w16 = torch.tensor(np.frombuffer(seg16.raw_data, dtype=np.int16).astype(np.float32) / 32768.0)
    validate_clone_audio(w16)           # 质量校验：时长/音量/噪声/爆音
    mimi_dev = next(M['mimi'].parameters()).device
    mimi_dtype = torch.float16 if mimi_dev.type != 'cpu' else torch.float32
    with torch.inference_mode():
        t = w24.unsqueeze(0).unsqueeze(0).to(device=mimi_dev, dtype=mimi_dtype)
        codes = M['mimi'].encode(t).audio_codes
        nf = math.ceil(w24.shape[-1] / SAMPLES_PER_FRAME)
        ref_codes = codes[0, :8, :nf].cpu()[:, :min(nf, REF_FRAMES)]  # 前8层 × 前300帧
    with torch.no_grad():
        mel = M['mel_fn'](w16.unsqueeze(0).to(M['device']))
        feat = mel.clamp(min=1e-10).log().transpose(1, 2)
        feat = feat - feat.mean(dim=1, keepdim=True)   # CMVN 归一化
        spk_emb = M['campplus'](feat).squeeze(0).cpu()
    return {'ref_codes': ref_codes, 'spk_emb': spk_emb}

两条采样率各司其职

  • Mimi @ 24kHz：编解码器原生采样率，encode 出 8 层量化码本，截前 300 帧作 ref
  • CAM++ @ 16kHz：说话人模型训练采样率，先过 MelSpectrogram 再提 192 维 spk_emb

几个常量

  • SAMPLES_PER_FRAME=1920（24kHz ÷ 12.5fps）
  • REF_FRAMES=300（≈最长参考 24 秒，但加速后通常更短）
  • codes 里 ≥2049 的会被当 padding 清零（见 _mimi_decode）

被忽略的问题：并发

Web 服务可能同时来多个请求，但一张 GPU 同时只能跑一次模型推理。怎么办？用互斥锁（Lock）——同一时间只允许一个请求进入推理，其他排队等。

from threading import Lock
infer_lock = Lock()

def handle_request(prompt):
    with infer_lock:              # 获取锁，同一时刻只有一个请求能进
        result = model.generate(prompt)
    return result                 # 离开 with 块自动释放锁，下一个请求进入

这是单卡部署 Web 服务的常见妥协。要支持真并发，得多卡部署或上推理框架（如 vLLM）。

📌 对应源码：webui/web_demo.py 的 run_generate()（193-197 行）——MODEL_LOCK（24 行）就套在这里。所有推理路径（Chat 的 gen()、Call 的 realtime()）都通过 yield from M['model'].generate(stream=True) 走它：

MODEL_LOCK = threading.Lock()        # 模块级全局锁

def run_generate(x, audio_inputs, audio_lens, pixel_values, **kw):
    with MODEL_LOCK, torch.no_grad():  # 拿到锁才开始推理
        yield from M['model'].generate(
            x, M['tokenizer'].eos_token_id, stream=True, return_audio_codes=True,
            audio_inputs=audio_inputs, audio_lens=audio_lens, pixel_values=pixel_values, **kw)

注意 yield from + with MODEL_LOCK 的组合：整个流式生成期间锁都不释放，所以单卡下两个请求的推理严格串行——这也是并发模式下排队卡顿的直接来源。

观察思考：Call 模式里，你在 AI 说话时立刻开口，AI 会停下来吗？这个「打断」的延迟大概是多少？文本是逐字出现的还是整段出现的？

预期现象

Call 模式支持打断——你开口后，VAD 会很快（几百毫秒内）检测到，AI 输出中断，转入处理你的新输入。文本是逐字流式出现的（SSE/WebSocket 持续推送的效果）。这两个现象正是本章讲的流式传输和状态机打断的体现。

Web 演示常见坑

音频在浏览器放不出来

原因：采样率不匹配，或 base64 编码有误。

修复：确认 PCM 是 24kHz；检查 base64 编解码对称；浏览器控制台看报错。

Call 模式总是误触发/不触发

原因：VAD 的 min_silence/min_speech 阈值不合适。

修复：环境嘈杂就调高阈值；说话慢就调大 min_silence。

多人访问时响应卡顿

原因：互斥锁导致请求排队。

修复：单卡只能串行，接受排队；或部署多实例 + 负载均衡。

麦克风权限被拒

原因：浏览器安全策略，非 HTTPS 不给麦克风权限。

修复：用 localhost 访问（被视为安全源）；或配置 HTTPS。

关键要点回顾

两套方案

Gradio 快速演示（代码少），Flask+WebSocket 完整功能（实时通话、打断）。

SSE 流式

服务器长连接持续推送，让文字逐字出现。文本消息+base64 音频混合传输。

VAD 检测说话结束

语音概率从高变低并持续超过阈值，判定用户说完，触发回复。

WebSocket 实时通话

双向二进制流，毫秒级延迟，PCM 直传无需 base64。

打断靠状态机

AI 说话时 VAD 仍在工作，检测到新语音就中断输出，转处理新输入。

互斥锁保并发安全

单卡只能串行推理，用 Lock 让请求排队，避免显存冲突。
