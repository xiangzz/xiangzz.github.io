喂给模型的那一口

阶段 4 · 全模态训练里最棘手的一环——把三种模态对齐

训练数据从哪来

上一章我们拆解了 Thinker-Talker 架构。但模型不会自己学会说话——它得靠数据喂出来。

纯文本 LLM 的数据处理简单：一段话切成 token 就完事。但 MiniMind-O 是全模态：一条训练样本里同时有文字、语音、可能还有图片，它们长度不同、维度不同、含义不同。怎么把它们塞进同一次训练？

这是全模态训练里最容易被忽视、却最决定成败的一环。本章不讲模型，专讲「数据怎么准备」——你会看到一条样本如何被一步步加工成模型能消化的 9 通道张量。

一条样本装了什么

训练数据存在 Parquet 文件里，每条样本是一段「对话 + 配套的多模态素材」。一个典型样本：

{
  "conversations": [
    {"role": "user", "content": "你好"},
    {"role": "assistant", "content": "你好！有什么可以帮你的吗？"}
  ],
  "question_audios": ["用户说话的语音字节"],
  "answer_audios": [120, 450, 890, 23, ...],   // 助手回复的 Mimi 码
  "image_bytes": null,                          // 这条没图片
  "ref_audios": [...],                          // 参考音频码（声音克隆用）
  "spk_emb": [0.12, -0.34, ...]                 // 192 维说话人嵌入
}

六个字段，涵盖了对话内容、用户语音、助手回复的声音、可选的图片、克隆用的音色参考。模型要学的，就是「看到/听到这些输入后，该怎么回复（文字+声音）」。

Part 1：三种模态对齐

这是全章的核心难题。

回想阶段 3：模型的输入是 (9, T) 的 9 通道张量——8 个音频通道 + 1 个文本通道，共享长度 T。但原始数据里，文本有几个 token、音频有几帧，是完全独立的两串数。怎么让它们「对齐」到同一长度 T？这是数据处理的头号任务。

关键洞察：共享时间步

解决方案很巧妙：让文本 token 和音频码本共享同一根时间轴。在每个时间步上，既有这个位置的文本 token（通道 8），也有这个位置的 8 层音频码（通道 0-7）。

这样做的好处：模型在每个时间步都同时看到文字和它的声音，能从数据中学到「这个词对应什么样的声音」。这正是全模态对齐的根基。

输入目标错位：左移一位

语言模型的训练目标是「根据前文预测下一个词」。所以输入和目标要错开一位：输入是第 0~T-2 步，目标是第 1~T-1 步。

位置:    0      1      2      3
输入:  [你好]  [有什么][能帮的] [...]     ← 左移，预测用
目标:  [有什么][能帮的][的吗?]  [<end>]  ← 右移，监督用

9 个通道都做同样的错位。这样一次前向，每个位置都在「预测下一个 token 和下一个音频码」。

📜 真实源码：错位怎么切

教程里画的「左移/右移」很直观，但真实代码没有两个独立数组——它是从已经构造好的目标数组里切前缀当输入。这是最反直觉的一步，看懂它就看懂了 9 通道对齐。

# 构造9路输入：input_ids = (9, T) = 8路audio + 1路text
# 关键反直觉点：音频输入 X_audio 取自
#   音频目标数组 Y_audio_layers 的 [:-1]
X_audio = torch.tensor(
    [layer[:-1] for layer in Y_audio_layers],
    dtype=torch.long)                       # (8, T-1)
X_text  = torch.tensor(input_ids[:-1],
    dtype=torch.long)                       # (T-1,)
input_ids = torch.cat(
    (X_audio, X_text.unsqueeze(0)), dim=0)  # (9, T-1)

text_labels = torch.tensor(text_labels[1:],
    dtype=torch.long)                       # (T-1,)
audio_labels = torch.tensor(
    [layer[1:] for layer in audio_labels],
    dtype=torch.long)                       # (8, T-1)

反直觉关键点：音频输入侧 X_audio 塞的不是「干净的输入码」，而是音频目标数组 Y_audio_layers 切掉最后一位的前缀（[:-1]）。换句话说，输入侧塞的是「真实音频目标码」往前挪一格，再叠上一份 [1:] 的目标。这就是「预测下一个音频码」的本质实现——不需要再单独构造一份输入，目标的「错位副本」就是输入。

📜 真实源码：omni_dataset.py 第 220-229 行

# 随机截断到某一轮（每轮=user+assistant）
asst_indices = [i for i, t in enumerate(conversations) if t['role'] == 'assistant']
if len(asst_indices) > 1:
    rand_idx = random.randint(0, len(asst_indices) - 1)
    # 从随机轮次开始，向前回退直到长度安全
    for i in range(rand_idx, -1, -1):
        conversations = conversations[:asst_indices[i] + 1]

        if len(self.tokenizer(test_prompt).input_ids) + 100 < self.max_length:
            break

这些随机性为什么重要：同一条样本，每次被采样时占位符位置、保留几轮对话都可能不同。模型必须学到「不管 audio 放前面还是后面、不管截到第几轮，都能理解语义」——这种位置鲁棒性是全模态模型在真实推理时面对任意输入的前提。配合 pre_processing_chat（20% 加 system prompt）和 post_processing_chat（20% 保留空 think），整条样本的呈现形式高度随机化。

Part 2：屏蔽与损失

不是序列里每个位置都该参与训练。

用 -100 屏蔽无关位置

一段对话里有 system 提示、有用户的话、有助手的历史回复、还有助手这次的回复。模型只该学「这次怎么回复」——前面的都是上下文，不是要学的内容。

做法：把不该计算损失的位置，标签设成 -100。PyTorch 的 CrossEntropyLoss 见到 -100 就自动跳过，不算这些位置的损失。

图：标签 mask——只在最后回复处计算损失

【AI 生图提示词】请生成一张中文技术示意图，风格简洁、配色柔和、适合教学： - 画面主体：上下两行对照，上行是输入序列的每个 token，下行是对应的标签 - 上行（输入）：[<im_start>, system, 你是助手, <im_end>, <im_start>, user, 你好, <im_end>, <im_start>, assistant, 你好！, <im_end>] - 下行（标签）：system 和 user 部分（前 9 个位置）全部标注 -100 且用浅红色「不计算损失」；assistant 的回复部分（最后 3 个位置：你好！、<im_end>）标注真实标签且用浅绿色「计算损失」 - 上下用竖线对齐每个位置 - 关键标注：在浅红色区域标注「上下文，不是要学的内容」；在浅绿色区域标注「只在这里算损失，教模型『根据历史生成这次回复』」；右侧标注「-100 是 PyTorch CrossEntropyLoss 的默认忽略值」 - 配色建议：浅灰背景，输入行浅蓝色，-100 标签浅红色，真实标签浅绿色 - 画面比例：16:9

音频侧也类似：在 assistant 开始说话（\n\n 标记，叫 think_end）之前，音频标签全是 -100；之后才是真正要学的音频码。这保证了模型只在「该回复的时间段」学发声。

「只训最后一个 assistant」不是一步到位的——它分两步完成，第二步藏在 __getitem__ 里。这是源码里最容易看漏的细节。

📜 真实源码：omni_dataset.py 第 179-197 行

def generate_text_labels(self, input_ids):
    labels = [-100] * len(input_ids)
    ranges = []
    i = 0
    while i < len(input_ids):
        # 第一步：用 bos_id（'{bos}assistant\n' 的编码）
        #         子串扫描，定位每个 assistant 区间的起点
        if input_ids[i:i + len(self.bos_id)] == self.bos_id:
            start = i + len(self.bos_id)
            end = start
            #         再用 eos_id 子串扫描，找到区间终点
            while end < len(input_ids):
                if input_ids[end:end + len(self.eos_id)] == self.eos_id:
                    break
                end += 1
            ranges.append((start, end))
            # 把 [start, end+eos] 设为真实 label（先全部保留）
            for j in range(start, min(end + len(self.eos_id), self.max_length)):
                labels[j] = input_ids[j]
            i = end + len(self.eos_id) if end < len(input_ids) else len(input_ids)
        else:
            i += 1
    return labels, ranges   # ranges = [(s0,e0),(s1,e1),...] 每个assistant一段

注意：到这里 labels 把所有 assistant 区间都设成了真实 label。真正的「只留最后一个」发生在 __getitem__ 里——把 ranges[:-1]（除最后一轮以外的所有 assistant）重新 mask 回 -100：

📜 真实源码：omni_dataset.py 第 277-280 行

# 生成labels（只训练最后一个assistant）
text_labels, assistant_ranges = self.generate_text_labels(input_ids)
for start, end in assistant_ranges[:-1]:          # ← 关键：[:-1] 排除最后一轮
    mask_end = min(end + len(self.eos_id), self.max_length)
    text_labels[start:mask_end] = [-100] * (mask_end - start)   # 重新 mask 回 -100

为什么要分两步？第一步必须先标出所有 assistant 区间，因为音频目标的精密构造（下一页）需要用到「最后一个 assistant 的起始位置 assistant_start」来定位。但文本 loss 只想要最后一个，所以第二步再把非最后一轮的 label 重新打回 -100。两步法同时满足了「音频要精确对位」和「文本只训最后一段」两个需求。

📜 真实源码：8 层目标

音频目标不是简单填进去的——它要处理 8 层拆解、think_end 搜索、spk 占位、ref 右对齐、按层偏移 5 件事。这是 __getitem__ 里最复杂的一段。

📌 对应源码：omni_dataset.py 的 OmniDataset.__getitem__（第 282-318 行）

📜 真实源码：omni_dataset.py 第 282-318 行

# 生成8层audio targets（只填充最后一个assistant）
Y_audio_layers = [[self.audio_pad_token] * self.max_length for _ in range(8)]
audio_labels   = [[-100] * self.max_length for _ in range(8)]
if assistant_ranges and last_audio_codes:
    assistant_start, assistant_end = assistant_ranges[-1]
    # 1) 在 assistant_start 起 50 token 窗口内搜 think_end_ids
    #    （跳过空 <think></think> 后的真实回复起点）
    for pos in range(assistant_start, min(assistant_end, assistant_start + 50)):
        if input_ids[pos:pos + len(self.think_end_ids)] == self.think_end_ids:
            assistant_start = pos + len(self.think_end_ids)
            break
    # 2) spk_emb 占位 + ref_codes 右对齐（50% 概率 drop ref）
    has_spk = bool(spk_emb_raw)
    has_ref = bool(ref_audios) and random.random() > 0.5
    spk_reserve = 1 if has_spk else 0
    if has_ref:
        ref_codes = [[] for _ in range(8)]
        for i in range(0, len(ref_audios) - 7, 8):
            for j in range(8): ref_codes[j].append(ref_audios[i + j])
        ref_len = len(ref_codes[0])
        ref_start = max(spk_reserve, assistant_start - ref_len)
        for layer_idx in range(8):
            codes = ref_codes[layer_idx][-(assistant_start - ref_start):] if ref_len > (assistant_start - ref_start) else ref_codes[layer_idx]
            for i, code in enumerate(codes):
                Y_audio_layers[layer_idx][ref_start + i] = code   # ref 只进 Y，不进 label
    else:
        ref_start = assistant_start
    if has_spk and ref_start > 0:
        spk_pos = ref_start - 1
        for layer_idx in range(8):
            Y_audio_layers[layer_idx][spk_pos] = self.audio_spk_token   # 2051
    # 3) target codes 填到 assistant_start 之后（真正参与 loss 的部分）
    for layer_idx in range(8):
        codes = last_audio_codes[layer_idx]
        start_pos = assistant_start + layer_idx + 1              # ← 按层偏移！
        for i, code in enumerate(codes):
            if start_pos + i < self.max_length:
                Y_audio_layers[layer_idx][start_pos + i] = code  # 进输入侧
                audio_labels[layer_idx][start_pos + i] = code    # 同时进目标侧

5 个关键细节逐条对照：

  • ① 8 层拆解：answer_audios 是一维数组，每 8 个连续整数是一帧的 8 个码本层，按 for j in range(8) 拆成 8 路。
  • ② 50 token 窗口搜 think_end：assistant 开头可能有空 <think></think>，要在前 50 token 内找到 </think>\n\n，把 assistant_start 推到真实回复起点。
  • ③ spk_emb 占位：说话人嵌入占 audio_spk_token(2051) 一个位置，放在 ref 之前。
  • ④ ref_audios 50% drop + 右对齐：克隆参考音以 50% 概率丢弃，保留时右对齐塞进 assistant_start 之前；ref 只写进 Y_audio_layers（输入侧），不写进 audio_labels（不算损失）。
  • ⑤ 按层偏移：真正 target codes 按 start_pos = assistant_start + layer_idx + 1 填充，第 0 层比第 7 层早开始 7 个位置——这是「错位」在 8 层上的体现。

Part 3：为何搞坏数据

数据增强听起来反直觉，却是防止模型变傻的关键。

如果训练数据全是干净清晰的录音，模型会「死记」这些干净样本，一到真实环境（有噪声、有口音、语速不同）就抓瞎。数据增强就是主动给训练数据加各种「脏」，逼模型学会在乱七八糟的输入下也能工作。

波形增强：模拟真实声音

原始音频波形会被随机施加这些变换，每一种都模拟一种真实场景：

📌 对应源码：omni_dataset.py 的 OmniDataset.augment_wav()（第 89-121 行）

增强模拟的场景
随机变速（0.7~1.6 倍）说话快慢不同的人
高斯噪声录音环境的底噪
音量缩放话筒远近、说话大小声
时间掩蔽（置零一小段）信号丢包、短暂中断
低通滤波电话音质（高频丢失）
混响（指数衰减）空旷房间的回声

这些变换按概率随机施加，所以同一段语音每次喂给模型都不太一样——模型见过的「变体」越多，泛化能力越强。

随机遮蔽几帧。

提升对不完整输入的容错。

一句话理解数据增强：它制造了「同一个意思、不同表现」的大量样本，让模型学到的是「本质」而非「表面」。这是小数据集训练出能用模型的核心技巧。

计划采样

Scheduled Sampling：偶尔喂「错答案」

还有一个更反直觉的增强：以 5% 的概率，把输入序列里的某些 token 随机替换成别的 token。

推理时模型是自回归的——每一步的输出会喂回下一步当输入。如果训练时它只见过的「完美历史」，一旦自己生成时出点小错，错误就会滚雪球。Scheduled Sampling 提前让模型练过「从错误中恢复」，推理时就更稳。

📜 真实源码：非无脑替换

教程里说「5% 概率随机替换」是简化。真实代码有三个保护性条件，避免破坏关键结构。

📌 对应源码：omni_dataset.py 的 OmniDataset.apply_scheduled_sampling()（第 199-209 行）

📜 真实源码：omni_dataset.py 第 199-209 行

def apply_scheduled_sampling(self, input_ids, audio_labels, text_labels):
    """Scheduled Sampling: 用随机值替代部分GT，让模型学会从错误历史中恢复"""
    if self.scheduled_sampling_prob <= 0:
        return input_ids
    # 条件①：只在 audio_labels != -100 的位置（即「要算损失」的位置）替换
    # 条件②：且随机命中 scheduled_sampling_prob(默认0.05)
    audio_mask = (audio_labels != -100).any(dim=0) & (torch.rand(input_ids.size(1)) < self.scheduled_sampling_prob)
    for i in range(8):
        # 条件③：替换值域是 [0, audio_vocab_size=2112)，不是任意 token
        input_ids[i] = torch.where(audio_mask, torch.randint(0, self.audio_vocab_size, input_ids[i].shape), input_ids[i])
    # 保护 image token 的连续性：文本侧排除 image_token_id，且同样只在 label!=-100 + 概率命中处替换
    text_mask = (text_labels != -100) & (input_ids[8] != self.image_token_id) & (torch.rand(input_ids.size(1)) < self.scheduled_sampling_prob)
    input_ids[8] = torch.where(text_mask, torch.randint(0, self.text_vocab_size, input_ids[8].shape), input_ids[8])
    return input_ids

三个反直觉点：

  • 不是无脑随机替换：只在 audio_labels != -100 的位置替换——也就是只在「模型本来要预测音频码」的那些时间步动手。上下文区域（label=-100）保持原样。
  • 文本侧保护 image token：图像占位符 image_token_id 是连续 64 个，一旦打散模型就找不到图了，所以额外排除 input_ids[8] != self.image_token_id。
  • 替换值域受限：音频替换值落在 [0, 2112)（2048 个 mimi 码 + 64 特殊 token），文本落在 [0, len(tokenizer))——不会替换出非法 token。

Part 4：长短样本凑一锅

训练是按 batch 进行的，但每个样本长度不同。

collate_fn

对齐与填充

一个 batch 里，样本 A 的对话有 50 步，样本 B 有 80 步，样本 C 没有图片……直接堆成张量会维度不匹配。collate_fn 就是来解决这个的：

  • 文本/音频序列：pad 到 batch 内最长那个的长度，凑成统一形状
  • 图片：所有样本都堆起来——没图片的样本在 dataset 里就已填成 dummy 全零图，保证 batch 里每个位置都有图张量（见下页源码）
  • 音频 fbank 特征：同样 pad 到最长
# 一个 batch 的 3 个样本
样本1: 文本 50 步, 有图片
样本2: 文本 80 步, 无图片
样本3: 文本 60 步, 有图片

# collate 之后
input_ids: (3, 9, 80)     ← 全部 pad 到 80 步
pixel_values: (3, 3, 256, 256)  ← 样本2 是 dummy 全零图，但形状一致，batch 索引对齐

padding 填的是占位符（如 <|audio_pad|> 或 -100），这些位置不会被计算损失——它们只是为了让张量形状规整。

dummy 占位，非跳过

修正：之前为便于理解讲成「没图片的跳过」，真实实现不是跳过——而是返回一个全零的 dummy 张量，保证 batch 里每个样本的键结构（key/shape）完全一致。这样 collate 时直接 stack 不会因为缺键报错。

📌 对应源码：omni_dataset.py 的 OmniDataset.__getitem__（第 249-254 行）

📜 真实源码：omni_dataset.py 第 249-254 行

# 混合训练时，无音频样本返回dummy tensor保持batch索引尽可能对齐 (SenseVoice: T x 560)
if audio_inputs is None and self.audio_processor:
    audio_inputs = torch.zeros(1, 1, 560)          # ← 无音频 → dummy 全零
    audio_len = 0
if pixel_values is None and self.vision_processor:
    pixel_values = {'pixel_values': torch.zeros(1, 3, 256, 256)}   # ← 无图像 → dummy 全零

为什么不跳过而用 dummy：collate_fn 要把 batch 里所有样本的 pixel_values / audio_inputs 堆成一个大张量（torch.stack）。如果有的样本返回 None、有的返回张量，stack 会直接报错。用 dummy 全零张量占位，形状 (1,3,256,256) 和真实图一致，stack 时维度对齐；而全零的输入不会激活任何有意义特征，对训练无害。这才是「batch 键结构一致」的正确做法。

练习：理解 9 通道

填空与思考

一段助手回复「你好呀！」对应的训练样本，文本通道是 [你好, 呀, ！, <|im_end|>]。请回答：

  1. 对应的音频通道为什么是 8 层而不是 1 层？
  2. 如果文本标签是 [你好, 呀, ！, <|im_end|>]，而前面 system+user 部分的标签应该是什么值？为什么？
  3. 为什么要对波形做「加噪声、变速」这种「搞坏」数据的操作？

参考答案

1) 因为 Mimi 把音频编码成 8 层残差码本（阶段 0、3 讲过），8 层从粗到细表达声音，少一层就丢信息。2) 前面部分标签全是 -100。因为那些是上下文不是要学的内容，-100 让 CrossEntropyLoss 跳过，模型只学「最后这段回复」。3) 数据增强。真实环境的语音有噪声、语速差异，只学干净样本模型会过拟合、一到真实场景就抓瞎。增强逼模型学到本质而非表面。

常见困惑排解

「音频码为什么是交错排列的？」

answer_audios 是一维数组，每 8 个连续整数属于 8 个码本层（一帧）。解析时按 8 个一组切开，还原成 (8, T) 的形状。

「-100 这个数有特殊含义吗？」

没有数学特殊性，纯粹是 PyTorch 的约定——CrossEntropyLoss 的 ignore_index 默认就是 -100。换成别的负数也行，但约定俗成用 -100。

「没图片的样本怎么办？」

不是跳过，而是填一张 dummy 全零图 torch.zeros(1,3,256,256)。因为 collate_fn 要用 torch.stack 把整个 batch 的图张量堆起来，缺了会报错；全零图形状一致、stack 对齐，且全零输入不会激活有意义特征，对训练无害。

「增强会不会把数据搞得太乱学不会？」

增强强度是调过的（概率、幅度都有限制），目的是「增加多样性」而非「毁掉信号」。太强确实会学不会，所以参数要克制。

关键要点回顾

9 通道对齐

8 层音频 + 1 层文本共享同一时间轴，让模型学到「词对应什么声音」。

输入目标错一位

输入左移、目标右移，实现「预测下一个 token/音频码」的训练目标。

-100 屏蔽

只在最后一段 assistant 回复处算损失，前面的上下文用 -100 跳过。

数据增强

波形/频谱增强模拟真实环境，Scheduled Sampling 训练「纠错能力」，防过拟合。

collate 对齐

pad 到 batch 内最长，无图/无音频样本用 dummy 全零占位，让长短不一的样本凑成规整张量。

所有这些处理，都是为了让「文字、声音、图像」能在同一次训练里被模型同时学到。
