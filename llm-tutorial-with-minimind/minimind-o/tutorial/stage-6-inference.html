阶段 6 · 推理与评估——六种方式玩转 MiniMind-O

训练完了，然后呢

前面五章，我们拆解了架构、数据、训练。但模型训练好之后，躺在磁盘上只是个 .pth 文件——它不会自己开口。你得写代码把它加载起来、喂输入、收输出。

这个过程叫推理（inference）。MiniMind-O 的推理脚本 eval_omni.py 提供了六种「玩法」，覆盖它能做的所有事：文字聊天、多轮对话、语音对话、声音克隆、图像理解、混合输入。

本章就讲两件事：模型怎么从磁盘「活」过来，以及这六种玩法分别怎么玩。学完你能熟练地让 MiniMind-O 干活。

Part 1：唤醒模型

推理的第一步，是让冷冰冰的权重变成内存里能跑的对象。

📜 源码地图

整个推理脚本就三个函数 + 一个 main()，读源码时按这张地图找位置：

函数行号职责
init_model(args)17-40根据 load_from 选择加载方式，把主模型 + SenseVoice + SigLIP2 + Mimi 全部请回内存
eval_sample(...)43-87推理核心：构造 prompt → 流式生成 → 实时打印文本 + 攒音频帧 → Mimi 解码落盘
main()90-239解析参数，按 mode 调用 eval_sample；六种 mode 的输入构造都在这里

另外两个被 main() 调用的工具：音频预处理 OmniDataset.process_audio(path, processor)（定义在 dataset/omni_dataset.py，负责重采样 + SenseVoice fbank 提取）；以及模型自身的 MiniMindOmni.load_sensevoice / load_vision 静态方法。本章不展开它们的内部，只看 eval_omni.py 怎么用。

📌 一句话总结：理解了 init_model（加载）和 eval_sample（推理）这两个函数，main() 里六种 mode 只是「换不同输入喂给 eval_sample」的排列组合。

要加载的不止是主模型

MiniMind-O 推理时需要加载四样东西，缺一不可：

组件作用来源
主模型（Thinker+Talker）核心理解与生成你训练的 .pth
SenseVoice把输入语音转成特征预训练外部模型
SigLIP2把输入图像转成特征预训练外部模型
Mimi 解码器把生成的音频码变回声音预训练外部模型

回想阶段 1：真正训练的只有 ~113M 主模型，其余 400M+ 外部编码器都是「借用」的。推理时必须把它们都请回来，否则模型听不见、看不见、也说不出声。

两种权重格式

主模型支持两种加载方式，根据 --load_from 路径自动判断：

原生 PyTorch 格式

路径含 model，加载 .pth 文件。

先创建模型实例，再 load_state_dict。

适合你自己训练出来的模型。

HuggingFace 格式

用 AutoModelForCausalLM.from_pretrained。

标准化格式，方便分享和跨框架。

适合下载社区的模型。

model.eval()                # 切到推理模式（关闭 dropout 等）

def init_model(args):
    tokenizer = AutoTokenizer.from_pretrained(args.load_from)
    if 'model' in args.load_from:
        moe_suffix = '_moe' if args.use_moe else ''
        ckp = f'./{args.save_dir}/{args.weight}_{args.hidden_size}{moe_suffix}.pth'
        model = MiniMindOmni(
            OmniConfig(hidden_size=args.hidden_size,
                       num_hidden_layers=args.num_hidden_layers,
                       use_moe=bool(args.use_moe)),
            audio_encoder_path="./model/SenseVoiceSmall",
            vision_model_path="./model/siglip2-base-p32-256-ve")
        model.load_state_dict(torch.load(ckp, map_location=args.device), strict=False)
    else:
        model = AutoModelForCausalLM.from_pretrained(args.load_from, trust_remote_code=True)
        model.audio_encoder, model.audio_processor = MiniMindOmni.load_sensevoice("./model/SenseVoiceSmall")
        model.vision_encoder, model.vision_processor = MiniMindOmni.load_vision("./model/siglip2-base-p32-256-ve")
    log_model_params(model)
    if model.audio_encoder is not None: model.audio_encoder.to(args.device)
    if model.vision_encoder is not None: model.vision_encoder.to(args.device)
    model.mimi_model = MimiModel.from_pretrained("./model/mimi").eval()
    return model.half().eval().to(args.device), tokenizer

注意几个源码细节：(1) 判断分支用的是字符串包含 'model'，而不是看文件扩展名——原生训练权重的 --load_from 默认就是 'model'。(2) 原生分支在构造 MiniMindOmni 时直接传了 audio_encoder_path/vision_model_path，构造函数内部就完成了 SenseVoice/SigLIP2 的加载；HF 分支则在 from_pretrained 之后，用 MiniMindOmni.load_sensevoice/load_vision 这两个静态方法手动挂上。(3) Mimi 是两种分支共用的最后一步（第 39 行），单独用 MimiModel.from_pretrained 加载。(4) load_state_dict(strict=False) 容错，允许权重和模型结构有少量键不匹配（外部编码器没存进 .pth）。

Part 2：六种玩法

同一个模型，六种不同的输入组合，对应六种能力展示。

一张表看懂六种模式

mode输入输出展示的能力
0文本文字 + 语音基本文本对话
1文本（多轮）文字 + 语音上下文保持
2语音文字 + 语音语音对话（A2A）
3文本 + 参考音色模仿音色的语音声音克隆
4图像描述文字 + 语音图像理解（I2T）
5语音 + 图像文字 + 语音多模态理解

它们底层都走同一条推理流程（下一节），区别只在「输入怎么准备」。我们重点看几个有代表性的。

Mode 0：文本对话

这是入门玩法。输入一段文字，模型回复文字并附带语音。你在阶段 1 跑通的就是它。

python eval_omni.py --mode 0 --load_from ./out/model/xxx.pth

没有音频/图像输入，所以 Thinker 只处理文本，但 Talker 照常生成语音——只是这段语音是「标准音色」，没有特定的说话人特征。

📌 对应源码：eval_omni.py 第 116-129 行（mode '0' 分支）。它的调用特别干净：eval_sample(model, tokenizer, args, idx, prompt, None, f"text-{idx:02d}.mp3")——audio_inputs 传 None，pixel_values 默认 None，没有 ref_codes/spk_emb，纯文本走最短路径。

Mode 1：多轮对话

记住上下文

多轮对话的秘密不在 eval_sample，而在调用它时传的 history 参数。

📌 对应源码：eval_omni.py 第 131-174 行（mode '1' 分支）。每个测试用例是一个 {"history": [...], "prompt": "..."} 字典，history 是若干轮 {role, content}。

关键在 eval_sample 第 44 行：messages = (history or []) + [{"role": "user", "content": prompt}]——把历史对话拼到当前 prompt 前面，再交给 apply_chat_template 一次性展开成完整的 ChatML 多轮序列。模型一次看到全部历史，自然就「记住」了上下文。注意这不是增量式的 KV cache 复用，而是每次都重新拼整段历史重算——简单直接，适合评估场景。

Mode 2：语音对话

它听你说话

给它一段语音文件，它用语音回答。这是「耳朵」的展示。

关键在于输入准备：语音文件要经过和训练时一样的预处理——重采样到 16kHz、SenseVoice 提取 fbank 特征。然后 prompt 里用一串 <|audio_pad|> 占位符，这些占位符的位置会被真实音频特征注入（回顾阶段 3 的注入机制）。

audio-zh-01.mp3
  → 重采样 16kHz
  → SenseVoice 提取 fbank → mel (T, 560)
  → prompt 里放 audio_pad × valid_len 个占位符
  → 模型前向时，占位符被真实音频特征替换
  → Thinker 理解了语音内容 → 生成回复

📌 对应源码：eval_omni.py 第 181-188 行（mode '2' 分支）。下面是真实输入构造代码。

📜 真实源码：eval_omni.py 第 183-188 行

mel, valid_len = OmniDataset.process_audio(os.path.join(args.audio_dir, audio_file), model.audio_processor)
audio_inputs = mel.unsqueeze(0).to(args.device)            # (1, T, 560) fbank 特征
audio_lens = torch.tensor([valid_len], device=args.device) # 有效帧数（去掉 padding 后的真实长度）
audio_token_len = valid_len or 1                           # valid_len 为 0 时至少给 1 个占位符，避免空 prompt
prompt = model.config.audio_special_token * audio_token_len  # prompt 就是一串 <|audio_pad|> 占位符
eval_sample(model, tokenizer, args, idx, prompt, audio_inputs, f"audio-{idx:02d}-{...}.mp3", audio_lens=audio_lens)

读懂这段要抓住三个角色：audio_inputs 是真正的音频特征张量（喂给 eval_sample 的 audio_inputs 形参）；audio_lens 告诉模型这段特征实际有多少帧是有效的（后面用于注入）；prompt 是一串占位符，占位符个数 = valid_len，让模型在序列里预留出对应数量的位置，前向时这些位置被真实音频特征替换。audio_special_token 就是 <|audio_pad|>。

Mode 3：声音克隆

学谁像谁

声音克隆是 MiniMind-O 最「炫」的能力。它的关键在两个东西（阶段 3 提过）：

  • ref_codes：参考音频的 Mimi 码（声音的「样本」）
  • spk_emb：说话人嵌入，192 维向量（说话人的「身份」）

预置音色文件 voices.pt 里存了一批名人的 ref_codes + spk_emb。推理时把它们注入 Talker 的对应位置，Talker 就会用那个人的音色生成回复。

📌 对应源码：eval_omni.py 第 190-209 行（mode '3' 分支）。真实加载与注入代码如下。

📜 真实源码：eval_omni.py 第 195-209 行

voices_pt = os.path.join(..., 'model', 'speaker', 'voices_unseen.pt')
voices = [('default', None, None)]   # 第一个总是「默认音色」（不注入任何参考）
if os.path.exists(voices_pt):
    voice_data = torch.load(voices_pt, map_location=args.device)
    for speaker, v in sorted(voice_data.items()):
        rc = v['ref_codes'].unsqueeze(0).to(args.device)                              # ref_codes: (1, 8, T_ref)
        se = v['spk_emb'].half().unsqueeze(0).to(args.device) if 'spk_emb' in v else None  # spk_emb: (1, 192)
        voices.append((speaker, rc, se))

    for idx, prompt in enumerate(clone_prompts):

注意 ref_codes 的形状是 (1, 8, T_ref)——8 层码本、T_ref 帧（参考音频长度决定），对应一段真实声音样本；spk_emb 是 (1, 192) 的说话人身份向量。它们被传给 eval_sample 的 ref_codes / spk_emb 形参，再一路传进 model.generate(...)，在 Talker 序列里：ref_codes 放在目标音频生成区之前（作为声音样本，告诉 Talker「按这个风格开口」），spk_emb 注入到 <|audio_spk|> 位置（提供身份）。两者结合就实现了克隆。源码里有个 ('default', None, None)——这是不注入任何参考的对照项，输出就是模型自己的标准音色。

Part 3：推理完整流程

不管哪种模式，底层都走同一条路。

推理核心函数

eval_sample

所有模式最终都调用 eval_sample()，它做四件事：

  1. 组装 prompt：用 apply_chat_template 把对话格式化成模型认识的 ChatML 字符串
  2. 调用生成：model.generate(stream=True)，内部走阶段 3 讲的 stream_generate
  3. 实时收文本：每 yield 一个文本 token，立刻解码打印（打字机效果）
  4. 攒音频解码：把 yield 的音频帧收集起来，结束后一次性送 Mimi 解码、保存

注意第 3、4 步的区别：文本是实时显示的，音频是攒完再解码的（因为音频要凑够 8 层一帧才能解码）。

真实代码：两条节奏

eval_sample 的文本与音频分流

对照上面的四步，看真实源码怎么实现「文本实时 + 音频攒帧」。

📌 对应源码：eval_omni.py 的 eval_sample()（第 43-87 行）。

📜 真实源码：eval_omni.py 第 43-65 行

def eval_sample(model, tokenizer, args, idx, prompt, audio_inputs, output_name,
                pixel_values=None, history=None, audio_lens=None, ref_codes=None, spk_emb=None):
    messages = (history or []) + [{"role": "user", "content": prompt}]
    inputs_text = tokenizer.apply_chat_template(messages, tokenize=False, add_generation_prompt=True,
                                                open_thinking=bool(args.open_thinking))   # ① 组装 ChatML prompt
    x = torch.tensor(tokenizer(inputs_text).data['input_ids'], dtype=torch.long, device=args.device)[None, ...]  # ② 编码成 input_ids

    audio_frames = []
    with torch.no_grad():
        res_y = model.generate(x, tokenizer.eos_token_id, max_new_tokens=args.max_new_tokens,
                               temperature=args.temperature, top_p=args.top_p, stream=True,   # ③ stream=True 拿到生成器
                               return_audio_codes=True, open_thinking=bool(args.open_thinking),
                               audio_inputs=audio_inputs, audio_lens=audio_lens, pixel_values=pixel_values,
                               ref_codes=ref_codes, spk_emb=spk_emb)
        print('📒 [Thinker]: ', end='', flush=True)
        history_idx = 0
        for y, audio_frame in res_y:            # ④ 逐项迭代生成器
            if y is not None:                   # ⑤ 文本 token：实时 decode 打印（增量输出）
                answer = tokenizer.decode(y[0].tolist(), skip_special_tokens=True)
                if answer and answer[-1] != '�':
                    print(answer[history_idx:], end='', flush=True)
                    history_idx = len(answer)
            if audio_frame:                     # ⑥ 音频帧：先攒进列表，不立刻解码
                audio_frames.append(audio_frame)
        print()
        # ⑦ 攒完之后，audio_frames 一次性送 Mimi 解码（见下一 Part）

几个读懂关键：(1) apply_chat_template(..., add_generation_prompt=True) 会拼出形如 <|im_start|>assistant\n 的前缀，让模型从「助手开始说话」的位置续写——这是 ChatML 推理的标准姿势。(2) res_y 是个生成器，每次 yield (y, audio_frame) 一个元组：y 是文本 token id（可能是 None，表示这一步只产音频），audio_frame 是一帧 8 层音频码（可能是空，表示这一步只产文本）。(3) 文本用 answer[history_idx:] 做增量打印（只打印新增部分），靠 flush=True 立刻显示——这就是打字机效果。(4) 音频帧 audio_frame 只要非空就 append 到 audio_frames，循环结束后才统一处理。两条节奏由此分流。

你会看到的终端体验

📒 [Thinker]:
你（停顿）好（停顿）呀（停顿）！（停顿）有（停顿）什（停顿）么...
🎹 [Talker]: 45 frames | Audio decoded to: ./output/text-00.mp3

文本逐字出现（每个 token 之间有模型计算的微小停顿），全部生成完后，音频一次性解码保存成 mp3。这种「文字先流式、声音后落盘」的体验，正是 stream_generate 的 yield 机制带来的。

Part 4：码本变回声音

模型吐出的是 8 层音频码，怎么变成能播放的波形？

if audio_frames:
    if args.decode_audio:
        try:
            codes = [f for f in audio_frames if f and len(f) == 8]   # 只留长度恰为 8 的有效帧

            mimi_codes = torch.tensor(codes, dtype=torch.long).T.unsqueeze(0).to(args.device)  # (1, 8, T)
            filtered = torch.where(mimi_codes >= 2049, torch.zeros_like(mimi_codes), mimi_codes)  # 清零控制码
            audio = model.mimi_model.decode(filtered).audio_values                          # → 波形
            wav_path = output_path.rsplit('.', 1)[0] + '.wav'
            sf.write(wav_path, audio.squeeze().float().cpu().numpy(), 24000)                # 存 WAV，24kHz
            AudioSegment.from_wav(wav_path).export(output_path, format='mp3', bitrate='64k') # WAV → MP3
            os.remove(wav_path)                                                              # 删中间 WAV
        except Exception as e:
            print(f'⚠️ 保存音频失败: {str(e)}')

读真实代码要抓住四点：(1) [f for f in audio_frames if f and len(f) == 8] 这一步过滤掉长度不等于 8 的残帧——只有完整的 8 层码本才是一帧有效音频。(2) torch.tensor(codes).T.unsqueeze(0) 把列表转成 Mimi 要的 (1, 8, T) 形状（转置 + 加 batch 维）。(3) 核心 torch.where(mimi_codes >= 2049, 0, mimi_codes)——把所有 id ≥ 2049 的特殊控制码（pad=2049 / stop=2050 / spk=2051 等）替换成 0（Mimi 码本里的静音码），不是删除。换成静音而不是删除，是为了保持帧数，否则时间轴会错位。(4) 解码出来后先 sf.write 存 WAV（采样率 24000），再用 pydub 转 MP3（64kbps），最后 os.remove 删掉中间 WAV 文件——磁盘上只留 MP3。

练习：动手试一遍

六种模式各跑一次

用 --mode -1 一次串跑所有模式，或者逐个跑。重点观察并回答：

  1. Mode 0 和 Mode 2 生成的 mp3，音色一样吗？为什么？
  2. Mode 3 用不同预置音色，输出的语音有什么区别？
  3. 把 --temperature 从 0.7 调到 0.1 和 1.5，观察生成内容的差异。

参考答案

1) 不完全一样。Mode 0 没有特定说话人输入，用默认音色；Mode 2 的音色取决于输入语音的处理，可能有差异。2) 不同预置音色的 ref_codes 和 spk_emb 不同，Talker 模仿不同人的音色，听起来像不同人在说话。3) temperature=0.1 输出保守、重复性高、确定性；1.5 输出奔放、多样、可能跑题。这正是阶段 2 讲的采样策略效果。

推理常见坑

生成的内容是乱码

原因：tokenizer 和模型不匹配，或权重加载错位。

修复：确认 tokenizer.json 和模型权重是同一版本；检查 load_from 路径。

音频文件没声音/极短

原因：Mimi 没加载，或音频码全被过滤了。

修复：确认 Mimi 路径；看终端的 frames 数，若为 0 说明 Talker 没正常生成。

推理特别慢

原因：没用到 GPU，或 KV Cache 没生效。

修复：确认 model.to('cuda')；确认 use_cache=True；减小 max_new_tokens。

声音克隆不像

原因：spk_emb 或 ref_codes 注入位置不对，或音色文件版本不匹配。

修复：确认 voices.pt 与模型配套；参考音频长度建议 3-6 秒。

关键要点回顾

四件套加载

主模型 + SenseVoice + SigLIP2 + Mimi，缺一不可。外部编码器是「借」来的，推理时要请回。

六种模式

同一模型、不同输入组合：文本/多轮/语音/克隆/图像/混合。底层流程一致。

注入是关键

音频/图像输入的本质，是用真实特征替换 prompt 里的占位符。

声音克隆

ref_codes（声音样本）+ spk_emb（身份），注入 Talker 实现模仿。

流式文本+落盘音频

文本实时 yield 显示，音频攒帧后 Mimi 解码保存。两条节奏。

解码要过滤

特殊控制码（≥2049）必须过滤掉，否则 Mimi 解码出噪声。
