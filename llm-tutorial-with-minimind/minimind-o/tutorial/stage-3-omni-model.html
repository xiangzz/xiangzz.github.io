阶段 3 · 全模态模型 Thinker-Talker 双路径

Thinker 还差两样

上一章的 Thinker，还差两样东西

阶段 2 结束时，Thinker 已经是一个合格的语言模型：它能读懂文字、能生成文字。但 MiniMind-O 叫「全模态」——它还得能听（理解语音和图像）、能说（生成语音）。

问题是：同一个 Transformer，怎么既当大脑又当嘴巴？让一个网络同时干「理解」和「发声」这两件差别极大的事，行不行？

MiniMind-O 的回答是：别让一个网络硬扛，拆成两个。一个 Thinker 专心理解、生成文字；一个 Talker 专门把文字变成声音。两者用一个 Bridge 连起来。

这个「双大脑」设计，是本章的全部。理解了它，你就理解了 MiniMind-O 与普通 LLM 的本质区别。

卸掉这个比喻：「大脑」「嘴巴」「桥」只是为了帮你建立直觉。代码里 Thinker 和 Talker 是两个独立的 nn.Module（Transformer），它们之间传递的并不是「想法」，而是一个 (B, T, 768) 的浮点张量——具体说是 Thinker 第 3 层的隐藏状态。Bridge 也不是物理连接，就是一次张量切片 + 线性投影。所以接下来看到 bridge_layer、hidden_states 这些词时，记得把它们对回这里的比喻。

Part 1：两个大脑

从「一个会读写的模型」到「一个能听能说的模型」，最关键的设计决策。

一个网络硬扛会怎样

设想最朴素的方案：把 Thinker 的输出头从「6400 个词」换成「同时预测词 + 8 层音频码」。听起来简单，但有两个硬伤：

  • 任务打架：理解语言需要「语义」表征，生成声音需要「声学」表征，两者最优的隐藏状态分布完全不同。一个网络被拉扯，两边都做不好。
  • 浪费算力：纯文本对话时根本不需要算声音，但混在一起就停不下来。

所以 MiniMind-O 的选择是：保留 Thinker 专攻语言，新增一个 Talker 专攻声音。

挂载但不注册

object.__setattr__：把大编码器「挂」上去但不参与训练

📌 对应源码：model_omni.py 的 MiniMindOmni.__init__()（第 110-121 行）

读源码时你会看到 __init__ 里用 object.__setattr__(self, 'thinker', self.model) 这种写法，而不是常见的 self.thinker = self.model。这不是炫技，是故意绕过 nn.Module 的参数注册。

📜 真实源码：model_omni.py 第 110-121 行

class MiniMindOmni(MiniMindForCausalLM):
    def __init__(self, config, audio_encoder_path=..., vision_model_path=...):
        super().__init__(config)
        object.__setattr__(self, 'thinker', self.model)        # thinker 是 model 的别名！
        object.__setattr__(self.model, 'lm_head', self.lm_head)
        self.talker = TalkerModule(config)
        self.audio_proj = MMAudioProjector(...)
        self.vision_proj = MMVisionProjector(...)
        # ...
        audio_encoder, audio_processor = self.load_sensevoice(audio_encoder_path)
        object.__setattr__(self, 'audio_encoder', audio_encoder)   # 大编码器，不注册参数
        object.__setattr__(self, 'audio_processor', audio_processor)
        vision_encoder, vision_processor = self.load_vision(vision_model_path)
        object.__setattr__(self, 'vision_encoder', vision_encoder) # 大编码器，不注册参数
        object.__setattr__(self, 'vision_processor', vision_processor)

普通 self.x = ... 会发生什么

nn.Module.__setattr__ 会自动把赋值对象的参数登记到 self._parameters / self._modules，于是 self.parameters() 会包含它，优化器会更新它。

object.__setattr__ 绕过注册

直接调用最底层的 object 的赋值，跳过 nn.Module 的注册逻辑。于是 audio_encoder / vision_encoder 虽然挂在 self 上能调用，但不进入 self.parameters()，不会被训练（也省显存，不用给它们存梯度）。

点破一个关键别名：self.thinker 就是继承来的 self.model。 MiniMindOmni 继承自 MiniMindForCausalLM，父类已经有个 self.model（Thinker 本体）。object.__setattr__(self,'thinker',self.model) 只是把 self.model 起了个语义更清晰的别名 self.thinker——所以在源码里你会看到 self.thinker.layers、self.thinker.norm，它们和 self.model.layers、self.model.norm 是同一个对象。同理 self.audio_encoder / self.vision_encoder 用 object.__setattr__ 注册，是因为这俩是大预训练模型，整个冻结、不训练（代码里 requires_grad = False 也佐证了这一点）。

Part 2：感官对齐

文字、声音、图像，怎么塞进同一个 Thinker？

Thinker 只认 768 维向量。但三种输入的「原生维度」完全不同：文本经 Embedding 是 768 维，音频经 SenseVoice 是 512 维，图像经 SigLIP2 虽然也是 768 维但语义空间不同。必须把它们对齐到同一个 768 维空间，才能拼到一起送进 Transformer。

投影器：维度翻译官

📌 对应源码：model_omni.py 的 MMAudioProjector / MMVisionProjector（第 31-54 行）

对齐的工具是投影器（Projector）——一个两层的小 MLP。它把每种模态的特征「翻译」成 Thinker 能消化的 768 维。

教程简化版

# 音频投影器：512 维 → 768 维
class MMAudioProjector(nn.Module):
    def __init__(self):
        self.norm = nn.LayerNorm(512)
        self.proj = nn.Sequential(
            nn.Linear(512, 768),   # 升维到 768
            nn.GELU(),             # 非线性
            nn.Linear(768, 768),   # 再做一次变换
        )
    def forward(self, x):
        return self.proj(self.norm(x))   # (T, 512) → (T, 768)

真实源码 model_omni.py:31-41

📜 真实源码：model_omni.py 第 31-41 行

class MMAudioProjector(nn.Module):
    def __init__(self, in_dim, out_dim):
        super().__init__()
        self.mlp = nn.Sequential(
            nn.LayerNorm(in_dim),
            nn.Linear(in_dim, out_dim),    # 512 → 768
            nn.GELU(),
            nn.Linear(out_dim, out_dim),   # 768 → 768
        )
    def forward(self, x):
        return self.mlp(x)
# 实例化：self.audio_proj = MMAudioProjector(config.audio_hidden_size, config.hidden_size)
#        = MMAudioProjector(512, 768)

视觉投影器 MMVisionProjector 结构完全相同（model_omni.py 第 44-54 行），只是 SigLIP2 输出本来就是 768 维，所以是 768→768 的变换（主要起「语义对齐」而非「改维度」的作用）。

为什么是两层 MLP 而不是一层 Linear？ 因为不同编码器的语义空间差异较大（SenseVoice 的 512 维和 Thinker 的 768 维含义完全不同），需要一点非线性变换才能把语义对齐好。LayerNorm 先归一化能让训练更稳。注意真实代码里 in_dim/out_dim 是构造时传入的（不是写死 512/768），所以同一个类既能做音频（512→768）又能做视觉（768→768）。

「注入」而不是「拼接」

对齐之后，怎么把音频/图像特征送进 Thinker？MiniMind-O 用了一个巧妙的设计叫注入（inject）：不是在序列末尾追加新 token，而是替换序列里的占位符。

注入：toy ↔ 源码

对照：注入黑盒 ↔ 真实 inject_audio_features

📌 对应源码：model_omni.py 的 MiniMindOmni.inject_audio_features()（第 160-181 行）

真实实现的「注入」不是一句 hidden[mask] = audio_feat，而是扫描连续 marker、切片替换、且只注入第一段。逐样本遍历 token 序列，遇到 <|audio_pad|> 就连续往前吞，吞到的这一段用真实音频特征切片替换。

教程概念版

def inject(hidden, audio_feat, audio_pad_positions):
    # 把 audio_pad 位置替换成真实音频特征
    hidden[audio_pad_positions] = audio_feat
    return hidden

看起来一句赋值就够。但真实实现要处理「连续 marker」「长度对齐」「多段只填第一段」。

真实源码 model_omni.py:160-181

📜 真实源码：model_omni.py 第 160-181 行

def inject_audio_features(self, tokens, h, audio_feats, seqlen):
    marker = self.config.audio_ids[0]   # <|audio_pad|>
    out = []
    for b in range(h.size(0)):
        hb, seq, i = h[b], tokens[b].tolist(), 0
        af = audio_feats[b] if audio_feats[b] is not None else None
        while i < len(seq):
            if seq[i] == marker:
                start = i
                while i < len(seq) and seq[i] == marker:
                    i += 1                          # 吞掉连续 marker
                if af is not None:
                    inject_len = min(af.size(0), i - start)
                    hb = torch.cat((hb[:start], af[:inject_len], hb[start + inject_len:]), dim=0)  # 切片替换
                    af = None                        # 只注入第一段，后面 marker 保持原样
            else:
                i += 1
        out.append(hb)
    return torch.stack(out)

三个关键细节学生容易卡：(1) 用 while i < len(seq) and seq[i] == marker 把连续的占位符整段吞掉，start 记起点、i 走到末尾；(2) inject_len = min(af.size(0), i - start) 取「音频特征帧数」和「占位符个数」的较小值，torch.cat((hb[:start], af[:inject_len], hb[start+inject_len:])) 把这一段切片替换掉；(3) 替换完立刻 af = None，保证只注入第一段音频（一句话只需注入一次说话人的语音特征，后面再有 marker 也不填）。

含 None 的 list

encode_audio_inputs 的陷阱：返回含 None 的 list

📌 对应源码：model_omni.py 的 MiniMindOmni.encode_audio_inputs()（第 137-158 行）

这是学生读源码最容易卡住的地方：这个函数的返回值不是 tensor，是一个 list，而且当批次里部分样本没有音频时，list 里会含有 None。

📜 真实源码：model_omni.py 第 137-158 行

@torch.compiler.disable
def encode_audio_inputs(self, audio_inputs, audio_lens=None):
    if (audio_inputs is None) or (self.audio_encoder is None) or (not audio_inputs.any()):
        return None
    batch_mask = audio_inputs.flatten(1).any(1)            # 哪些样本真的有音频
    enc_dtype = next(self.audio_encoder.parameters()).dtype
    valid_fbank = audio_inputs[batch_mask].to(dtype=enc_dtype)   # 只编码"有音频"的样本
    # ...
    emb_list = [self.audio_proj(emb[i, ...].unsqueeze(0).to(proj_dtype)).squeeze(0) for i in range(emb.size(0))]
    if batch_mask.all():
        return emb_list                                     # 全部都有音频 → list[tensor]
    out = [None] * audio_inputs.size(0)                     # 关键：含 None 的 list
    j = 0
    for i in range(audio_inputs.size(0)):
        if batch_mask[i]:
            out[i] = emb_list[j]                            # 有音频的位置填上
            j += 1                                          # 没音频的位置保持 None
    return out                                              # 返回 list，里面混着 None

为什么是 list 而不是 tensor？ 因为不同样本的音频长度不同（帧数不同），无法 stack 成一个规整的 tensor，所以用 list 逐样本存。为什么含 None？批次里有的样本是纯文本（没音频），batch_mask 把它们过滤掉只送有效样本给编码器，但返回时要在原位置补 None 占位，保证 out[i] 和原 batch 的第 i 个样本对应。下游 inject_audio_features 用 af = audio_feats[b] if audio_feats[b] is not None else None 来兼容这个 None——读源码时如果在这里看到 None 检查，就知道是处理「这个样本没音频」的情况。

Part 3：Bridge

Thinker 想好了要说什么，Talker 怎么知道？

从哪一层取信息

从 Thinker 的哪一层取信息

Thinker 有 8 层。Talker 需要拿到 Thinker 的「想法」来生成声音——但该从哪一层取？MiniMind-O 的答案是第 3 层（从 0 开始数，共 8 层）。

取哪一层问题
太浅（第 0、1 层）语义信息还没充分提取，太「原始」
太深（第 6、7 层）信息已经过度适配「预测下一个词」这个具体任务，损失了生成声音所需的丰富表征
中间（第 3 层）既有足够语义理解，又保留了丰富的中间表征 ← 选这个

📌 对应源码：model_omni.py 的 OmniConfig（第 10-29 行）；bridge_layer 在第 29 行：默认 self.bridge_layer = kwargs.get("bridge_layer", self.num_hidden_layers // 2 - 1)，对 8 层 Thinker 就是 8//2-1 = 3。

这叫 bridge_layer = 3，是 OmniConfig 里的一个关键超参数。它本质是个折中：在「理解得够深」和「表征够通用」之间找平衡点。这个值是实验调出来的，不同模型可能不同。

顺便熟悉一下 OmniConfig（model_omni.py 第 10-29 行）里几个你会反复看到的字段：audio_pad_token=2049（音频占位码）、audio_stop_token=2050（停止码）、audio_spk_token=2051（说话人占位码）、audio_vocab_size=2112（每层码本词表）、spk_emb_size=192（说话人嵌入维度）、image_token_len=64（图像 token 数）、think_end_ids=[26,234,234]（</think>\n\n）。

Bridge 状态怎么用

Thinker 前向时，顺手把第 3 层的隐藏状态存下来（叫 bridge_states）。Talker 拿到它后，先过一个 embed_proj 投影，再作为 Talker 的主要输入。

# Thinker 前向时捕获第 3 层
for i, layer in enumerate(self.thinker.layers):
    hidden = layer(hidden)
    if i == self.bridge_layer:           # 第 3 层
        bridge_states = hidden           # 存下来，留给 Talker

但 Talker 的输入不只这一路——还有来自音频的信号。两路怎么融合？

两路融合公式

融合公式：文字意图 + 声音信号

Talker 的输入是两路信号相加：

talker_input = embed_proj(bridge_states) × text_scale
              + codec_proj(audio_embeddings) × audio_scale

图：Talker 输入的两路融合

【AI 生图提示词】请生成一张中文技术示意图，风格简洁、配色柔和、适合教学： - 画面主体：两股信号从左右两侧汇入中间一个 + 号的流程图 - 左路（上方）：bridge_states（Thinker 第 3 层，浅蓝色）→ embed_proj 投影 → × text_scale=3.0（标注「文字意图，权重更大」） - 右路（下方）：audio_embeddings（8 码本嵌入平均，浅紫色）→ codec_proj 投影 → × audio_scale=1.0（标注「声音信号，权重较小」） - 两路在中间的 + 号汇合，得到 talker_input（浅绿色），标注「Talker 的输入」 - 关键标注：在 text_scale 旁标注「初始 3.0，语义理解是基础，权重更大」；在 audio_scale 旁标注「初始 1.0，声音是辅助」；底部补充「两个 scale 是可学习参数，训练中模型自己调整比例」 - 配色建议：浅灰背景，文字路浅蓝色，声音路浅紫色，汇合结果浅绿色，scale 数字橙色 - 画面比例：16:9

为什么文字权重（3.0）比声音权重（1.0）大？ 因为「说什么」由语义决定（文字意图是主导），「怎么说」（声音细节）是辅助。初始给文字更大权重，让模型先学会「说对话」，再慢慢调声音。这两个 scale 是可学习的，训练中模型会自己找到最佳比例。

Part 4：8 层声音

声音有 8 层码本，Talker 怎么同时预测 8 个输出？

朴素方案的代价

每个位置 Talker 要输出 8 个码（对应 8 层码本），每个码是 2112 选 1。最直白的做法：搞 8 个独立的输出头，每个是一个 Linear(768, 2112)。

8 个独立输出头 = 8 × Linear(768, 2112)
             = 8 × 1.6M = 12.8M 参数

13M 参数，对一个 ~113M 的模型来说占比太大了。而且这 8 层码本预测的内容高度相关（都是同一句话的声音），用 8 个完全独立的头是一种浪费。

共享基座 + 轻量适配器

📌 对应源码：model_omni.py 的 TalkerHead（第 57-65 行）、TalkerEmbedding（第 68-76 行）、TalkerModule（第 88-102 行）

MiniMind-O 的优化：一个大基座大家共享，每个码本再加一个小适配器表达差异。

教程简化版

class TalkerHead(nn.Module):
    def __init__(self):
        self.base = nn.Linear(768, 2112)          # 共享基座，所有码本都用它
        self.adapters = nn.ModuleList([           # 8 个轻量适配器
            nn.Sequential(nn.Linear(768, 256), nn.GELU(), nn.Linear(256, 2112))
            for _ in range(8)
        ])

    def forward(self, x):
        base_out = self.base(x)                   # 共享部分
        return [base_out + adapter_i(x)           # 每层 = 共享 + 该层专属微调
                for adapter_i in self.adapters]

class TalkerHead(nn.Module):
    def __init__(self, in_features, out_features, num_layers=8, rank=256):
        super().__init__()
        self.num_layers = num_layers
        self.base = nn.Linear(in_features, out_features, bias=False)
        self.adapters = nn.ModuleList([
            nn.Sequential(nn.Linear(in_features, rank, bias=False),
                          nn.GELU(),
                          nn.Linear(rank, out_features, bias=False))
            for _ in range(num_layers)])
    def forward(self, x):
        base_out = self.base(x)
        return [base_out + adapter(x) for adapter in self.adapters]

8 个独立头

12.8M 参数

8 层完全独立，重复造轮子

共享 + 适配器

约 7.5M 参数（省 40%）

共性用基座，差异用小适配器（低秩 256）

这本质是一种低秩思想：8 层码本共享大部分知识（基座），只在细节上有差异（用 256 维的小适配器表达）。和 LoRA 的思路一脉相承。

对称设计：TalkerEmbedding（model_omni.py 第 68-76 行）也用同样的「基座 + 适配器」结构，只不过是反向的——把音频码本 id 映射回嵌入向量：self.base = nn.Embedding(...) 共享，self.adapters 每层一个，forward 里 sum(base_out[:, i, :] + self.adapters[i](x[:, i, :]) for i in ...)/num_layers。输出头和输入嵌入一进一出，结构完全对称。TalkerModule（第 88-102 行）则把 talker 的所有零件（4 层 MiniMindBlock、RMSNorm、TalkerHead lm_head、TalkerEmbedding embed_tokens、codec_proj/embed_proj、text_scale/audio_scale、spk_proj）打包到一起。

交错延迟

交错延迟：让声音「错落有致」地生成

📌 对应源码：model_omni.py 的 MiniMindOmni.stream_generate()（audio_step 与 if audio_step < i 判断）

这是 MiniMind-O 最巧妙的设计之一。Talker 不是「同时」生成 8 层，而是让第 i 层码本延迟 i 步才开始生成——形成阶梯式的延迟。真实实现里，延迟由一个统一的 audio_step 变量控制，不是「第 i 层各自独立计数」。

教程概念版

每层各自延迟，第 i 层从第 i 步开始。这是为了建立直觉的简化说法。

码本层 i 从第 i 步开始生成：
  layer 0: 第 0 步开始
  layer 1: 第 1 步开始
  ...
  layer 7: 第 7 步开始

真实源码 model_omni.py:363-378

📜 真实源码：model_omni.py 第 363-378 行

step = input_ids.shape[1] - start_pos

# ...

    if audio_step < i:                       # 第 i 层还没轮到
        audio_codes[i].append(self.audio_pad_token)
    else:
        # ... 真正采样第 i 层码本

之前为便于理解讲成「第 i 层从第 i 步开始」，真实实现是：用一个统一的 audio_step 控制。在普通模式下 audio_step = step - 1（恒定延迟 1 步）；每层用 if audio_step < i 判断「我这一层还没轮到，就补一个 audio_pad_token 占位」。audio_step 是个不断增长的「时钟」，所有 8 层共享它，于是自然形成了阶梯延迟的效果（第 i 层要等 audio_step 长到 >= i 才开始真采样）。

为什么要 *0

训练时只有部分数据流会经过某些新模块（例如纯文本 batch 根本不碰 vision_proj，没有 spk_emb 时不碰 spk_proj）。PyTorch 里没参与前向的参数不会被优化器更新（在 AdamW 里甚至可能跳过权重衰减，造成训练不一致）。

*0 怎么解决问题

把 audio_proj / vision_proj / adapters / spk_proj 的参数显式加进 loss，*0 保证不改变 loss 数值（梯度贡献也是 0），但让这些参数"出现"在反向传播的计算图里，从而在每一步都被优化器统一处理（含权重衰减）。

另一个省算力的细节：logits_to_keep 切片。 slice_indices = slice(-logits_to_keep, None) 表示只对序列末尾 logits_to_keep 个位置算 logits（过 lm_head）。训练时如果只关心最后几个位置的预测（比如最后一个 token 的 next-token loss），就不用对整个序列算一遍 768→6400 / 768→2112 的大矩阵乘法，省一大笔显存和算力。h_thinker[:, slice_indices, :] 就是切出这个末尾窗口。

Part 6：流式生成

推理时，Thinker 和 Talker 不是「想完再说」，而是同步进行。

stream_generate：一个会 yield 的循环

def stream_generate(self, input_ids, eos_token_id, max_new_tokens, temperature, top_p, rp, use_cache, return_audio_codes=False, **args):
    start_pos, past_kvs, text_finished, first_finished = input_ids.shape[1], None, False, True
    audio_codes = [[] for _ in range(8)]
    audio_stop_pos = [None] * 8
    audio_buffer = torch.full((1, 8, start_pos), self.audio_pad_token, ...)
    # ... 处理 spk_emb / ref_codes 初始化

        out = self.forward(...)                      # 一次 forward（带 KV cache）
        past_kvs = out.past_key_values
        # ... 文本采样 + 音频按 audio_step 采样（见前面采样 slide）
        if text_finished and all(audio_stop_pos[i] is not None for i in range(8)): break

调用方（比如 eval_omni.py）拿到 yield 的文本就立刻打印（打字机效果），拿到音频帧就攒着——攒够 8 层一帧就送去 Mimi 解码播放。文本和语音是同步流式产出的，这就是为什么 MiniMind-O 能实现「边说边出声」的实时感。注意源码里 audio_buffer 是个 (1,8,T) 的张量，每一步往右长一格，把 8 层码本的「已知部分」喂给下一次 forward。

什么时候停

📌 对应源码：model_omni.py 的 MiniMindOmni.stream_generate() 第 378、380 行

生成在两个条件都满足时结束：

  • 文本侧：Thinker 生成了结束符 <|im_end|>（对应 eos_token_id，text_finished=True，第 391-393 行）
  • 音频侧：所有 8 层码本都触发了停止（all(audio_stop_pos[i] is not None for i in range(8))，第 380 行）

📜 真实源码：model_omni.py 第 378、380 行

if audio_stop_pos[i] is None and code >= 2048:    # code>=2048 判停止
    audio_stop_pos[i] = len(audio_codes[i]) - 1   # 记录这一层停在哪一步
# ...
if text_finished and all(audio_stop_pos[i] is not None for i in range(8)): break   # 两边都停才 break

注意音频侧的停止判据是 code >= 2048，不是只判 == 2050。这是因为码本 0-2047 是正常音频码，而 2048 及以上都是控制码（audio_pad_token=2049 / audio_stop_token=2050 / audio_spk_token=2051）——只要模型在某一层吐出了控制码，就认为这一层该结束了。

由于交错延迟，文本先结束，音频还会再跑几步把剩余的码本层补齐。所以你会看到终端里「文本打完了，但 Talker 还在输出几帧音频」的现象——这是正常的。

声音克隆：换个音色说话

声音克隆（mode 3）的秘密就藏在 forward 第 4 步：注入不同的 spk_emb 和参考音频码 ref_codes，Talker 就会用对应的音色生成。

# 克隆流程
录 3~6 秒某人的声音
    → Mimi 编码成 ref_codes（参考音频码）
    → CAM++ 提取 spk_emb（192 维说话人嵌入）
    → 推理时注入到 Talker 的 spk 位置
    → Talker 模仿这个音色生成回复

ref_codes 提供「声音的样本」，spk_emb 提供「说话人的身份」。两者结合，Talker 就能「学谁像谁」。预置音色文件 voices.pt 里就存了一批这样的组合。

练习：设计选择题

三个设计决策，为什么这么做

试着不看前文，回答这三个「为什么」：

  1. 为什么 Talker 从 Thinker 的第 3 层（而不是最后一层）取 bridge_states？
  2. 为什么融合公式里 text_scale=3.0 大于 audio_scale=1.0？
  3. 为什么 TalkerHead 用共享基座 + 适配器，而不是 8 个独立头？

参考答案

1) 最后一层过度适配「预测下一个词」，表征太专用；太浅层语义不足。第 3 层是「理解够深 + 表征够通用」的折中。2) 「说什么」由语义主导，声音是辅助；初始给文字更大权重让模型先学对话，两个 scale 可学习会再调。3) 8 层码本高度相关，共享基座表达共性、小适配器表达差异，省 40% 参数还不损效果（低秩思想）。

常见困惑排解

「文本和音频是怎么对齐的？」

靠 9 通道共享时间轴。训练时每个文本 token 和对应的音频码在同一时间步，模型从数据中学到「这句话对应这段声音」。

「为什么 Talker 只有 4 层，比 Thinker 少？」

生成声音比理解语言简单（它已经有了 Thinker 的理解结果作输入）。少层既够用又省参数。4 层是从 Thinker 后 4 层复制来的。

「纯文本对话时 Talker 还工作吗？」

工作，但你听不到。没有音频输入时，Talker 仍会生成音频码——只是这部分输出你可能不保存。它不会拖慢太多，因为 Talker 层数少。

「实时通话的打断（barge-in）怎么实现？」

那是 Web 端 VAD（语音活动检测）的功劳，不在模型内部。详见阶段 7 Web 演示——VAD 检测到用户开口，就中断正在生成的回复。

关键要点回顾

双大脑分工

Thinker（8层）管理解+文字，Talker（4层）管发声。一个网络干不好两件相反的事。

投影对齐 + 注入

三种模态经投影器对齐到 768 维，再用「替换占位符」的方式注入序列。

Bridge 第 3 层

从 Thinker 中间层取状态给 Talker，是「够深」和「够通用」的折中。

共享 + 适配器

TalkerHead 用一个共享基座 + 8 个低秩适配器，省 40% 参数表达 8 层码本。

交错延迟

由统一的 audio_step 控制，if audio_step < i 决定第 i 层是否补 pad。低层先动高层后跟，模拟真实语音产生。

流式同步输出

stream_generate 用 yield 同时吐文本和音频，实现边说边出声的实时感。
