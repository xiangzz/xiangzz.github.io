Agent RL 工具调用

阶段 9 · 教小模型学会"使用工具"——从只会说话，到会动手解决问题

模型的盲区

经过前面八个阶段的训练，你的 MiniMind 已经能流利对话、区分好坏回答、甚至学会推理。但它有一个根本性的局限——

它只能靠"记忆"回答问题，无法获取实时信息或执行精确计算。

你问 "256 x 37 = ?"，它靠训练数据猜，可能猜对也可能猜错。你问"北京今天天气"，它只能编一个。训练数据再好，也覆盖不了所有事实和计算。

怎么办？给它工具。让模型学会在需要的时候调用计算器、查天气、翻译文本——从"背书的书呆子"变成"会查资料的实用派"。

这就是 Agent RL：用强化学习教会模型使用工具。

Part 1: Agent 概念

理解什么是 Agent，以及为什么 LLM 需要工具。

模型再能说会道，也只会"靠记忆回答问题"——算术可能算错，天气只能瞎编。给它工具，它就从"背书的书呆子"变成了"会查资料的实用派"。这一节建立 Agent 的基本概念：LLM + 工具 = 能决策、能执行的智能体。

  • 什么是 Agent：Agent = LLM + 外部工具。模型生成特殊格式的标记来请求执行函数，外部系统解析后返回结果——本质是纯文本协议
  • 核心工作流：用户提问 → Agent 理解意图并决策用哪个工具 → 调用工具拿到结果 → 基于结果组织回答
  • 架构全景：文本协议层是核心——所有交互都是纯文本，模型不直接调用函数，通过 tool_call/tool_response 标签通信

什么是 Agent

定义：Agent = LLM + 使用外部工具的能力。模型在生成文本的过程中，可以插入特定格式的标记来请求执行外部函数，然后基于函数返回结果继续生成。

白话：想象你雇了一个助手。没有工具时，你问 256 x 37，他靠心算，可能算错。给了他计算器后，他会主动拿计算器按一下——结果一定准确。

这个比喻只为建立直观感受。实际上，模型只是生成了特殊格式的文本标记，外部系统解析这些标记后执行函数并返回结果——没有真正的"助手"在工作。

Part 2: 工具定义

6 个模拟工具的定义、调用格式和模拟数据机制。

模型只会输出文字，怎么让它"调用工具"？答案是约定一套文本协议：模型输出 <tool_call> 标签，外部系统就执行对应函数。这一节介绍 MiniMind 定义的 6 个训练工具、它们的调用格式，以及为什么训练时用模拟数据而不是真实 API。

  • 标签协议：<tool_call> 和 <tool_response> 标签机制，标签内必须是合法 JSON，包含 name 和 arguments
  • 6 个内置工具：calculate_math、unit_converter、get_current_weather、get_current_time、get_exchange_rate、translate_text，每个遵循 OpenAI Function Calling 标准
  • 模拟数据机制：训练时不调真实 API——太慢、不稳定、要花钱。模拟执行器用 eval 做计算（带安全限制），CHECK_ARGS 做参数校验

为什么用标签

核心矛盾：模型只会输出文字，不会真的"按按钮"。那怎么让它调用工具？

解决方案：约定一套文本协议。模型输出特殊标签 <tool_call> 时，外部系统就执行对应工具。本质上，工具调用只是"生成特殊格式的文本"。

<!-- 模型发出：工具调用 -->
<tool_call
{"name": "calculate_math", "arguments": {"expression": "256*37"}}
</tool_call

<!-- 系统返回：工具响应（模型不生成这个） -->
<tool_response
{"result": "9472"}
</tool_response

格式要求：标签内必须是合法 JSON，包含 name（工具名）和 arguments（参数字典）。为什么不用其他格式（比如纯 JSON 或 XML）？因为标签对正则解析更友好，且与模型已有的特殊 token（如 <|im_start|>）风格一致。

为什么要模拟？训练时不调用真实 API——太慢、不稳定、要花钱。就像在教室里用模拟题训练，等学会了方法，换真实工具没问题。

Part 3: 模型如何调用工具

模型生成了 <tool_call> 文本，系统如何提取意图并安全执行？

上一节定义了工具的"字典"，这一节搞定工具的"执行管线"：从模型输出的一大段文本中准确提取工具调用，然后安全地执行。两个核心问题——怎么从混合文本中提取 JSON？怎么防止 eval() 执行恶意代码把训练进程卡死？

  • 解析设计：用 <tool_call> 标签做"信封"，正则提取标签内 JSON。容错策略：解析失败直接跳过，不崩溃
  • parse_tool_calls 代码：正则 <tool_call\n(.*?)\n</tool_call 非贪婪匹配 + re.DOTALL，JSON 解析失败静默跳过
  • 安全执行 execute_tool：1 秒超时保护防止 eval() 执行死循环，出错返回 None 不中断训练

为什么要这样解析

问题：模型的输出是一大段文本，里面可能混杂着自然语言和工具调用。怎么准确提取工具调用？

思路：用 <tool_call> 标签做"信封"——正则表达式找到标签，再解析里面的 JSON。标签机制的好处是：模型可以同时输出自然语言和工具调用，两者不冲突。

模型输出:

解析失败怎么办？模型可能生成格式错误的 JSON。设计上采用容错策略：失败的调用直接跳过，不会导致训练崩溃。宁可漏掉一个调用，也不能让整个流程挂掉。

安全执行工具

为什么需要超时保护？calculate_math 使用 eval() 执行用户输入的表达式。如果模型传了 "while True: pass"，没有超时保护会卡死整个训练进程。

def execute_tool(name, args):
    fn = MOCK_RESULTS.get(name)
    if not fn: return None        # 工具不存在
    try:
        signal.alarm(1)           # 1秒超时保护
        return fn(args)           # 执行工具
    except:
        return None               # 出错就返回None
    finally:
        signal.alarm(0)           # 取消超时

执行管线的完整流程：模型输出 → parse_tool_calls() 提取调用 → execute_tool() 执行 → 结果以 role='tool' 注入上下文 → 模型继续生成。参数校验（CHECK_ARGS）不在执行时使用，而是在奖励计算阶段判断调用是否合法。

Part 4: 让对话动起来

Agent 的核心循环——生成、调工具、拿结果、继续生成。

普通 RL 一次生成就够了，但 Agent 可能需要多轮：先查天气，再查汇率，最后综合回答。这一节是 Agent RL 最核心的部分——多轮交互循环的实现。理解了 rollout_single 的流程和 response_mask 的设计，后面所有训练逻辑都是在这个基础上搭建的。

  • 多轮交互设计：rollout_single 实现"思考-行动"循环——每轮重新渲染完整上下文、模型生成、解析工具调用、执行并注入结果
  • response_mask：Agent RL 与普通 RL 最核心的架构差异。mask=1 表示模型生成的 token（参与梯度），mask=0 表示工具结果（不参与梯度）
  • 批量生成 rollout_batch：每个样本生成 num_generations 次，必须深拷贝 messages 防止数据污染

多轮交互设计

为什么需要多轮？普通 RL 只需生成一次回答。但 Agent 可能需要多轮交互——先查天气，再查汇率，最后综合回答。rollout_single() 就是实现这个"思考-行动"循环的核心函数。

response_mask

批量生成

rollout_batch() 对每个样本生成 num_generations 次（默认 4 次），用于后续的优势计算。一个关键细节：

必须深拷贝 messages：rollout_single() 会修改 messages 列表（追加 assistant 和 tool 消息）。每次生成都必须深拷贝，否则第 2 次生成会从第 1 次的状态开始，导致数据污染。

def rollout_batch(rollout_engine, tokenizer,
        messages_batch, tools_batch, num_gen, ...):
    for messages, tools in zip(messages_batch, tools_batch):
        for _ in range(num_gen):

Part 5: 奖励计算

Agent RL 的奖励信号比普通 RL 更复杂——工具对齐、GT 匹配、标签格式、完成度。

普通 RL 只需要 RM 打分就行，Agent RL 则需要回答一连串问题：工具调对了没？参数传对了没？最终答案对不对？标签格式规范吗？模型是不是磨蹭到 max_turns 还没回答完？这一节拆解 Agent RL 的多层奖励设计——核心原则是"结果正确 > 过程正确 > 格式规范"。

  • 奖励设计理念：GT 匹配分（0~+2.5，权重最高）> 工具对齐分（过程指标）> 标签格式惩罚（基础规范）> 未完成惩罚（效率信号）> 重复惩罚（质量底线）
  • 计算流程：有工具调用和无工具调用走两条分支，最终总分 clip 到 [-3.0, +3.0] 保证训练稳定
  • 标签格式与工具对齐：标签不闭合扣分；合法调用数与 GT 期望数的差距决定过程分
  • GT 匹配与数值实例：支持文本子串匹配和数值近似匹配，通过成功/失败两个场景理解奖励叠加

奖励设计理念

先看全局：为什么要选这些奖励信号？每个信号的设计目的是什么？

奖励信号分值范围为什么需要它
GT 匹配分0 ~ +2.5终极目标：答对了才算好。权重最高，因为过程再正确，答错也不行
工具对齐分+0.5 或 -0.5*gap过程指标：调了几个工具？合法吗？与 GT 期望的数量一致吗？
标签格式惩罚-0.5 * N基础规范：标签不闭合说明模型还没学会协议格式
未完成惩罚-0.5效率信号：达到 max_turns 还没给出最终回答，说明规划能力不足
重复惩罚0 ~ -0.5质量底线：防止模型生成"天气很好天气很好天气很好"
总分 Clip[-3.0, +3.0]稳定性保障：防止极端值导致训练不稳定

核心思想：结果正确（GT 匹配）> 过程正确（工具对齐）> 格式规范（标签闭合）。下面逐项展开。

计算流程

奖励计算分两条路径：有工具调用和无工具调用。无工具时走普通 RL 奖励逻辑（长度分 + RM 打分）；有工具时走 Agent 专用逻辑（工具对齐 + GT 匹配）。

格式与对齐

标签格式惩罚

无论是否有工具调用，都检查 <tool_call> 标签是否成对：

reward -= 0.5 * sum(
  abs(turn.count('

不闭合就扣 0.5 分/对。教会模型：调用工具，标签必须完整。

工具对齐分

衡量"合法调用数"与"GT 期望数"的差距：

# 合法 = 工具名有效 + 参数通过校验
valid = sum(1 for call in tool_calls
  if name in valid_names
  and CHECK_ARGS[name](args))
gap = abs(valid - len(gt)) + \
  max(0, len(tool_calls) - valid)
reward += 0.5 if gap == 0 \
  else -0.5 * gap

GT 期望 1 个调用，模型调了 3 个（1 合法）→ gap=2，扣 1.0 分。

GT 匹配分

为什么权重最高？工具对齐只是过程指标——调对了工具但答错了，依然不该得高分。GT 匹配直接衡量最终效果。最高 +2.5 分。

# 最终回答 = 最后一次 tool_call 之后的内容
final_text = answer.split('

validate_gt_in_text() 支持两种匹配模式：

模式适用场景示例
文本子串匹配天气、翻译等文本 GTGT="晴"，回答含"晴"→匹配
数值近似匹配计算、汇率等数字 GTGT="9472"，回答含 9472→匹配（误差 < 1e-6）

加上未完成惩罚（-0.5）和重复惩罚（3-gram 重复率，上限 0.5），总分 clip 到 [-3, 3]。

成功场景

# 工具对齐：1合法 vs 1个GT → gap=0 → +0.5
# GT匹配：9472在回答中 → +2.5
# 重复惩罚：无 → 0
# 未完成：False → 0

total = 0 + 0.5 + 2.5 + 0 + 0 = 3.0

失败场景

# 标签格式：缺少闭合标签 → -0.5
# 工具对齐：调2次(1合法) vs 1个GT
#   gap = |1-1| + max(0,2-1) = 1 → -0.5
# GT匹配：回答里没9472 → 0
# 重复惩罚：轻微重复 → -0.1
# 未完成：True → -0.5

total = -0.5-0.5+0-0.1-0.5 = -1.6

Part 6: 从单轮到多轮

Agent RL 训练与普通 GRPO 有什么关键差异？

前面五节铺垫了 Agent 的所有组件——工具、解析、多轮循环、奖励。这一节把它们串起来，看 Agent RL 的完整训练流程。核心是理解它与普通 GRPO 的三大差异：多轮 rollout（上下文动态增长）、工具感知奖励（不只是 RM 打分）、mask 区分来源（工具结果不参与梯度）。

  • 对比普通 RL：生成方式从一次性变为多轮交互、上下文从固定变为动态增长、训练目标从"生成好回答"变为"何时调用、调哪个、怎么用结果"
  • 训练数据格式：JSONL 包含 conversations、tools、gt 三个字段，messages[:-1] 去掉最后一条让模型自己生成
  • 训练循环四阶段：多轮 Rollout → 工具感知奖励计算 → 组内标准化优势 → CISPO 策略更新（completion_mask 精确控制梯度）

对比普通 RL

训练循环

rl_train_epoch() 一个 batch 的处理分四个阶段。与普通 GRPO 相比，核心差异在 Phase 1（多轮 Rollout）和 Phase 2（工具感知奖励）：

# Phase 1: 多轮 Rollout（与GRPO的最大区别）
with torch.no_grad():
    results = rollout_batch(
        rollout_engine, tokenizer, messages_batch,
        tools_batch, num_generations=4, max_turns=3)

# Phase 2: 工具感知奖励（不只是RM打分）
rewards = calculate_rewards(
    prompts, completions, gt_batch, tools_batch,
    num_generations, reward_model)

# Phase 3: 优势计算（与GRPO相同：组内标准化）
advantages = (rewards - mean) / (std + 1e-4)

# Phase 4: CISPO策略更新（与GRPO类似）
# 用 completion_mask 只更新模型生成的 token
# mask=0的工具结果 token 被排除在 loss 之外

CISPO 与 PPO 的区别：PPO 用 clamp(ratio, 1-eps, 1+eps) 限制更新幅度，CISPO 只限制上界 clamp(ratio, max=epsilon_high)，允许策略自由下降但限制上升幅度，训练更稳定。

精确控制梯度

为什么 completion_mask 这么重要？多轮 Rollout 生成的序列很长，包含 prompt、模型生成、工具结果、padding。训练时必须精确控制：只有模型自己生成的、EOS 之前的 token 参与 loss 计算。

# 构建流程：
# 1. response_mask 标记: mask=1(模型生成), mask=0(工具结果)
# 2. 找到 EOS 位置，mask 掉 EOS 之后的 token
# 3. 最终：completion_mask = response_mask ∩ (位置<=EOS)

# 效果：只有绿色部分参与梯度
# [prompt(0) | Turn1生成(1) | 工具结果(0) | Turn2生成(1) | ... ]

此外，超长序列会从右侧截断（保留最近的 token，通常是最终回答部分）。所有序列 pad 到 batch 内最大长度后组成 batch 张量。

扩展注意

工具描述要清晰

模型的工具选择依赖 description 字段。描述越精确，模型越容易学会何时调用。比如"搜索网页"比"搜索引擎"更好。

参数类型要准确

parameters 中的 type 字段影响模型的参数格式。数字用 number，字符串用 string。错误类型会导致模型传参失败。

MOCK 数据要合理

模拟数据应该覆盖典型用例。如果 MOCK 数据太简单，模型可能学到的是"记住答案"而非"学会调用工具"。

gt 字段要精确

gt 列表中的值会在最终回答中被精确匹配（数值用浮点近似，文本用子串）。确保 gt 值在回答中的表述方式一致。

常见错误诊断

模型不生成 tool_call

症状：模型总是直接回答，从不调用工具。

原因：SFT 阶段没见过工具调用格式的数据，或 tokenizer 的 chat_template 不支持 tools 参数。

解决：确保 agent_rl.jsonl 中 system 消息包含 tools 字段。检查 tokenizer 的 chat_template 是否正确处理 tools。

tool_call 格式错误

症状：生成了 tool_call 标签但 JSON 解析失败。

原因：模型没学会正确的 JSON 格式，比如少了引号或括号。

解决：检查 parse_tool_calls() 的正则是否能匹配模型输出。增加 SFT 数据中的工具调用示例。

unfinished 惩罚过高

症状：奖励一直是负数，频繁触发 max_turns。

原因：max_gen_len 太小，模型没空间生成最终回答。

解决：增大 max_gen_len（默认 768）或减小 max_turns（默认 3）。

更多排错

奖励不收敛

症状：训练多 epoch，奖励值仍剧烈波动。

原因：learning_rate 太大或 num_generations 太少。

解决：降低 learning_rate（默认 3e-7），增大 num_generations（默认 4）来稳定优势估计。

OOM 显存溢出

症状：多轮 Rollout 后显存暴增。

原因：max_total_len（默认 2500）允许的总序列太长。

解决：减小 max_total_len、batch_size 或 max_turns。或用 --accumulation_steps 替代大 batch。

GT 匹配分总是 0

症状：validate_gt_in_text 始终返回空集。

原因：模型调了工具但最终回答没包含 GT 值。或 gt 格式不对。

解决：检查 gt 格式（应为字符串列表，如 ["9472"]）。检查模型能否将工具结果整合进回答。

重复输出严重

症状：模型反复输出相同内容。

原因：rep_penalty 不够，或模型太小无法同时处理多轮上下文。

解决：降低 temperature（rollout 中默认 0.8），增大 thinking_ratio 让模型"先想后说"。

一句话总结

Agent RL 的本质，就是教模型学会三件事：什么时候该用工具、用哪个工具、怎么用工具的结果来回答问题。

不是让它背下所有答案，而是教它学会利用工具来解决问题。面对新问题、新工具，也能举一反三。
