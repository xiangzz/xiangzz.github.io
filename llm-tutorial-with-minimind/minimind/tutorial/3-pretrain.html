Part 1: 核心思想

理解预训练的本质：Next Token Prediction。这是所有自回归语言模型的统一训练目标。

在写任何训练代码之前，我们必须先想清楚一个问题：语言模型到底在"学"什么？答案出人意料地简单——预测下一个 token。不管是 GPT-4 还是 MiniMind，训练目标都是同一个：给模型一段文字，让它猜下一个字是什么。这一部分的目标就是把这个核心思想吃透，理解"一次前向传播 = 所有位置同时在学习"这个关键洞察。

  • Next Token Prediction —— 预测下一个字，自回归语言模型唯一的训练目标
  • 滑动预测全景 —— 一次前向传播中，序列的每个位置都在同时练习预测下一个 token
  • 输入与目标对齐 —— logits[:-1] 和 labels[1:] 的 shift 操作，确保预测和目标一一对应
  • 对齐代码溯源 —— 回到模型代码中找到 shift 操作的具体实现，打通理论和代码

预测下一个字

模型的任务：给定前面的字，预测下一个字

定义：Next Token Prediction——给定一个 token 序列，模型对每个位置输出一个概率分布，预测下一个 token 是什么。

已知内容（输入）要预测的下一个字
今天
今天天
今天天气
今天天气真
今天天气真好

白话：就像手机输入法的"联想输入"——你打了"今天天"，它猜下一个字是"气"。但模型要同时在整个序列的每个位置做这件事。

模型并不是一次只看一个字。它同时处理整个序列，对每个位置都做一次"预测下一个字"的练习。一次前向传播 = N 次预测练习。

关键洞察：序列长度为 N 时，一次前向传播产生 N-1 个训练信号。这就是 Transformer 高效的原因。

这里用"婴儿学说话"的比喻只是帮你建立直观。在计算机内部，它实际上是矩阵乘法 + softmax，对词表中每个 token 计算概率。

输入与目标对齐

logits 取前 N-1 个，labels 取后 N-1 个，逐位比较

输入:  [你,  好,  世,  界]    (input_ids)
预测:  [好', 世', 界', ?' ]   (logits)
       取 [:-1] ↑  ↑  ↑
标签:  [好,  世,  界,  ! ]    (labels)
              取 [1:] ↑  ↑  ↑

交叉熵 = 比较每个位置的预测与真实值

白话：模型看了"你"，要预测"好"；看了"你好"，要预测"世"。关键操作是——

操作含义
logits[..., :-1, :]去掉最后一个位置的预测（没有对应标签）
labels[..., 1:]去掉第一个位置的标签（不需要预测它）

这不就是上一章 MiniMindForCausalLM.forward 里的 shift 操作吗？没错——模型架构已经写好了预测逻辑，现在要做的是：喂数据、算损失、更新参数。

对齐代码溯源

回顾模型 forward 中的 shift 操作

# model_minimind.py 中的 forward 方法（简化）
def forward(self, input_ids, labels=None):
    # 1. 词嵌入 + 位置编码
    x = self.model(input_ids)
    # 2. Transformer 层
    x = self.lm_head(x)           # (batch, seq_len, vocab_size)

    if labels is not None:
        # 3. 关键：移位对齐
        loss = F.cross_entropy(
            x.view(-1, x.size(-1))[..., :-1, :],
            labels.view(-1)[..., 1:]
        )
        return CausalLMOutput(loss=loss, logits=x)

三步走：

  1. 定义：shift 操作让预测和标签错位对齐。
  2. 白话：就像批改作业——第 i 个位置的学生答案（logits[i]）对第 i+1 个位置的标准答案（labels[i+1]）。
  3. 代码：logits[..., :-1, :] 与 labels[..., 1:] 逐位计算交叉熵。

数据集类源码

PretrainDataset：把原始文本变成训练样本

class PretrainDataset(Dataset):
    def __init__(self, data_path, tokenizer, max_length=512):
        super().__init__()
        self.tokenizer = tokenizer
        self.max_length = max_length
        # 用 HuggingFace load_dataset 加载 JSONL 文件
        self.samples = load_dataset('json', data_files=data_path, split='train')

    def __len__(self):
        return len(self.samples)

    def __getitem__(self, index):
        sample = self.samples[index]
        # 第1步：分词，留2个位置给 BOS 和 EOS
        tokens = self.tokenizer(str(sample['text']),
            add_special_tokens=False,
            max_length=self.max_length - 2,
            truncation=True).input_ids
        # 第2步：加 BOS（开头）和 EOS（结尾）
        tokens = [self.tokenizer.bos_token_id] + tokens + [self.tokenizer.eos_token_id]
        # 第3步：PAD 填充到固定长度
        input_ids = tokens + [self.tokenizer.pad_token_id] * (self.max_length - len(tokens))
        input_ids = torch.tensor(input_ids, dtype=torch.long)
        # 第4步：labels = input_ids 的副本，PAD 位置设为 -100
        labels = input_ids.clone()
        labels[input_ids == self.tokenizer.pad_token_id] = -100
        return input_ids, labels

每一步的目的：

  1. 分词：文字→数字，模型只认数字。
  2. 加 BOS/EOS：告诉模型"从这开始"和"到这结束"。
  3. PAD 填充：凑齐固定长度，方便组成 batch。
  4. labels 中 PAD→-100：让损失函数忽略填充部分。

① 原始文本"你好"从 JSONL 中取出
② 分词后[456, 789]tokenizer 把文字变成数字
③ 加特殊标记[1, 456, 789, 2]BOS=1 开头, EOS=2 结尾

为什么 PAD 设为 -100？PyTorch 的 cross_entropy 函数默认 ignore_index=-100。所有 label 为 -100 的位置不参与损失计算。这样模型就不会在填充内容上浪费学习。

为什么是 -100？

深入理解 ignore_index 机制

# PyTorch 源码中 cross_entropy 的核心逻辑（简化）
def cross_entropy(input, target, ignore_index=-100):
    loss = 0
    count = 0
    for i in range(len(target)):
        if target[i] == ignore_index:
            continue    # 直接跳过，不计入损失
        loss += -log(softmax(input[i])[target[i]])
        count += 1
    return loss / count  # 只对有效位置求平均
位置input_idslabels是否计入损失
01 (BOS)1是
1456456是
2789789是
32 (EOS)2是
40 (PAD)-100否
50 (PAD)-100否

如果不设 -100，模型会努力预测填充位置也是 0，浪费大量学习能力在无意义的数据上。这个机制确保模型只从真实文本中学习。

max_length 取舍

max_length 影响显存和训练效果

max_length显存占用训练信号适用场景
256低短文本足够快速实验
340（默认）中等平衡MiniMind 默认
512高长文本更好显存充裕时
1024很高完整长文SFT 阶段常用

MiniMind 默认 max_seq_len=340。中文约 1 token ≈ 1.5~1.7 个字符，340 token 约覆盖 500+ 字的段落。

分词时留 2 个位置！代码中 max_length=self.max_length - 2，因为还要塞进 BOS 和 EOS。如果忘记减 2，最终序列会超长。

train_pretrain.py 中的 train_epoch 函数

def train_epoch(epoch, loader, iters, start_step=0, wandb=None):
    start_time = time.time()
    last_step = start_step
    for step, (input_ids, labels) in enumerate(loader, start=start_step + 1):
        input_ids = input_ids.to(args.device)
        labels = labels.to(args.device)
        last_step = step

        # ① 计算当前学习率（余弦调度）
        lr = get_lr(epoch * iters + step, args.epochs * iters, args.learning_rate)
        for param_group in optimizer.param_groups:
            param_group['lr'] = lr

        # ② 前向传播（混合精度）
        with autocast_ctx:
            res = model(input_ids, labels=labels)
            loss = res.loss + res.aux_loss       # 主损失 + MoE 辅助损失
            loss = loss / args.accumulation_steps # 梯度累积：除以累积步数

        # ③ 反向传播
        scaler.scale(loss).backward()

        # ④ 每隔 accumulation_steps 步才真正更新参数
        if step % args.accumulation_steps == 0:
            scaler.unscale_(optimizer)
            torch.nn.utils.clip_grad_norm_(model.parameters(), args.grad_clip)
            scaler.step(optimizer)
            scaler.update()
            optimizer.zero_grad(set_to_none=True)

        # ⑤ 日志记录
        if step % args.log_interval == 0 or step == iters:
            spend_time = time.time() - start_time
            current_loss = loss.item() * args.accumulation_steps
            Logger(f'Epoch:[{epoch+1}/{args.epochs}]({step}/{iters}), '
                   f'loss:{current_loss:.4f}, lr:{lr:.8f}')

        # ⑥ 定期保存检查点
        if (step % args.save_interval == 0 or step == iters) and is_main_process():
            model.eval()
            # ... 保存逻辑 ...
            model.train()

余弦学习率

来自 trainer_utils.py 的 get_lr 函数

定义：学习率按余弦曲线从初始值平滑衰减到终值。

def get_lr(current_step, total_steps, lr):
    """余弦学习率调度"""
    return lr * (0.1 + 0.45 * (1 + math.cos(math.pi * current_step / total_steps)))

白话：学习率就像开车——起步时速度适中，中间平稳行驶，快到终点时慢慢减速。最低不会降到 0（保留 10%），让模型始终有微调能力。

训练进度current_step / total_stepscos 值学习率
开始01.0lr × 1.0 = base_lr
中间0.50.0lr × 0.55
结束1.0-1.0lr × 0.1 = 最低学习率

这个比喻只是为了帮你建立直观感受。在计算机内部，它实际上是余弦学习率调度，使用 math.cos 函数根据当前步数和总步数计算衰减系数。

为什么不直接用固定学习率？固定学习率到后期会"震荡"——参数在一个点附近来回跳动，无法收敛到最优。余弦衰减让后期步子变小，精调参数。

梯度累积

小显存也能享受大批量的好处

想用 batch_size=256 训练，但显卡只够放 batch_size=32？

梯度累积：每次只放 32 条数据，但累积 8 次梯度（32 × 8 = 256），等效于 batch_size=256。

# 关键代码（train_pretrain.py）
loss = loss / args.accumulation_steps  # ① loss 除以累积步数
scaler.scale(loss).backward()          # ② 反向传播（梯度自动累加）

if step % args.accumulation_steps == 0:  # ③ 每 8 步才更新一次
    scaler.step(optimizer)
    optimizer.zero_grad(set_to_none=True)
loss / accumulation_steps 很关键！不除的话，累积 8 次梯度就是 8 倍大，等效学习率变成 8 倍，训练会炸。这一行代码是初学者最容易遗漏的。

累积机制详解

梯度在内存中是如何一步步叠加的

图：梯度累积机制

【AI 生图提示词】请生成一张中文技术示意图，风格简洁、配色柔和、适合教学： - 画面主体：上方"理想"大方块(红色虚线框"显存不够")；下方"梯度累积"8个小batch方块(绿色)→累加器漏斗→等效大方块 - 8个小batch编号①-⑧汇入累加器 - 累加器旁标注"loss ÷ 8 再backward" - 底部显示等效结果：32 × 8 = 256 等效 batch - 配色建议：浅灰背景，理想方块红色虚线，小方块绿色，累加器橙色，输出蓝色 - 画面比例：16:9 - 避免：过度装饰、3D 效果

Step操作梯度状态
1forward + backwardgrad += grad_1
2forward + backwardgrad += grad_2
.........
8forward + backward + updategrad += grad_8 → 更新 → 清零

PyTorch 的 backward() 默认行为是累加梯度，不是覆盖。所以只有调用 zero_grad() 时才清零。

混合精度训练

用更少的内存跑更大的模型

定义：混合精度 = 用低精度（16bit）做前向和反向，用高精度（32bit）维护参数主副本。

精度类型占用速度数值范围需 GradScaler
float32高（4字节）慢±3.4e38不需要
float16低（2字节）快±6.5e4需要
bfloat16低（2字节）快±3.4e38不需要

               else torch.cuda.amp.autocast(dtype=dtype)
# GradScaler 仅 float16 需要（bfloat16 范围够大，不需要）
scaler = torch.cuda.amp.GradScaler(enabled=(args.dtype == 'float16'))

三种精度对比

bfloat16 为什么是最佳选择？

图：三种浮点精度格式的内存布局

【AI 生图提示词】请生成一张中文技术示意图，风格简洁、配色柔和、适合教学： - 画面主体：三行对比。float32:"1位符号|8位指数|23位尾数"(32位)；float16:"1位符号|5位指数|10位尾数"(16位)；bfloat16:"1位符号|8位指数|7位尾数"(16位) - float32和bfloat16指数位同色(都是8位，蓝色)，float16指数位红色(只有5位) - 标注：float32"±3.4e38，4字节"；float16"±6.5e4，需GradScaler"；bfloat16"±3.4e38，无需Scaler" - 底部结论框："bfloat16 = float16 的内存 + float32 的范围" - 配色建议：白色背景，符号位灰色，指数位蓝色或红色，尾数绿色 - 画面比例：16:9 - 避免：过度装饰、3D 效果

白话：float16 的"量程"太小（±6.5万），稍大的梯度就溢出了，需要 GradScaler 帮忙。bfloat16 和 float32 一样大（±3.4e38），但只要一半内存。MiniMind 默认用 bfloat16。

一句话记忆：bfloat16 = float16 的内存占用 + float32 的数值范围。能选 bfloat16 就选它。

GradScaler

float16 的"保镖"——防止梯度下溢

# GradScaler 的工作流程
# 1. 放大 loss，防止小梯度在 float16 下变成 0
scaler.scale(loss).backward()

# 2. 缩放回来，检查有没有 inf/nan
scaler.unscale_(optimizer)

# 3. 如果正常，更新参数；如果有 inf/nan，跳过这步
scaler.step(optimizer)

# 4. 调整缩放因子
scaler.update()

bfloat16 因为范围够大，不需要这个保镖。所以 MiniMind 的代码中 enabled=(args.dtype == 'float16')——只在 float16 时启用。

如果你用的是老旧 GPU（如 GTX 1080），它不支持 bfloat16，只能选 float16。这时 GradScaler 是必需的，不能关。

梯度裁剪

防止梯度爆炸的"限速器"

# train_pretrain.py 第 43 行
torch.nn.utils.clip_grad_norm_(model.parameters(), args.grad_clip)
# grad_clip 默认 1.0
# 如果所有参数梯度范数 > 1.0，就等比例缩小到 1.0

三步走：

  1. 定义：计算所有参数梯度的 L2 范数，超过阈值则等比缩放。
  2. 白话：给梯度设上限，就像汽车限速——不管多着急，最快 120。遇到"特别难"的数据时，梯度可能突然爆炸，裁剪防住它。
  3. 代码：clip_grad_norm_(params, max_norm=1.0)，超过 1.0 就缩到 1.0。

这个比喻只是为了帮你建立直观感受。在计算机内部，梯度裁剪实际上是计算所有参数梯度向量的 L2 范数，除以 max_norm 得到缩放系数。

裁剪位置很关键——必须在 unscale_ 之后、step 之前。因为要先还原真实梯度大小，才能正确判断是否超阈值。

尾部残余梯度

train_epoch 末尾的兜底处理

# train_epoch 函数的末尾（第 74-79 行）
if last_step > start_step and last_step % args.accumulation_steps != 0:
    # 如果 epoch 结束时还有未更新的残余梯度
    scaler.unscale_(optimizer)
    torch.nn.utils.clip_grad_norm_(model.parameters(), args.grad_clip)
    scaler.step(optimizer)
    scaler.update()
    optimizer.zero_grad(set_to_none=True)

假设 accumulation_steps=8，epoch 在 step=45 结束。45 % 8 = 5，还剩 5 步累积的梯度没有更新。

这一段代码确保不浪费任何梯度。否则每个 epoch 末尾最多会丢失 7 步的梯度信息，训练数据利用率降低。

for epoch in range(start_epoch, args.epochs):
    train_sampler and train_sampler.set_epoch(epoch)
    setup_seed(42 + epoch)
    indices = torch.randperm(len(train_ds)).tolist()

    # 关键：断点续训时跳过已训练的 batch

        train_sampler or indices, args.batch_size, skip
    )
    loader = DataLoader(train_ds, batch_sampler=batch_sampler,
                        num_workers=args.num_workers, pin_memory=True)

    if skip > 0:
        Logger(f'跳过前{skip}个step，从step {skip+1}开始')
    train_epoch(epoch, loader, len(loader) + skip, skip, wandb)

# ⑨ 清理分布进程
if dist.is_initialized():
    dist.destroy_process_group()

SkipBatchSampler 是断点续训的关键——它跳过已经训练过的 batch，直接从断点处继续。不用它的话，恢复后会重复训练已见过的数据。

工程基础设施

检查点续训与多卡训练——这里先建立直觉，深度留给阶段 11

检查点（lm_checkpoint）

训练的"存档"机制。保存两类文件：pretrain_768.pth（纯权重，用于推理）和 pretrain_768_resume.pth（权重+优化器+epoch/step，用于断点续训）。配合 SkipBatchSampler，中断后能从断点无缝继续。

分布式（init_distributed_mode）

多卡并行训练。每张 GPU 处理不同数据切片，算出梯度后用 All-Reduce 取平均，再用相同梯度更新。4 张卡接近 4 倍速。DistributedSampler 自动分片，无需手动切。

原子保存

保存时先写 .tmp 临时文件，再用 os.replace 原子替换。即使保存中途断电，文件要么是旧的要么是新的，不会出现损坏的半成品。

OOM 与显存

CUDA Out of Memory

症状：RuntimeError: CUDA out of memory

原因：batch 太大或序列太长，显存放不下。

修复（按优先级）：

  1. 减小 batch_size（32→16→8）
  2. 减小 max_seq_len（340→256→128）
  3. 增大 accumulation_steps 补偿 batch

显存占用估算

粗略公式：

显存 ≈ 模型参数 × 4 (float32)
     或 模型参数 × 2 (bfloat16)
     + batch_size × seq_len × hidden × 4

MiniMind-768 约 64M 参数，float32 时约 256MB。加上梯度和优化器状态，总共约 1-1.3GB。非常省显存。

Loss 异常诊断

Loss 不下降

症状：训练几百步 loss 没变化

排查清单：

  1. 学习率是否太小？（试试 1e-3）
  2. 数据量是否太少？（至少需要上万条）
  3. 数据质量是否太差？（大量乱码、重复）
  4. 模型结构是否正确？（检查 config）

Loss 突然飙升

症状：loss 正常下降后突然变大

排查清单：

  1. 学习率是否太大？（试试 1e-4）
  2. 是否有异常数据？（空行、超长行）
  3. 梯度裁剪是否生效？（检查 grad_clip）
  4. 从最近的检查点重新开始

NaN 与恢复异常

Loss 变成 NaN

症状：训练几步后 loss 突然变成 NaN。

原因：学习率过高导致梯度爆炸，或混合精度下数值溢出。

修复：

  1. 降低学习率（5e-4 → 1e-4）
  2. 确认梯度裁剪生效
  3. 使用 bfloat16 而非 float16
  4. 检查数据是否有极端值

恢复训练后异常

症状：--from_resume 1 后 loss 跳到很大。

修复：

  1. 确认 resume 文件完整（大小合理？）
  2. 检查 optimizer 和 scaler 是否都恢复了
  3. 确认恢复前后模型配置一致
  4. 确认学习率调度器步数正确
NaN 是致命的！一旦出现 NaN，后续所有计算都是 NaN。唯一的办法是从最近的检查点重新开始，并降低学习率。
