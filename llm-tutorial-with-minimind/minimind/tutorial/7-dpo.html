Part 1：为何对齐

SFT 让模型"会说话"，但"说好话"是另一个维度的问题。这一节我们理解对齐的动机。

SFT 训练出来的模型能回答问题、能听懂指令，看起来已经很不错了。但它缺乏一个关键能力：区分回答的好坏。同一个问题，它可能给出一个精心组织的回答，也可能敷衍了事。这一节我们要搞清楚：为什么 SFT 还不够，以及"对齐"到底要解决什么问题。

  • 训练三阶段 —— 预训练、SFT、对齐分别干什么，DPO 处于哪个阶段
  • SFT 的局限 —— 行为克隆能学会格式，却无法区分回答质量
  • 有害输出问题 —— 未对齐的模型可能产生有害、偏见、不一致的内容
  • 对齐的定义 —— 让模型输出与人类偏好保持一致

对齐的核心思想：给模型看"好回答"和"差回答"，让它学会区分并偏好好的。DPO 是目前最简洁高效的对齐方法。

SFT 的局限

SFT 教会模型"模仿标准答案"。但现实世界中，同一个问题存在多种回答方式，有好有坏。

SFT 能做到SFT 做不到
学会回答问题的格式区分回答的质量好坏
学会基本的对话能力避免有害、偏见、不一致的输出
记住训练数据中的知识在多种合理回答中偏好更好的那个
SFT 本质上是"行为克隆"。模型学会了说话的方式，却没有价值观来判断什么该说什么不该说。

Part 2：RLHF→DPO

DPO 之前，业界标准方案是 RLHF。理解 RLHF 的痛点，才能体会 DPO 的精妙。

在 DPO 出现之前，对齐的业界标准是 RLHF（基于人类反馈的强化学习）。它效果不错，但代价很高：需要 4 个模型同时跑，训练不稳定，显存爆炸。DPO 的核心洞察是——与其先训练一个评委再让评委指导选手，不如直接告诉选手哪个好哪个差。

  • RLHF 三步流程 —— SFT → 训练奖励模型 → PPO 强化学习，复杂度层层叠加
  • RLHF 的痛点 —— 4 个模型、训练不稳定、显存爆炸、奖励黑客问题
  • DPO 的核心思想 —— 砍掉奖励模型和强化学习，直接用偏好数据优化策略模型
  • RLHF vs DPO 对比 —— 模型数量、训练稳定性、实现复杂度的全面比较

RLHF 的痛点

痛点说明
复杂度高需要 4 个模型：SFT、奖励、Critic、Reference
训练不稳定PPO 对超参极其敏感，调参如炼丹

DPO 一句话核心

定义

DPO（Direct Preference Optimization）：与其训练一个奖励模型来打分、再用强化学习去优化策略，不如直接用偏好数据一步到位优化策略模型本身。

白话

RLHF 是"先培养一个评委，再让评委打分指导选手"。DPO 是"直接告诉选手哪个好哪个差，让选手自己悟"。

Part 3：数据

DPO 的核心输入是"成对偏好数据"。理解数据的结构，是理解一切的基础。

DPO 不需要奖励模型，但它需要高质量的偏好数据。每一组数据都是一个三元组：同一个问题、一个好回答（chosen）、一个差回答（rejected）。本节从数据格式到编码流程，完整拆解偏好数据是怎么从 JSONL 文件变成训练张量的。

  • 成对偏好数据 —— 同一问题配一个好回答和一个差回答，差异体现在质量而非长度
  • JSONL 格式与三条铁律 —— chosen 和 rejected 的用户提问必须完全相同
  • DPODataset 编码流程 —— 从 chat_template 到 tokenizer 编码再到张量构建
  • 损失掩码 —— 只在 assistant 回答部分计算损失，用户提问部分不参与优化
  • 数据流全览 —— 从 JSONL 到 6 个训练张量的完整转换链路

数据加载与编码的核心流程

class DPODataset(Dataset):
    def __init__(self, file_path, tokenizer, max_length=4096):
        super().__init__()
        self.tokenizer = tokenizer
        self.max_length = max_length
        self.padding = tokenizer.pad_token_id if tokenizer.pad_token_id is not None else 0
        self.bos_id = tokenizer(f'{tokenizer.bos_token}assistant\n',
                                add_special_tokens=False).input_ids
        self.eos_id = tokenizer(f'{tokenizer.eos_token}\n',
                                add_special_tokens=False).input_ids
        self.samples = load_dataset('json', data_files=file_path, split='train')

bos_id 和 eos_id 是模型回答的边界标记。DPO 只对模型回答部分计算损失，这两个标记就是定位边界的"标尺"。

数据编码流程

__getitem__ 将偏好数据转为训练张量

def __getitem__(self, index):
    sample = self.samples[index]
    chosen = sample['chosen']      # 好回答的对话列表
    rejected = sample['rejected']  # 差回答的对话列表

    # 用 chat_template 将对话列表转为文本
    chosen_prompt = self.tokenizer.apply_chat_template(
        chosen, tokenize=False, add_generation_prompt=False)
    rejected_prompt = self.tokenizer.apply_chat_template(
        rejected, tokenize=False, add_generation_prompt=False)

    # 编码 + 截断 + padding
    chosen_encoding = self.tokenizer(
        chosen_prompt, truncation=True, max_length=self.max_length, padding='max_length')
    rejected_encoding = self.tokenizer(
        rejected_prompt, truncation=True, max_length=self.max_length, padding='max_length')

    chosen_input_ids = chosen_encoding['input_ids']
    rejected_input_ids = rejected_encoding['input_ids']

损失掩码生成

只在 assistant 回答部分计算损失

def generate_loss_mask(self, input_ids):
    loss_mask = [0] * len(input_ids)
    i = 0
    while i < len(input_ids):
        # 找到 assistant 回答的开头标记
        if input_ids[i:i + len(self.bos_id)] == self.bos_id:
            start = i + len(self.bos_id)
            end = start
            # 找到回答的结尾标记 eos_id
            while end < len(input_ids):
                if input_ids[end:end + len(self.eos_id)] == self.eos_id:
                    break
                end += 1
            # bos 和 eos 之间的位置标记为 1
            for j in range(start, min(end + len(self.eos_id), self.max_length)):
                loss_mask[j] = 1
            i = end + len(self.eos_id) if end < len(input_ids) else len(input_ids)
        else:
            i += 1
    return loss_mask

Part 4：数学

DPO 背后有一套优雅的数学。理解公式，才能正确调参和排错。

DPO 不是拍脑袋想出来的，它有扎实的数学基础。从 Bradley-Terry 偏好模型出发，到 RLHF 的闭式解，再到最终的 DPO 损失公式，每一步都有清晰的推导。本节把这些数学拆成你能消化的层次，重点理解公式每个符号在代码中的对应。

  • Bradley-Terry 模型 —— 偏好建模的概率基础，好差回答之间的奖励差决定偏好概率
  • 从 RLHF 到 DPO 的推导 —— 优化问题存在闭式解，用概率比替代奖励模型
  • DPO 损失公式 —— log-sigmoid 结构，策略偏好与参考偏好的差值驱动优化
  • logits_to_log_probs —— 将原始 logits 转为真实 token 的 log 概率，DPO 比较的基础
  • dpo_loss 实现 —— 四步对应公式四层：掩码求和、拆分 batch、计算比值、log-sigmoid

BT 模型

DPO 的理论根基

假设人类对回答 y_w（好）和 y_l（差）的偏好服从 Bradley-Terry 模型：

定义

P(y_w > y_l | x) = sigmoid(r(x, y_w) - r(x, y_l))

其中 r(x, y) 是某个隐含的"奖励函数"，表示回答 y 在问题 x 下的好坏程度。

白话

好回答和差回答之间的"奖励差"越大，人类偏好好回答的概率就越高。如果奖励相同，偏好概率恰好是 50%。

RLHF→DPO

DPO 的关键数学洞察

RLHF 的优化目标：最大化奖励，同时约束不偏离参考模型：

max E[r(x,y)] - beta * KL[pi || pi_ref]

DPO 论文的核心贡献：这个优化问题存在闭式解。奖励函数可以用策略模型和参考模型的概率比来表示：

r(x, y) = beta * log(pi(y|x) / pi_ref(y|x)) + beta * log Z(x)

其中 Z(x) 是配分函数，在 chosen/rejected 对比中会消掉。

不必完全理解这个推导。关键是：DPO 用概率比替代了奖励模型，绕过了强化学习。

DPO 损失公式

L = -log(sigmoid(beta * (log pi(y_w|x) - log pi(y_l|x) - log pi_ref(y_w|x) + log pi_ref(y_l|x))))

符号含义白话
y_wchosen（好回答）人类标注的优质回答
y_lrejected（差回答）人类标注的劣质回答
pi当前策略模型正在被训练的模型
pi_ref参考模型冻结的 SFT 模型
beta温度参数控制偏离惩罚力度

logits 转概率

logits_to_log_probs 的作用

定义：将模型输出的 logits 转为每个位置上"真实 token"的 log 概率。

白话：模型给词汇表中每个词打了个分（logits）。这个函数问：对那个实际出现的词，模型打了多少分？

假设词汇表有 5 个词 ["我", "你", "他", "她", "它"]：

# 模型在某个位置输出的 log 概率：
# [-1.2, -0.3, -2.1, -3.5, -4.0]
#               ^^^^
# 实际下一个 token 是 "你" (index=1)
# 所以该位置的 log_prob = -0.3

logits→概率

模型输出的是 6400 维的原始分数，我们需要把它变成每个 token 的对数概率

这一步很关键：DPO 要比较"策略模型给 chosen 多少分"和"参考模型给 chosen 多少分"。但模型输出的是原始 logits，不是概率。

转换分三步：先 softmax 归一化 → 再取 log → 最后用 gather 按 label 索引挑出真实 token 对应的值。

log_probs = F.log_softmax(logits, dim=2)  # 归一化 + 取 log
log_probs_per_token = torch.gather(        # 按 label 挑出真实 token
    log_probs, dim=2, index=labels.unsqueeze(2)
).squeeze(-1)
return log_probs_per_token  # (batch, seq_len)

这个函数同时用于策略模型和参考模型。DPO 的核心比较就建立在这两组值上。

dpo_loss

DPO 损失函数的完整实现

def dpo_loss(ref_log_probs, policy_log_probs, mask, beta):
    # 应用掩码，只对 assistant 回答部分求和
    ref_log_probs = (ref_log_probs * mask).sum(dim=1)
    policy_log_probs = (policy_log_probs * mask).sum(dim=1)

    batch_size = ref_log_probs.shape[0]
    # 前 N 条是 chosen，后 N 条是 rejected
    chosen_ref = ref_log_probs[:batch_size // 2]
    reject_ref = ref_log_probs[batch_size // 2:]
    chosen_policy = policy_log_probs[:batch_size // 2]
    reject_policy = policy_log_probs[batch_size // 2:]

    # 核心公式：与数学公式一一对应
    pi_logratios = chosen_policy - reject_policy      # log pi(y_w) - log pi(y_l)
    ref_logratios = chosen_ref - reject_ref            # log ref(y_w) - log ref(y_l)
    logits = pi_logratios - ref_logratios              # 两者的差
    loss = -F.logsigmoid(beta * logits)                # -log(sigmoid(beta * logits))
    return loss.mean()

逐步拆解

四步对应公式的四个层次

步骤代码含义
1. 掩码求和(log_probs * mask).sum(dim=1)只累加 assistant 回答部分
2. 拆分 batch[:batch_size//2] vs [batch_size//2:]前半 chosen，后半 rejected
3. 计算比值pi_logratios - ref_logratios策略偏好 vs 参考偏好
4. 最终损失-F.logsigmoid(beta * logits)log-sigmoid 变换

-log(sigmoid(z)) 的性质：当 z 很大时趋近 0（好），当 z 为 0 时等于 0.693（基线），当 z 很小时趋近 |z|（惩罚）。

避免对 chosen 和 rejected 分别做两次前向传播。拼接后一次推理，节省约一半的计算时间。

Part 5：参考模型

DPO 需要两个模型。参考模型是理解 DPO 的关键之一。

蒸馏需要教师和学生两个模型，DPO 也需要策略模型和参考模型两个模型。参考模型是 SFT 模型的一个冻结副本，它的作用是充当"锚点"——防止策略模型在优化偏好的过程中走偏，退化成什么都不说。理解参考模型的角色，才能真正理解 DPO 损失在做什么。

  • 为什么需要参考模型 —— 充当安全绳，防止模型走捷径降低所有概率来"作弊"
  • 没有 ref 会怎样 —— 模型可能退化到输出空回复或乱码
  • 双模型初始化 —— 策略模型和参考模型从完全相同的 SFT 权重初始化，参考模型立刻冻结
  • GPU 显存分析 —— 参考模型省了梯度和优化器状态，MiniMind 双模型约 100MB 完全可接受

为什么需要 ref

定义：参考模型是 SFT 模型的一个冻结副本，充当"锚点"，约束策略模型不能偏离太远。

白话：没有参考模型，模型可能发现一条捷径——把所有回答的概率都降低，rejected 降得更多。结果？模型学会了"什么都不说"。

参考模型就像一根安全绳。它保证模型只在已有能力上微调偏好，不会偏离到生成空回复或乱码的地步。

卸甲条款：上面的"安全绳"比喻只是帮助你建立直觉。在代码层面，参考模型是一个冻结了参数的模型副本，在 DPO 损失函数中提供基准的对数概率分布，数学上等价于 KL 散度约束项。

def train_epoch(epoch, loader, iters, ref_model, lm_config,
                start_step=0, wandb=None, beta=0.1):
    for step, batch in enumerate(loader, start=start_step + 1):
        # 1. 取出 chosen 和 rejected 数据，移到 GPU
        x_chosen = batch['x_chosen'].to(args.device)
        x_rejected = batch['x_rejected'].to(args.device)
        y_chosen = batch['y_chosen'].to(args.device)
        y_rejected = batch['y_rejected'].to(args.device)
        mask_chosen = batch['mask_chosen'].to(args.device)
        mask_rejected = batch['mask_rejected'].to(args.device)

        # 2. 沿 batch 维度拼接，一次前向传播搞定
        x = torch.cat([x_chosen, x_rejected], dim=0)
        y = torch.cat([y_chosen, y_rejected], dim=0)
        mask = torch.cat([mask_chosen, mask_rejected], dim=0)

损失与反向传播

前向计算和梯度更新的完整流程

        # 3. 动态学习率调整
        lr = get_lr(epoch * iters + step, args.epochs * iters,
                    args.learning_rate)
        for param_group in optimizer.param_groups:
            param_group['lr'] = lr

        with autocast_ctx:
            # 参考模型前向：不计算梯度
            with torch.no_grad():
                ref_outputs = ref_model(x)
            ref_log_probs = logits_to_log_probs(ref_outputs.logits, y)

            # 策略模型前向：计算梯度
            outputs = model(x)
            policy_log_probs = logits_to_log_probs(outputs.logits, y)

            # 计算 DPO 损失 + MoE 辅助损失
            dpo_loss_val = dpo_loss(ref_log_probs, policy_log_probs,
                                    mask, beta=beta)
            loss = dpo_loss_val + outputs.aux_loss
            loss = loss / args.accumulation_steps

        # 4. 梯度累积 + 裁剪 + 更新
        scaler.scale(loss).backward()
        if step % args.accumulation_steps == 0:
            scaler.unscale_(optimizer)
            torch.nn.utils.clip_grad_norm_(model.parameters(), args.grad_clip)
            scaler.step(optimizer)
            scaler.update()
            optimizer.zero_grad(set_to_none=True)

                0, wandb, args.beta)

学习率为何极低

默认 4e-8，比 SFT 的 1e-5 小约 1000 倍

原因一：防止遗忘

DPO 基于 SFT 模型微调。学习率太大会破坏 SFT 阶段学到的能力。模型会"忘记"怎么好好说话。

原因二：精细调整

DPO 不是教新知识，而是微调偏好方向。只需微小的参数变化，就能改变对 chosen/rejected 的偏好倾向。

原因三：DPO 梯度更敏感

DPO 损失涉及两个模型的概率差值。微小的参数变化会放大为较大的概率变化，所以需要更小的学习率。

如果学习率超过 5e-8，模型可能快速退化。表现为：输出变短、重复、甚至完全无法生成有意义的回答。

梯度累积与精度

梯度累积

accumulation_steps 控制梯度累积步数。等效 batch size = batch_size * accumulation_steps。

# 不增加显存，模拟大 batch
if step % args.accumulation_steps == 0:
    scaler.step(optimizer)
    optimizer.zero_grad()

显存不足时，增大 accumulation_steps 而非减小 batch_size。

混合精度

默认使用 bfloat16，节省显存并加速训练。

dtype = torch.bfloat16 if args.dtype == "bfloat16" else torch.float16
autocast_ctx = torch.cuda.amp.autocast(dtype=dtype)

双模型场景下，混合精度几乎是必须的——它能节省约 50% 的参数显存。

准备 DPO 数据

错误诊断一

loss 不下降

可能原因：学习率太小、beta 太大、chosen 和 rejected 差异太小。

排查：打印 pi_logratios 和 ref_logratios。如果几乎相同，说明模型没有区分能力。尝试增大学习率到 2e-8 或减小 beta。

loss 突然爆炸

可能原因：学习率太大，或 chosen/rejected 数据质量差（标注反了）。

排查：检查数据中是否有 chosen 比 rejected 更差的情况。减小学习率到 1e-8。

训练后模型变傻

可能原因：灾难性遗忘——学习率太大或训练轮数太多。

排查：降低学习率到 1e-8，减少 epoch 数，增大 beta 约束偏离。

错误诊断二

CUDA OOM

原因：双模型占用约 2 倍显存。

解决：减小 batch_size，增大 accumulation_steps，使用 --dtype bfloat16，或减小 max_seq_len。

ref_model 输出异常

原因：忘记 ref_model.eval() 或 requires_grad_(False)。

解决：确认参考模型处于 eval 模式且不计算梯度。否则 BatchNorm/Dropout 行为异常。

loss 始终约 0.693

原因：-log(sigmoid(0)) = log(2) = 0.693。logits 全为 0，策略模型和参考模型完全相同。

解决：检查模型加载是否正确，确认 from_weight 路径指向有效的 SFT 权重。如果模型没有被训练过，策略和参考完全一致。

错误诊断三

loss 出现 NaN

原因：log_probs 中出现极小值，导致数值溢出。或者 chosen/rejected 的 token 序列完全相同。

解决：检查数据中 chosen 和 rejected 是否完全相同。确保使用混合精度训练。

显存占用异常大

原因：没有及时释放中间变量。

解决：源码末尾有 del 语句清理不需要的张量。确保没有额外保留对中间结果的引用。

# train_epoch 末尾的清理代码
del x_chosen, x_rejected, y_chosen, y_rejected, mask_chosen, mask_rejected
del ref_outputs, ref_logits, ref_log_probs, outputs, logits, policy_log_probs
