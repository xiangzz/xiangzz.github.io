模型加载

支持两种权重格式：原生 torch 和 HuggingFace transformers

def init_model(args):
    tokenizer = AutoTokenizer.from_pretrained(args.load_from)
    if 'model' in args.load_from:
        # 路径1：原生 MiniMind 格式（.pth 权重）
        model = MiniMindForCausalLM(MiniMindConfig(...))
        model.load_state_dict(torch.load(ckp, map_location=args.device))
        if args.lora_weight != 'None':
            apply_lora(model)  # 可选：加载 LoRA 旁路
            load_lora(model, lora_path)
    else:
        # 路径2：HuggingFace transformers 格式
        model = AutoModelForCausalLM.from_pretrained(args.load_from)
    return model.half().eval().to(args.device), tokenizer

两条路径的区别：路径 1 直接加载 MiniMind 原生权重（.pth），路径 2 加载转换后的 HuggingFace 格式。后者可以用 vLLM 等推理加速框架。

控制模型"怎么说"的三个旋钮

参数默认值作用调大调小
temperature0.85控制随机性更发散、有创意更确定、保守
top_p0.95核采样阈值候选词更多只保留高概率词
max_new_tokens8192最大生成长度回答更长回答更短

这是上一章 MiniMindForCausalLM.generate() 中讲过的 Temperature、Top-P 采样的实际应用。temperature=0 表示贪心解码（每次选概率最高的词）。

@app.post("/v1/chat/completions")
async def chat_completions(request: ChatRequest):
    messages = request.messages
    # 应用聊天模板
    inputs = tokenizer.apply_chat_template(messages, return_tensors="pt")
    if request.stream:
        # 流式输出
        return StreamingResponse(generate_stream(inputs, request),
                                 media_type="text/event-stream")
    else:
        # 同步输出
        outputs = model.generate(inputs, max_new_tokens=request.max_tokens)
        return format_response(outputs, request)

流式输出

逐 Token 推送，不用等完整回答生成

定义：Server-Sent Events（SSE）是一种服务器向客户端单向推送的技术。每生成一个 Token 就立即推送，用户看到"打字机"效果。

说白了，就像微信语音转文字——不用等整段话说完，一边说一边出字。

这个比喻只是为了帮你建立直观感受。在计算机内部，SSE 是一种 HTTP 长连接协议，服务器通过 data: 前缀逐行发送文本块，浏览器用 EventSource API 接收。

class CustomStreamer(TextStreamer):
    def __init__(self, tokenizer, queue):
        super().__init__(tokenizer)
        self.queue = queue

    def on_finalized_text(self, text, stream_end=False):
        # 每生成一个 token，推入队列
        self.queue.put(text)
        if stream_end:
            self.queue.put(None)  # 发送结束信号

兼容 OpenAI 的 data: {...} 格式

data: {"id":"chatcmpl-1","object":"chat.completion.chunk",

客户端用 OpenAI SDK 可以直接消费：

from openai import OpenAI

Part 4：转换

让 MiniMind 模型兼容更广泛的生态系统。

原生 .pth 权重只能用 MiniMind 代码加载——不能用 vLLM 加速、不能上传 HuggingFace Hub。转换成 transformers 格式后，你的模型就进入了整个 HuggingFace 生态。这一节讲解两种转换路径、Qwen3 架构兼容原理，以及 LoRA 合并转换的完整流程。

  • 为什么需要转换：原生 .pth 只能 MiniMind 代码加载，Transformers 格式可用 vLLM/SGLang 加速、可上传 HuggingFace Hub
  • 两种转换方式：转为 Qwen3 兼容格式（推荐，可用 vLLM）或保留 MiniMind 格式（兼容 transformers 库）
  • Qwen3 兼容原理：MiniMind 架构与 Qwen3 高度相似——RMSNorm、RoPE、GQA、SwiGLU 全部一致，转换后可直接用 vLLM 获 5-10 倍加速
  • LoRA 合并转换：先合并 LoRA 到基础模型，再转格式，两步搞定

原生 .pth 权重只能用 MiniMind 代码加载

原生格式

  • 不能使用 vLLM 加速
  • 不能使用 HuggingFace Hub
  • 适合：学习和实验

Transformers 格式

  • 可用 HuggingFace 生态加载

Part 5：高性能

转换成 Qwen3 格式后，用 vLLM / SGLang 把吞吐量拉满。

前面 Part 4 把 MiniMind 权重转成了 Qwen3 兼容格式——这不是为了好玩，而是为了借用成熟的推理引擎。vLLM 和 SGLang 这类引擎原生支持 Qwen3 架构，能提供 PagedAttention、连续批处理（continuous batching）、前缀缓存等优化，把单卡吞吐量提升一个数量级。MiniMind 自带的 FastAPI 服务适合学习和调试，真正要扛并发、压性能时，就该切换到这些引擎。

  • vLLM 启动实战 —— 一条命令把转换后的模型变成 OpenAI 兼容的高吞吐服务
  • FastAPI 生产部署 —— 多 worker 并发、超时控制、稳定性
  • 性能对比 —— 原生 PyTorch vs vLLM，什么场景该用哪个

vLLM 启动实战

转换成 Qwen3 格式后，一条命令起高吞吐服务

vLLM 不认识 MiniMind 的私有架构，但它认识 Qwen3。上一节 convert_torch2transformers 把权重转成 Qwen3Config 结构后，vLLM 就能直接加载。

# 1. 安装 vLLM（需要 CUDA 环境）
$ pip install vllm

# 2. 一条命令启动 OpenAI 兼容服务
$ python -m vllm.entrypoints.openai.api_server \
    --model ./transformers_minimind_768/ \
    --served-model-name minimind \
    --dtype bfloat16 \
    --max-model-len 2048 \
    --port 8000

# 3. 用同样的 chat_api.py 调用（接口完全兼容）
$ python scripts/chat_api.py

vLLM 默认开启了几个关键优化：PagedAttention（把 KV-Cache 像虚拟内存一样分页管理，减少显存碎片）、连续批处理（新请求随时插入正在处理的 batch，不必等整批完成）、前缀缓存（相同 system prompt 只算一次）。这就是它比原生 PyTorch 快的原因。

吞吐量对比

原生 PyTorch vs vLLM，差在哪

方案并发能力吞吐量（相对）显存效率适用场景
MiniMind FastAPI单进程串行1×低（KV-Cache 预分配）学习、调试、低并发
vLLM / SGLang连续批处理10×~20×高（PagedAttention）生产、高并发、压性能
不要盲目上 vLLM：MiniMind 只有 64M 参数，模型本身极小。在单用户场景下，原生 PyTorch 的延迟反而可能更低（少了引擎开销）。vLLM 的优势在高并发——当同时有几十个请求涌入时，连续批处理才能体现价值。自己玩用 FastAPI，要扛流量再上 vLLM。

深度边界：SGLang 是另一个高性能引擎，优势在复杂提示词结构（多轮、分支）的编译优化。MiniMind 的 rollout_engine.py（阶段 8 RL 训练用）已经集成了 SGLang 客户端，这里不再展开。

FastAPI 并发

不用 vLLM 时，怎么让自带服务扛住多请求

MiniMind 自带的 serve_openai_api.py 默认单进程运行，同一时刻只处理一个请求。要扛并发，用 uvicorn 的多 worker 模式：

# 单 worker（默认，适合调试）
$ python scripts/serve_openai_api.py

# 多 worker 并发（生产部署）
$ uvicorn scripts.serve_openai_api:app \
    --host 0.0.0.0 --port 8000 \
    --workers 4

# 配合 gunicorn 更稳定（Linux）
$ gunicorn scripts.serve_openai_api:app \
    -w 4 -k uvicorn.workers.UvicornWorker \
    --bind 0.0.0.0:8000

每个 worker 是独立进程，各加载一份模型。worker 数量建议等于 GPU 数（每卡一个 worker），或等于 CPU 核数（纯 CPU 推理时）。注意：4 个 worker = 4 倍显存，64M 模型还好，大模型要谨慎。

流式输出的坑：多 worker 模式下，负载均衡器（如 nginx）必须关闭缓冲（proxy_buffering off），否则 SSE 流会被攒成一坨再返回，失去"逐字输出"的效果。

Part 6：排错

部署中常见的问题。

部署阶段的问题通常不是算法问题，而是工程配置问题——显存不够、权重不匹配、API 返回空、精度丢失。这一节把最常见的坑列出来，给你排查思路。最后两个动手练习帮你熟悉 API 调用和采样参数调优。

  • 常见错误诊断：CUDA OOM（确认 .half()、减小 max_new_tokens、用 CPU）、输出乱码（权重与配置不匹配）、API 响应为空（EOS token 问题）、转换后效果变差（精度损失）
  • 动手练习：启动 API 并用 curl 调用观察 JSON 格式；对比不同 temperature 下的回答差异（0.1 vs 1.5）

常见错误诊断

CUDA Out of Memory

症状：推理时报显存不足

修复：① 确认用了 .half()；② 减小 max_new_tokens；③ 用 CPU 推理 --device cpu

输出乱码

症状：生成结果是随机字符

原因：权重文件与模型配置不匹配

修复：确认 hidden_size、num_layers、use_moe 参数与训练时一致

API 响应为空

症状：curl 返回空内容

原因：模型没有正确生成 EOS token

修复：检查 tokenizer 的 eos_token_id 是否正确

转换后效果变差

症状：转换后推理结果与原始不同

原因：精度损失（float32→float16）

修复：用 float16 而非 bfloat16 转换，或验证权重是否完整
