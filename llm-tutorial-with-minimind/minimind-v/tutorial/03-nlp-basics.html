自然语言处理基础

第三阶段 · 理解文本如何变成数字输入给模型

本章知识地图

本章解决一个核心问题：人类写的文字（中文、英文、混合了图片的文本），怎么变成神经网络能处理的数字矩阵？整条链路分为六步，每一步都不可或缺。

  • 分词（Tokenization） —— 把连续文本切成有意义的单元（Token），再用 BPE 算法控制词表大小
  • 词嵌入（Embedding） —— 把整数编号变成高维向量，让语义相似的词在空间中靠近
  • 对话模板（Chat Template） —— 用特殊标记区分 system / user / assistant 三种角色
  • 标签生成 —— 只训练 assistant 部分，用 -100 屏蔽其他位置
  • 下一个词预测 —— GPT 的核心训练目标，用 Shift 技巧高效实现
  • 数据格式 —— Parquet 列式存储，把图文数据打包成一体化文件

3.1 计算机如何理解文字

计算机只认识数字（0 和 1），不认识文字。所以第一步是把文字"翻译"成数字。整个翻译链路是：文本 → 分词 → Token ID → 嵌入向量 → 送入 Transformer。

  • 文本到数字的桥梁 —— 从原始字符串到高维向量，每一步的目的和原理
  • 为什么不用现成的 Unicode —— Unicode 是编号系统，不携带语义信息

为何不用 Unicode

你可能会想：每个汉字在计算机里本来就有一个数字编号（Unicode），为什么不直接用这个编号？

"猫" 的 Unicode: 29483
"狗" 的 Unicode: 29399
"汽车" 的 Unicode: 27773, 36710

问题：
- "猫"和"狗"在 Unicode 中差 84，没有语义关系
- 但在语义上它们非常相似（都是动物）
- 我们需要一种编码让"猫"和"狗"在向量空间中距离很近

Unicode 编码只是一个编号系统，相邻编号之间没有语义关联。"猫"是 29483，"狗"是 29399，差了 84——但它们的语义几乎一样。而"猫"和"帽子"的 Unicode 差距可能更小，但语义完全不同。

我们需要一种表示方法，让语义相似的词在数学空间中也"距离相近"——这就是词嵌入的核心动机。好的词嵌入中，"猫"和"狗"的向量应该非常接近，而"猫"和"汽车"的向量应该很远。

3.2 分词

文本处理的第一步：把连续的文本切成一个个有意义的单元，然后给每个单元分配一个整数编号。

  • 三种分词策略 —— 字符级、词级、子词级（BPE），各有优劣
  • BPE 算法详解 —— MiniMind-V 的选择，在词表大小和序列长度之间取平衡
  • 特殊 Token 与图片占位符 —— 控制对话结构的标记和图片的编码方式

三种分词策略对比

以"我喜欢猫"为例，三种策略的切分结果和优缺点截然不同：

字符级分词

['我', '喜', '欢', '猫'] → 4 个 Token

优点：词表极小（几千个字符），永远不会有"未知词"。

缺点：每个 Token 没有语义（"喜"和"欢"分开看意思不完整），序列太长导致模型难以学习。

词级分词

['我', '喜欢', '猫'] → 3 个 Token

优点：每个 Token 有完整语义，序列短。

缺点：词表巨大（几十万甚至上百万），遇到新词直接 OOV（Out of Vocabulary，无法编码）。

BPE（子词级分词） 在两者之间取平衡：['我', '喜欢', '猫'] → 3 个 Token。常见词保持完整（序列短），罕见词自动拆成已知片段（词表小）。MiniMind-V 选择了 BPE，词表大小 6400。

BPE 算法的迭代过程

MiniMind-V 使用 BPE 分词。核心思想：反复合并最常见的相邻字符对

图：BPE 算法迭代合并流程

【AI 生图提示词】请生成一张中文技术示意图，风格简洁、配色柔和、适合教学： - 画面主体：一个带循环的流程图，展示 BPE 算法的迭代过程 - 流程步骤：初始所有字符都是单独的 token（词表={我,喜,欢,猫,狗,...}）→ 统计所有相邻字符对的频率 → 合并最频繁的字符对（如"喜"+"欢"→"喜欢"）→ 更新词表 → 还有常见组合？→ 是则回到统计步骤，否则输出最终词表（6400个 token） - 关键标注：循环箭头用橙色强调，最终节点标注"6400 个 token" - 配色建议：浅灰背景，普通步骤浅蓝色，判断节点橙色菱形 - 画面比例：16:9 - 避免：过度装饰、3D 效果、杂乱的颜色

BPE 的工作方式就像搭积木：先把所有文本拆成单个字符（最小积木块），然后统计哪些字符对最常一起出现，把它们"粘"成一个新的积木块。反复迭代，直到词表增长到目标大小。

BPE 具体例子：逐步合并

以语料 ["低 低", "低 低", "最 最", "最 最 最"] 为例，观察每轮如何找到最高频对并合并：

初始语料: ["低 低", "低 低", "最 最", "最 最 最"]

第1轮: "低"+"低" 最频繁 → 合并为 "低低"
  语料: ["低低", "低低", "最 最", "最 最 最"]

第2轮: "最"+"最" 最频繁 → 合并为 "最最"
  语料: ["低低", "低低", "最最", "最最 最"]

第3轮: "最最"+"最" 最频繁 → 合并为 "最最最"
  语料: ["低低", "低低", "最最", "最最最"]

每一轮都找到出现最频繁的相邻 Token 对，将它们合并为一个新的 Token。合并后重新统计频率，再找下一个最高频对，反复迭代直到词表增长到目标大小。

MiniMind-V 的词表最终增长到 6400 个 Token，存储在 model/tokenizer.json 中。分词器的配置信息（如 BOS/EOS Token 的 ID）则存储在 model/tokenizer_config.json 中。

特殊 Token

除了文本 Token，MiniMind-V 还定义了几个特殊 Token 来控制对话结构和多模态输入。它们不对应任何自然语言文本，而是模型理解对话格式的"标点符号"。

Token角色说明
<|im_start|>对话开始标记标记一段对话消息的开始，后面跟着角色名
<|im_end|>对话结束标记标记一段对话消息的结束
<|image_pad|>图片占位符 (ID: 12)每张图片用 64 个连续的占位符表示
<bos>句子开始 (ID: 1)标记句子的开头
<eos>句子结束 (ID: 2)标记句子的结尾

图片占位符机制——每张图片用 64 个 <|image_pad|> 表示：

原始文本: "<image>\n请描述这张图片"
替换后:   "<|image_pad|><|image_pad|>...(×64)\n请描述这张图片"

为什么要 64 个？因为 SigLIP2 视觉编码器把 256×256 的图片切成小块（patch）——SigLIP2 的 patch 大小是 32×32 像素，所以横向 256/32=8 块、纵向也是 8 块，共 8×8=64 个 patch。每个 patch 产生一个视觉 Token，总共 64 个。图片编码器的输出正好是 64 个向量，对应这 64 个占位符。

如果你以后查 SigLIP 文档看到 patch_size=32，就是这个意思——它决定了 64 这个数字的来源。

常见坑：成对出现的对话标记

<|im_start|> 和 <|im_end|> 必须成对出现。少了任意一个，模型会把多段对话当成一整段混乱文本，训练时 loss 不降、生成时胡言乱语。第 7 章读源码时你会看到 generate_labels() 专门用循环去匹配这对标记。

另一个容易误解的点：这里的"开始/结束"是逐段消息的标记，不是整段对话只有一个。每一句 system/user/assistant 都要各包一对。

3.3 词嵌入

Token ID 只是一个整数编号，没有语义信息。嵌入层（Embedding）把每个 ID 映射为一个高维向量，让语义相似的词在向量空间中距离相近。

  • 从 Token ID 到向量 —— 通过查表操作，把整数变成有语义的浮点向量
  • One-hot vs 词嵌入 —— 为什么稀疏的 one-hot 编码不好，稠密向量好
  • nn.Embedding 实战 —— PyTorch 中如何创建和使用嵌入层
  • 权重共享 —— 输入端和输出端共用同一个矩阵，减少参数量

One-hot vs 词嵌入

Token ID 本身只是一个编号（比如"猫"是 29483），模型不能直接对编号做运算。我们有两种方式把它变成向量：

One-hot 编码（不好）

'猫' → [0, 0, 0, ..., 1, ..., 0, 0]

6400 维的向量，只有 1 个位置是 1，其余全是 0。问题：

  • 极其稀疏，浪费空间
  • 任意两个词的距离完全相同（都是 √2），没有任何语义信息
  • 矩阵太大（6400 维），后续计算代价高

词嵌入（好）

'猫' → [0.23, -0.15, 0.89, ..., 0.12]（768 维）

每个位置都有值，向量之间的距离反映语义相似度：

  • '猫' 和 '狗' 的向量非常接近（都是动物）
  • '猫' 和 '汽车' 的向量完全不同
  • 维度低（768 vs 6400），计算高效

PyTorch 嵌入层

嵌入层的本质就是一张查找表（Look-up Table）：用 Token ID 当行号，取出对应的向量。

# PyTorch 中的嵌入层
import torch.nn as nn

# 创建嵌入层：6400 个 token，每个 768 维
embedding = nn.Embedding(num_embeddings=6400, embedding_dim=768)

# 查表：把 token ID 转为向量
token_ids = torch.tensor([234, 567, 12])   # 3 个 token ID
vectors = embedding(token_ids)              # 形状: [3, 768]
# vectors[0] = token 234 的 768 维向量
# vectors[1] = token 567 的 768 维向量
# vectors[2] = token 12 (<|image_pad|>) 的 768 维向量

在 MiniMind-V 中：model_minimind.py 第 201 行创建了嵌入层：

self.embed_tokens = nn.Embedding(config.vocab_size, config.hidden_size)
# = nn.Embedding(6400, 768)  → 一个 6400 行 × 768 列的查找表

这个矩阵有 6400 × 768 = 4,915,200 个参数，是模型中可训练的权重之一。训练过程中，这些向量会不断调整，让语义相似的 Token 靠近、语义不同的 Token 远离。

权重共享

MiniMind-V 使用了一个巧妙的设计：嵌入矩阵和输出层共享同一个权重矩阵。输入端用它把 Token ID 变成向量，输出端用它把向量映射回词表概率。

3.4 对话模板

光把文本切成 Token 还不够，模型还需要知道一段对话里"谁说了什么"。对话模板就是一套格式规则，用特殊标记把不同角色的内容包起来。

  • ChatML 格式 —— 用 <|im_start|> 和 <|im_end|> 标记每一段对话的角色和内容
  • 对话数据处理流程 —— 从原始对话数据到结构化文本的完整管线
  • 多轮对话格式 —— 多个 user/assistant 轮次的拼接方式

ChatML 格式详解

MiniMind-V 使用 ChatML 格式。每一条对话消息都用 <|im_start|> 开始、<|im_end|> 结束，开始标记后面跟着角色名。三种角色分别是 system（系统指令）、user（用户输入）、assistant（模型回复）。

<|im_start|>system
你是一个知识丰富的AI，尽力为用户提供准确的信息。<|im_end|>
<|im_start|>user
<|image_pad|><|image_pad|>...(×64)
请描述这张图中的主要物体和场景。<|im_end|>
<|im_start|>assistant
这张图片展示了...<|im_end|>

通用模板格式：<|im_start|>{role}\n{content}<|im_end|>\n。角色名告诉模型"这段话是谁说的"，内容就是实际的文本。

3.5 标签生成规则

训练语言模型时有一个关键设计：只训练模型生成"assistant"的回复。模型不需要学习如何复制用户的提问或系统指令，只需要学习在给定上下文时如何生成恰当的回答。

  • -100 忽略机制 —— PyTorch 的交叉熵损失函数支持 ignore_index=-100，标签为 -100 的位置不计算损失
  • 标签分配规则 —— system 和 user 部分标记为 -100，assistant 部分标记为真实 Token ID
  • 代码实现 —— generate_labels() 函数的逐行解析

标签分配规则与具体例子

对一段格式化后的对话文本，每个 Token 位置的标签取决于它属于哪个角色：

标签生成函数

下面是标签生成的完整代码，核心逻辑是双循环：外层循环寻找 assistant 段落，内层循环确定段落边界。

def generate_labels(self, input_ids):
    labels = [-100] * len(input_ids)       # 默认全部忽略
    i = 0
    while i < len(input_ids):
        if input_ids[i:i + len(self.bos_id)] == self.bos_id:
            # 找到了 <|im_start|>assistant\n
            start = i + len(self.bos_id)     # assistant 内容的开始
            end = start
            while end < len(input_ids):
                if input_ids[end:end + len(self.eos_id)] == self.eos_id:
                    break                    # 找到了 <|im_end|>
                end += 1
            # 标记 assistant 部分为真实 token
            for j in range(start, min(end + len(self.eos_id), self.max_length)):
                labels[j] = input_ids[j]
            i = end + len(self.eos_id)
        else:
            i += 1
    return labels

关键行解读：

  • labels = [-100] * len(input_ids) —— 初始化全部为 -100，默认所有位置都不计算损失
  • self.bos_id —— 预先存储的 <|im_start|>assistant\n 对应的 Token ID 序列
  • self.eos_id —— <|im_end|> 对应的 Token ID 序列
  • labels[j] = input_ids[j] —— 只有 assistant 部分才会执行这行，把真实 Token ID 作为标签

3.6 预测下一个词

这是所有 GPT 风格语言模型的核心训练目标。给定前面的词，预测下一个词是什么。模型通过反复练习这个任务，逐步学会"理解"语言的规律。

  • 直觉理解 —— 就像写作文时的"填空"，根据上下文预测空格里应该填什么词
  • 训练过程 —— 模型对输入序列的每个位置都预测下一个词
  • Shift 技巧 —— 一次前向传播，同时训练所有位置的预测能力

直觉理解与训练过程

想象你在做一道填空题："这只____"。你的大脑会根据"这只"预测后面可能出现的词——"猫"、"狗"、"鸟"等等。语言模型做的就是同样的事，只不过它给出的是每个候选词的概率。

如果逐位置单独训练，效率太低。Shift 技巧的巧妙之处在于：通过错位对齐，一次前向传播就能同时计算所有位置的损失。

旧方案的问题

50 万个零散的图片文件 + 一个 JSON 索引文件。下载慢（网络延迟 × 50 万次）、读取慢（磁盘 I/O × 50 万次）、磁盘压力大（大量小文件碎片）。

Parquet 的优势

1 个文件包含所有图文数据。体积小（内置压缩）、读取快（列式存储 + 批量读取）、一体化管理（数据和索引合一）。

3.8 总结

分词

BPE 算法在字符级和词级之间取平衡，用 6400 个 Token 覆盖中英文。特殊 Token 控制对话结构，图片用 64 个占位符表示。

词嵌入

nn.Embedding 查表把整数变成 768 维向量，让语义相似的词在空间中靠近。输入端和输出端共享权重，减少参数量。

对话模板

ChatML 格式用 <|im_start|>/<|im_end|> 标记每条消息的角色和边界，让模型区分 system/user/assistant。

标签生成

只训练 assistant 部分。非 assistant 位置标签设为 -100，PyTorch 交叉熵自动忽略这些位置。

下一个词预测

GPT 的核心训练目标。Shift 技巧通过错位对齐，一次前向传播训练所有位置的预测能力。

数据格式

Parquet 列式存储打包图文数据，内置压缩、批量读取、一体化管理。
