环境变量管理

环境用途数据来源

启动时校验环境变量

dotenv + zod —— 少一个变量立刻崩，比线上 500 强

运行时才发现的配置错误代价高昂。用 TypeScript + Zod 在入口文件最前面做一次 schema 校验；缺字段、类型错、端口越界都立刻报错退出。

// src/config/env.ts
import { z } from 'zod';
import dotenv from 'dotenv';

// 开发环境读取 .env；线上由平台注入环境变量，不读文件
if (process.env.NODE_ENV === 'development') {
  dotenv.config({ path: '.env.local' });
}

const envSchema = z.object({
  NODE_ENV: z.enum(['development', 'staging', 'production'])
    .default('development'),
  PORT: z.coerce.number().int().positive().default(3000),
  DATABASE_URL: z.string().url(),
  JWT_SECRET: z.string().min(32, 'secret too short'),
  REDIS_URL: z.string().url().optional(),
  LOG_LEVEL: z.enum(['trace','debug','info','warn','error'])
    .default('info'),
});

const parsed = envSchema.safeParse(process.env);

if (!parsed.success) {
  // 启动时直接失败——比线上 500 好得多
  console.error(
    'Invalid env:\n',
    JSON.stringify(parsed.error.flatten().fieldErrors, null, 2)
  );
  process.exit(1);
}

export const env = parsed.data;

数据库连接池配置

连接数不是越多越好 —— 按 CPU 核数和实例数反推

每个 Node.js 实例与 PostgreSQL 之间维持一个连接池。连接数过少会排队等待；过多则浪费数据库资源甚至被打满。经验公式：pool_size = (CPU核数 * 2) + 有效磁盘数，再除以实例数。

// Prisma schema (prisma/schema.prisma)
        datasource db {
          provider = "postgresql"
          url      = env("DATABASE_URL")
          // 连接池大小通过 URL 参数传递
        }
        
        // .env
        // 单实例 4 核：pool_size=10
        DATABASE_URL="postgresql://user:pass@host:5432/mydb?connection_limit=10&pool_timeout=30"
        
        // 多实例（PM2 cluster 4 workers）：每个 worker 5 个连接
        DATABASE_URL="postgresql://user:pass@host:5432/mydb?connection_limit=5&pool_timeout=30"
# 查看当前 PG 连接数
        $ psql -c "SELECT count(*) FROM pg_stat_activity WHERE datname='mydb';"
        # 查看最大连接数（默认 100）
        $ psql -c "SHOW max_connections;"

日志管理：别再用 console.log

结构化日志 + 分级输出，定位问题快十倍

console.log 输出的是纯文本字符串，grep 不到字段、过滤不了级别、stdout 缓冲还可能丢日志。生产环境推荐 JSON 结构化日志，能被 Loki / ELK / Datadog 直接采集，按 serviceName、level、traceId 聚合查询。

级别使用场景
trace进出函数、极其详细
debug本地排查，线上关闭
info启动完成、关键业务节点
warn降级、重试、可恢复异常
error不可恢复错误，需要介入
 
# .env（示例）
LOG_LEVEL=info          # 生产
LOG_LEVEL=debug         # 本地

Pino：最快的 Node.js 日志库

低开销 + 自带 Express 中间件 pino-http

Pino 把序列化推迟到 Worker 线程，单线程每秒可写数十万条日志。pino-http 自动给每个请求打一条 info 日志（method、url、status、响应时间），并提供绑定当前请求上下文的子 logger。

$ npm install pino pino-http
$ npm install -D pino-pretty     # 开发时用，生产不装
// src/logger.ts
import pino from 'pino';
import { env } from './config/env';

export const logger = pino({
  level: env.LOG_LEVEL,
  // 开发环境：彩色、可读输出；生产环境：JSON 到 stdout
  transport: env.NODE_ENV === 'development'
    ? { target: 'pino-pretty', options: { colorize: true, translateTime: 'HH:SS' } }
    : undefined,
  base: {
    service: 'my-app',
    version: process.env.npm_package_version ?? '0.0.0',
  },
});
// src/index.ts —— 接入 Express 请求日志
import express from 'express';
import pinoHttp from 'pino-http';
import { logger } from './logger';

const app = express();

// 每个请求自动打 info 日志：method / url / status / 耗时
app.use(pinoHttp({ logger }));

app.get('/api/users/:id', async (req, res) => {
  // req.log 是绑定当前请求上下文的子 logger
  req.log.info({ userId: req.params.id }, 'fetching user');
  const user = await getUser(req.params.id);
  res.json(user);
});

Nginx 反向代理

HTTPS、安全头、静态文件一站搞定

# /etc/nginx/sites-available/my-app
upstream nodejs_app {
    server 127.0.0.1:3000;
    keepalive 64;
}

server {
    listen 443 ssl http2;
    server_name myapp.com;

    ssl_certificate /etc/letsencrypt/live/myapp.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/myapp.com/privkey.pem;

    # 安全头
    add_header X-Frame-Options "SAMEORIGIN" always;
    add_header X-Content-Type-Options "nosniff" always;

    # API 反向代理
    location /api/ {
        proxy_pass http://nodejs_app;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    }

    location / {
        proxy_pass http://nodejs_app;
    }
}

零停机部署

pm2 reload 热重载 vs pm2 restart 冷重启

restart 先杀后起，期间所有请求失败；reload 会先启动新 worker，等其 ready 后再优雅关掉旧 worker —— 整个过程服务不中断。前提是应用必须支持优雅关闭（Graceful Shutdown）。

命令行为影响
pm2 restart杀进程再启所有在途请求失败
pm2 reload滚动替换 worker对新请求零影响
pm2 gracefulReload同 reload，走 IPC同上
 
# ecosystem.config.js —— 关键：cluster 模式 + wait_ready
module.exports = {
  apps: [{
    name: 'my-app',
    script: 'dist/index.js',
    instances: 'max',          // 按 CPU 核数起多个 worker
    exec_mode: 'cluster',
    wait_ready: true,          // 等 process.send('ready') 再视为启动完成
    listen_timeout: 8000,      // 8 秒未 ready 视为失败
    kill_timeout: 5000,        // 给旧 worker 5 秒优雅关闭
    max_memory_restart: '500M',
  }],
};


        
        

        

        
优雅关闭（Graceful Shutdown）

        
收到 SIGTERM 后：停止接收新请求 → 处理完在途请求 → 关闭连接 → 退出

        
零停机部署的前提是应用能正确处理 SIGTERM。PM2 reload 发出 SIGTERM 后等待 kill_timeout，超时则强杀。应用必须自己关闭 HTTP server、数据库连接、消息队列消费者。

        
// src/graceful-shutdown.ts
        import { Server } from 'http';
        import { prisma } from './db';
        import { logger } from './logger';
        
        export function setupGracefulShutdown(server: Server) {
          let isShuttingDown = false;
        
          const shutdown = async (signal: string) => {
            if (isShuttingDown) return;
            isShuttingDown = true;
            logger.info({ signal }, 'shutdown initiated');
        
            // 1. 停止接收新请求
            server.close((err) => {
              if (err) logger.error({ err }, 'error closing server');
              else logger.info('http server closed');
            });
        
            // 2. 关闭数据库连接
            await prisma.$disconnect();
            logger.info('database disconnected');
        
            // 3. 通知 PM2 已就绪退出（配合 wait_ready）
            process.exit(0);
          };
        
          process.on('SIGTERM', () => shutdown('SIGTERM'));
          process.on('SIGINT',  () => shutdown('SIGINT'));
        }
        
        // src/index.ts
        import { setupGracefulShutdown } from './graceful-shutdown';
        const server = app.listen(env.PORT, () => {
          logger.info(`listening on :${env.PORT}`);
          process.send?.('ready');   // 通知 PM2：我已就绪
        });
        setupGracefulShutdown(server);

Nginx upstream 滚动更新

多实例场景下，逐台摘流量、更新、加回

当应用跑在多台服务器或同一台多个端口上，Nginx 的 upstream 配合健康检查可以实现逐台滚动更新，比单机 PM2 reload 更可控。

# /etc/nginx/conf.d/upstream.conf
upstream node_backend {
    server 127.0.0.1:3000;
    server 127.0.0.1:3001;
    server 127.0.0.1:3002;
    server 127.0.0.1:3003;
}

server {
    listen 80;
    location / {
        proxy_pass http://node_backend;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_next_upstream error timeout http_502;
    }
}
# 滚动更新单台：先标记 down，更新完再恢复
curl -X POST 'http://nginx-api/servers/3001/down'
pm2 reload my-app --only 3001
sleep 5
curl -X POST 'http://nginx-api/servers/3001/up'

静态资源长期缓存

文件名带 hash，缓存一年也不怕

构建工具（Vite / Webpack / Next.js）会给静态资源生成内容 hash —— 文件内容变了，文件名就变了。这样可以对静态资源设置 Cache-Control: max-age=31536000, immutable，大幅提升二次访问速度。

# 构建产物示例
assets/
  index-a1b2c3d4.js        # 内容变了 → hash 变了 → URL 变了
  vendor-e5f6g7h8.js
  style.i9j0k1l2.css
# Nginx 配置：静态资源长期缓存，HTML 不缓存
server {
    location /assets/ {
        expires 1y;
        add_header Cache-Control "public, immutable";
    }

    location / {
        expires -1;   # HTML 每次都回源
        proxy_pass http://node_backend;
    }
}

故障恢复清单

出问题时按顺序排查，别慌

线上故障第一原则：先恢复，再追因。能回滚就回滚，能重启就重启，保留现场日志留到事后分析。

步骤命令 / 操作目的
1. 确认范围curl -I https://your.app/health全站 or 单接口
2. 看监控Sentry / Grafana / PM2 monit定位异常源
3. 看日志pm2 logs --nostream --lines 200找 stack trace
4. 回滚git revert HEAD && pm2 reload all先恢复
5. 复盘写 postmortem，加告警防止复发
 
# 一键回滚脚本
#!/usr/bin/env bash
set -euo pipefail
echo '⏪ reverting last commit...'
git revert --no-edit HEAD
npm run build
pm2 reload all
revert_exit=$?
if [ $revert_exit -ne 0 ]; then
  echo '❌ reload failed, resetting git...'
  git reset --hard HEAD@{1}
  exit 1
fi
echo '✅ rollback done'

排错：服务挂了

症状：网站突然无法访问，502 Bad Gateway。
原因：Node.js 进程崩溃（内存溢出、未捕获异常）。
修复：PM2 会自动重启。用 pm2 logs 查看崩溃日志，定位原因。常见问题：内存泄漏（重启频率高）、未处理的 Promise rejection。 
$ pm2 logs my-app --lines 100   # 查看最近日志
$ pm2 show my-app                # 查看重启次数
$ pm2 monit                      # 实时监控内存和 CPU
