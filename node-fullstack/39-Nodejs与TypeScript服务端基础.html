Node.js 与 TypeScript

服务端基础——用类型安全的方式写后端

你有没有想过

前端的 JavaScript 代码，能不能直接在服务器上运行？

答案是可以——这就是 Node.js 做的事。

但 JavaScript 是动态类型语言，写大型后端项目时容易出错。所以我们还需要 TypeScript 来给代码加上类型保护。

从这章开始，你将从零搭建一个 TypeScript 版的 Node.js 后端项目。这是后面所有后端章节的基础。

Part 1: 运行时回顾

Node.js 的本质与核心机制

Node.js 不仅是"浏览器外的 JavaScript"，它还有一套强大的内置模块。开始写后端之前，先搞清楚它和浏览器的区别，以及它的单线程模型如何处理并发请求。理解事件循环和异步模式，是写好 Node.js 代码的基石。

浏览器 vs Node

同样的 JS，不同的运行环境

能力浏览器Node.js
DOM 操作有没有
文件系统没有有（fs 模块）
HTTP 服务器没有有（http 模块）
环境变量没有有（process.env）
包管理没有有（npm）

Node.js 没有 DOM，但多了文件系统、网络、进程管理等服务器能力。它使用和 Chrome 相同的 V8 引擎来执行 JavaScript。

事件循环机制

单线程如何同时处理上千个请求？

Node.js 只有一个主线程，但它把耗时操作（读文件、网络请求）交给系统后台处理。主线程继续执行下一段代码，等后台完成后通过回调通知主线程。

事件循环六个阶段（按顺序循环执行）：

timers → pending → idle/prepare → poll → check → close callbacks

  • timers：执行 setTimeout / setInterval 到期的回调
  • poll：获取新 I/O 事件，执行 I/O 相关回调（最常停留的阶段）
  • check：执行 setImmediate 的回调
// 非阻塞：主线程不会停下来等文件读完
import { readFile } from "node:fs/promises";

console.log("1. 开始");
const filePromise = readFile("big.txt", "utf-8");  // 交给后台
console.log("2. 主线程继续执行");

filePromise.then(data => {
    console.log("3. 文件读完了，长度:", data.length);
});
console.log("4. 主线程结束");

输出顺序：1 → 2 → 4 → 3。主线程不会在 readFile 处卡住，这就是非阻塞 I/O。Node 靠这个机制，用一个线程就能服务成千上万的并发连接。

异步模式演进

从回调地狱到 async/await

Callback → Promise → async/await

// 1. 回调（容易嵌套太深）
readFile("a.txt", (err, data) => {
    if (err) throw err;
    console.log(data);
});

// 2. Promise（扁平化）
readFile("a.txt", "utf-8")
    .then(data => console.log(data))
    .catch(err => console.error(err));

// 3. async/await（最推荐）
try {
    const data = await readFile("a.txt", "utf-8");
    console.log(data);
} catch (err) {
    console.error("读文件失败:", err);
}

错误处理三种方式

// try/catch（推荐）
try {
    await riskyOperation();
} catch (e) {
    console.error(e);
}

// .catch() 链式
fetch(url).catch(e => console.error(e));

// 全局兜底（最后防线）
process.on("unhandledRejection",
    (reason) => {
        console.error("未捕获:", reason);
    }
);
// 并发读取三个文件——比串行快三倍
const [a, b, c] = await Promise.all([
    readFile("a.txt", "utf-8"),
    readFile("b.txt", "utf-8"),
    readFile("c.txt", "utf-8"),
]);
// Promise.all：全部成功才成功，一个失败就失败
// Promise.allSettled：等全部完成，不管成败
// Promise.race：谁先完成用谁的结果

核心内置模块

用 node: 前缀导入，这是推荐写法

import fs from "node:fs";                       // 文件系统
import path from "node:path";                   // 路径处理
import http from "node:http";                   // HTTP 服务器
import { EventEmitter } from "node:events";     // 事件
import crypto from "node:crypto";               // 加密
import os from "node:os";                       // 操作系统信息

// 使用 node: 前缀的异步 API
import { readFile } from "node:fs/promises";
const content = await readFile("package.json", "utf-8");
console.log(JSON.parse(content).name);

Node.js 有四个核心特点：单线程事件循环、非阻塞异步 API、npm 生态（世界最大包仓库）、V8 引擎。它特别适合 I/O 密集型应用。

Part 2: 搭建项目

从零创建一个 TS 后端项目

先把项目骨架搭起来。你需要初始化 npm 项目、安装 TypeScript 相关依赖、配置 tsconfig。我们还会对比几种常用的开发工具，帮你选到最趁手的方案。项目结构清晰了，后面的开发才能事半功倍。

初始化 TS 项目

五步创建一个可运行的 TS 后端项目

$ mkdir my-api && cd my-api
$ npm init -y

# 安装 TypeScript 开发依赖
$ npm install -D typescript tsx @types/node

# 安装 Express 及其类型
$ npm install express
$ npm install -D @types/express

# 初始化 tsconfig
$ npx tsc --init

其中 tsx 是一个零配置的 TypeScript 执行器，让你直接运行 .ts 文件，不需要先编译。

推荐目录结构

清晰的分层是项目可维护的前提

src/
├── index.ts          // 入口
├── routes/           // 路由
├── middleware/        // 中间件
├── services/         // 业务逻辑
├── models/           // 数据模型
└── types/            // 类型定义

这就像一栋楼的楼层：入口是门厅，路由是走廊，中间件是安检，业务逻辑是办公室。每层各司其职。

入口文件

五行代码启动一个 Web 服务器

// src/index.ts
import express from "express";

const app = express();
app.use(express.json());

app.get("/health", (_req, res) => {
    res.json({ status: "ok", timestamp: new Date().toISOString() });
});

const PORT = Number(process.env.PORT) || 3000;
app.listen(PORT, () => {
    console.log(`服务器运行在 http://localhost:${PORT}`);
});
$ npx tsx src/index.ts
服务器运行在 http://localhost:3000

$ curl http://localhost:3000/health
{"status":"ok","timestamp":"2025-01-01T00:00:00.000Z"}

Part 3: tsconfig 配置

让 TypeScript 编译器听你的

TypeScript 的编译行为全靠 tsconfig.json 控制。后端项目和前端的配置有显著区别：前端打包用 webpack/vite，后端直接用 tsc 编译。几个关键配置项搞错了，整个项目跑不起来。

tsconfig 要点

后端推荐配置——Node.js 18+ 用 ES2022

{
    "compilerOptions": {
        "target": "ES2022",
        "module": "NodeNext",
        "moduleResolution": "NodeNext",
        "outDir": "./dist",
        "rootDir": "./src",
        "strict": true,
        "esModuleInterop": true,
        "skipLibCheck": true,
        "forceConsistentCasingInFileNames": true,
        "resolveJsonModule": true,
        "declaration": true,
        "sourceMap": true
    },
    "include": ["src/**/*"],
    "exclude": ["node_modules", "dist"]
}
使用 NodeNext 时，需要在 package.json 中设置 "type": "module" 来启用 ESM。如果项目用 CommonJS（require），把 module 改为 "CommonJS"。

Part 4: 模块系统

ESM 与 CommonJS——两种导入导出方式

Node.js 历史上使用 CommonJS（require），后来 JavaScript 标准化了 ESM（import）。新项目推荐用 ESM，但你在老项目和第三方库里会经常看到 CommonJS。搞懂两者区别，遇到报错才不慌。

ESM vs CommonJS

语法对照表——看清差异

ESM（推荐）

// 导出
export const name = "app";
export default function run() {}

// 导入
import fs from "node:fs";
import { readFile } from "node:fs/promises";

// 文件扩展名必须写
import { config } from "./config.js";

CommonJS

// 导出
module.exports = { name: "app" };
exports.run = function() {};

// 导入
const fs = require("node:fs");
const { readFile } = require("node:fs/promises");

// 不需要写扩展名
const { config } = require("./config");

关键区别：ESM 是静态分析（编译时确定依赖），CommonJS 是动态加载（运行时才 require）。ESM 支持 tree-shaking，CommonJS 不支持。新项目推荐用 ESM。

ESM 实践要点

从 CommonJS 迁移到 ESM 要注意的坑

// package.json —— 启用 ESM 的开关
{
    "type": "module"
}
// CommonJS 中可用的 __dirname 和 __filename，在 ESM 中不存在
// 解决方案：
import { fileURLToPath } from "node:url";
import { dirname, join } from "node:path";

const __filename = fileURLToPath(import.meta.url);
const __dirname = dirname(__filename);

// 现在可以正常拼接路径了
const dbPath = join(__dirname, "data", "db.json");

tsconfig 的 moduleResolution：用 "NodeNext" 时，TypeScript 强制要求 ESM 导入带 .js 扩展名（即使源文件是 .ts）。这很反直觉但是正确的。

什么时候用 CommonJS？当你维护的老项目大量使用 require()，或者某个第三方库只提供 CJS 版本且没有 ESM 兼容层时。其他情况都建议用 ESM。

Part 5: 环境变量

敏感信息的"保险箱"

数据库密码、JWT 密钥这些敏感信息，绝不能硬编码在代码里。一旦推到 GitHub，全世界都能看到。环境变量就是解决这个问题的标准方案——配置和代码分离，不同环境用不同的值。

dotenv 入门

一行代码加载 .env 文件到 process.env

$ npm install dotenv
# .env 文件（不要提交到 Git！）
PORT=3000
NODE_ENV=development
DATABASE_URL=postgresql://user:pass@localhost:5432/mydb
JWT_SECRET=your-secret-key
// 在入口文件最顶部加载
import "dotenv/config";  // 自动加载 .env 到 process.env

const port = process.env.PORT; // string | undefined

类型安全配置

用函数封装，启动时就能发现配置缺失

// src/config.ts
function requireEnv(key: string): string {
    const value = process.env[key];
    if (!value) throw new Error(`环境变量 ${key} 未设置`);
    return value;
}

export const config = {
    port: Number(process.env.PORT) || 3000,
    nodeEnv: process.env.NODE_ENV ?? "development",
    databaseUrl: requireEnv("DATABASE_URL"),
    jwtSecret: requireEnv("JWT_SECRET"),
    isDev: process.env.NODE_ENV !== "production",
} as const;
// src/types/env.d.ts —— 让 process.env 有类型提示
declare namespace NodeJS {
    interface ProcessEnv {
        PORT?: string;
        NODE_ENV?: "development" | "production" | "test";
        DATABASE_URL: string;
        JWT_SECRET: string;
    }
}

使用配置

import config 之后，每个字段都有类型提示

import { config } from "./config";

console.log(config.port);        // number —— 有类型提示
console.log(config.databaseUrl); // string —— 启动时已验证
console.log(config.isDev);       // boolean

// 如果 .env 中缺少 DATABASE_URL，启动时会直接报错：
// Error: 环境变量 DATABASE_URL 未设置

这种"启动时校验"的模式叫 fail fast（快速失败）。宁可启动时崩溃，也不要运行到一半才发现配置缺失。

常见问题

遇到红色报错时，先停下来解决，不要硬着头皮往下写。

问题一：npx tsx 提示"命令未找到"

原因：没有安装 tsx，或者没有在项目目录下运行。

修复：执行 npm install -D tsx，确认当前目录有 node_modules。

问题二：import 报错"Cannot use import statement"

原因：package.json 中缺少 "type": "module"，或 tsconfig 的 module 设置不对。

修复：在 package.json 中添加 "type": "module"，确认 tsconfig 的 module 为 NodeNext。

问题三：process.env.XXX 总是 undefined

原因：忘记在入口文件顶部加载 dotenv/config，或 .env 文件不在项目根目录。

修复：确保 import "dotenv/config" 在所有其他 import 之前，且 .env 文件和 package.json 同级。

Part 6: 流式处理

用 Streams 处理大文件和数据

读取一个 2GB 的日志文件，用 readFile 会把整个文件加载到内存，服务器直接崩溃。Stream 的思路是"边读边处理"，每次只加载一小块数据到内存。Node.js 的流是事件循环的最佳搭档。

四种流

Readable、Writable、Transform、Duplex

类型方向典型场景
Readable只读读取文件、HTTP 请求体
Writable只写写入文件、HTTP 响应
Transform读 → 转换 → 写压缩、加密、格式转换
Duplex独立读写TCP socket、双向通信
 
import { createReadStream, createWriteStream } from "node:fs";
import { createGzip } from "node:zlib";
import { pipeline } from "node:stream/promises";

// 用 pipeline 把大文件压缩——内存占用极低
await pipeline(
    createReadStream("access.log"),    // 读取
    createGzip(),                      // 压缩（Transform）
    createWriteStream("access.log.gz") // 写入
);
console.log("压缩完成！内存占用始终很低");

为什么流很重要？处理大文件、实时数据（聊天消息、日志流）、视频转码时，流让你用恒定的小内存完成任务。不用流，2GB 的文件就要占 2GB 内存。
